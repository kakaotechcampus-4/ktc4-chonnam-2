### 4.1 policy.json 필수값의 출처

리소스 이름·주소·경로·식별자는 공개하지 않고 출처 종류를 남긴다. `decision_refs`는 기존 RT-14 결정과 이번 승인에 연결했다.

| policy 필드 | 출처 종류 | 채택 근거 / 한계 |
| --- | --- | --- |
| `region`, `repository`, `project` | 실측 + 기존 결정 | 현재 AWS/EC2·Compose project와 실제 publish artifact를 대조 |
| `mysql_volume`, `media_volume` | 실측 + 승인값 | 승인 후 새로 만든 volume의 소유/용도 label·empty 상태 확인 |
| `mysql_image`, `mysql_uid` | 실측 | 실제 EC2에서 MySQL 8.4 pull, exact digest 확인, network-none/read-only probe로 numeric UID `999` 확인 |
| `parameter_path`, `log_group` | 승인값 + 실측 | 이번 승인 범위에 생성한 SecureString 및 log group을 instance role로 확인 |
| `restart_policy` | 기존 결정 | RT-14 설계 §12.1의 `unless-stopped` |
| `log_retention_days` | 기존 결정 + 승인값 + 실측 | 설계 §11과 사용자 승인 `30`일, 실제 retention 확인 |
| `log_buffer_bytes` | 기존 실측 | RT-14 SP-2에서 사용한 `4194304` bytes (4 MiB), 이번 acceptance에 한정 재사용 |
| `disk_reserve_bytes` | 기존 결정의 후보 + 실측 | 설계 §15 보수적 후보 `10737418240` bytes (10 GiB); 두 image pull 후 free space `41232113664` bytes 확인. 운영 용량 보장 아님 |
| `memory_reserve_bytes` | 실측으로 산출 | production OCR 초기화 peak RSS `480731136` bytes의 2배를 MiB로 올림한 `961544192` bytes. probe 후 available memory `3278245888` bytes 확인. 동시 API/MySQL/Worker 용량 보장 아님 |
| `packet_margin_bytes` | 승인값 + DB 실측 | 8 MiB 승인, 실제 session 64 MiB guard 통과 |
| `decision_refs` | 기존 결정 + 승인 | 기존 RT-14 근거와 이번 temporary acceptance 승인 연결; fixture 결정을 차용하지 않음 |

policy validation, controller source와 RC 일치, immutable config 생성, 파일 소유/권한, app password와 URL-encoded DB URL의 일관성을 확인했다. Secret 값은 출력하지 않았다.

MySQL digest는 `sha256:a0225d1ea6631c8bc2385dc4c2faba17bbf1834ecf369e1659a9a382bd8d5dd7`이다. 새 IAM role/policy, KMS CMK, EC2/EBS는 만들지 않았다. 기존 리소스를 덮어쓰거나 DB/volume을 초기화하지 않았다.

당초 승인된 DDNS 우선 경로에서 EIP 선행으로 변경한 직접 근거는 사용자의 명시적 추가 승인이다. 10/31 allocate/associate dry-run PASS와 카테캠 도메인 가이드 §2 일치는 **운영자가 제공한 추가 확인 결과**로 구분한다. 이 문서화에서 직접 읽은 실행 증거는 실제 할당·연결 각 1회 성공, tag와 전후 불변성이다. EIP 제약·채택에 대한 상위 결정 갱신은 **RD-14a 갱신 PR에서 반영**하며 여기서 기존 결정을 고치지 않는다. 주소·allocation/association ID는 비공개로 보관한다.

| TLS / public smoke | 검증자 PC에서 system trust·hostname 검증, TLSv1.3, Web 200·revision 일치, same-origin API health·정상 404·HTTPS redirect PASS |

등록된 8종은 `HINT_EXTRACT`, `COARSE_SEARCH`, `FINE_VERIFY`, `INCIDENT_CLIP_BUILD`, `PLATE_READ`, `OVERLAY_TIME_READ`, `PLATE_IMAGE_EXPORT`, `REPORT_VIDEO_EXPORT`다. 단순 process alive 확인으로 대체하지 않았다. production image의 offline OCR acceptance와 실제 두 OCR job 실행을 함께 확인했다.

**Actions 결과 경계:** [deploy Actions 전체](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/actions/runs/41177301122)는 당시 hostname 미등록으로 post-SSM public step에서 **FAIL**했다. EC2 remote controller 배포는 PASS였다. 이후 사용자 설정 완료 후 **별도 검증자 PC public smoke가 PASS**했으며, Actions 전체 결과를 소급해 바꾸거나 전체 성공으로 표시하지 않는다.

public smoke는 exact RC의 수정하지 않은 `deploy/public_smoke.py`를 허용된 검증자 PC에서 실행해 exit `0`을 확인했다. GitHub-hosted runner는 Caddy 허용 대상이 아니므로 정상적으로 403을 받을 수 있다. 이를 해결하기 위해 Caddy/SG 허용 범위를 넓히지 않았다.

## 12. 재현 방법과 증거 보관

**private evidence는 운영자 보호 폴더에 보관(위치 비공개)**한다. 실제 식별자·secret·원본 로그·입력/결과 영상은 공개 문서나 PR에 붙이지 않는다.

1. 운영자는 작업 트리와 최신 develop/CI를 확인하고, 현재 runbook·workflow의 실행 gate와 사용자 승인을 대조한다. SSO·OIDC·SSM 경로를 사용한다.
2. `rt14-deploy.yml`의 `operation=publish`로 새 image를 만들고 secret/Web/media/offline OCR acceptance와 SHA·digest를 기록한다. image URI와 인프라 식별자는 보호 입력으로만 전달한다.
3. 실제 host/resource에서 policy 필수값의 근거를 확인한다. secret은 보호 source에 입력하고 존재 여부만 기록한다. 신규 리소스·보안 경계 변경은 승인 범위를 확인한다.
4. exact image/revision/immutable config tuple로 `operation=deploy`를 실행한다. controller의 MySQL→실제 session packet→migration→API/Worker→health→promotion 순서를 지키고 상태 불명 시 중단한다.
5. 허용된 검증자 PC에서 배포 RC의 `deploy/public_smoke.py`를 수정 없이 사용한다. DNS/TLS/Web revision/same-origin API/404를 확인하며 runner용 허용 범위 확대는 하지 않는다.
6. 개인정보·전송 권한이 확인된 작은 실제 MP4 1건을 HTTPS API에 등록·업로드·분석한다. 필요한 상황 확인 후 job claim/attempt/상태, usage, readout, asset 및 최종 CaseView/Package를 각각 확인한다.
7. DB-derived job 시각, media metadata와 실제 byte 길이, 자원 표본, CloudWatch 상관 event를 보호 증거로 대조한다. 종료 health/release 불변성과 남은 운영 상태를 기록한다.

이 절은 공개 가능한 절차 설명이다. 이번 문서 PR에서 위 동작을 재실행한 것은 아니다. 기존 리소스/데이터 발견, migration 상태 불명, packet/health 문제는 자동 재시도·초기화 대신 운영자 판단으로 넘긴다.
