# 제품 전략 (Product Strategy)

> Migration source: 서비스 기획안 1.3의 과제 4 및 차별화 관련 항목. 기술 세부 구현과 일정은 각각 `architecture/`, `modules/`, `management/` 문서에서 관리한다.

## 1. 단순한 AI 연결형 서비스(Wrapper)와 다른 지점

범용 비전-언어 모델(VLM)에 이미 잘라낸 짧은 영상을 넣고 내용을 묻는 것과 달리, 대신고는 다음의 **전체 사용자 흐름과 상태 관리**를 다룬다.

```
자연어 기억 단서
→ 여러 블랙박스 파일과 시간축 탐색
→ 사건 후보 탐색(Candidate Search)
→ 후보 장면의 근거 정밀 검증(Fine Evidence)
→ 상위 3개 후보 제시 + 사용자 보정
→ 사건 전후 증거 구간(Evidence Interval) 구성
→ 번호판 / 발생시각의 출처 / 위치 정보 보강
→ 파일 규격 / 신고요건 검사
→ 신고자료 묶음(Package) 생성
→ 안전신문고 제출 단계로 연결(Handoff)
```

핵심은 특정 프롬프트 자체가 아니라 **장시간 영상 → 사건 → 검증 가능한 근거 → 신고 준비가 완료된 자료**를 하나의 상태 있는 작업 흐름으로 연결하고, 사용자가 결과를 수정했을 때 필요한 단계만 다시 실행하는 것이다.

## 2. 3개월 뒤에도 남겨야 할 자산

### 데이터 자산

- 사전에 고정한 실제 장시간 영상 평가셋(locked real long-video eval)
- 정답 사례(Positive)와 헷갈리기 쉬운 정상 사례(Hard-negative)
- AI가 틀리거나 불확실했던 사례와, 사용자가 후보·시간·유형·번호판·위치 등을 직접 수정한 기록(failure / correction data)
- 반복 가능한 평가 체계(evaluation harness)

### 차별화된 UX 후보

- 자연어 기억 단서 입력에서 시작하는 단계형 작업 화면 — 1.3의 「대화형 AI 에이전트 UI」 후보는 프로토타입 단계에서 단계형 구조로 바뀌었다(`core-user-flow.md` §2)
- 구조화된 사건 근거 카드(Structured Evidence Cards)
- 사용자가 결과를 보정하면 필요한 단계만 다시 실행하는 흐름

### 책임 있는 작업 흐름

- 차량번호·위치·발생시각·외부 신고 단계를 각각 **정보의 출처(provenance)**와 함께 관리
- 최종 확인과 실제 외부 제출은 사용자가 직접 수행

> 특정 모델 자체보다 **실제 장시간 블랙박스 영상에서 무엇을 왜 놓치는지 반복해서 재현할 수 있는 평가체계와, 그 결과를 사용자가 직접 검증 가능한 근거와 신고 준비 단계까지 연결하는 작업 흐름**을 자산으로 남긴다.

### 초기 데이터 부족 문제(Cold Start)

사용자 측 초기 데이터 부족 문제는 크지 않다. **사용자는 자신의 기존 블랙박스 영상만으로 바로 가치를 얻을 수 있다.** 다른 사용자의 데이터가 쌓일 때까지 기다릴 필요가 없다.

반면 서비스 개발 측에는 초기 데이터 부족 문제가 있다. **실제 장시간 영상 평가 데이터셋은 처음부터 직접 구축해야 한다.** 평가(`eval`) 작업이 프로젝트 초반부터 집중적으로 배치되는 이유다.

### 단기 대응과 장기 자산으로 남는 방식

같은 문제를 해결하더라도, **현재 모델이나 상황에 맞춘 임시 최적화**와 **모델이 바뀌어도 계속 활용할 수 있는 데이터·평가체계·입출력 구조·사용자 흐름**은 구분해서 본다.

대신고는 단기적으로 필요한 최적화도 사용하되, 프로젝트가 끝난 뒤에도 다시 활용할 수 있는 구조와 데이터를 장기 자산으로 남기는 것을 우선한다.

| 단기 대응 | 장기 자산으로 남는 방식 |
| --- | --- |
| 영상 일부만 띄엄띄엄 분석하거나, 저해상도·저프레임 영상의 처리 설정을 조절 | **사전에 고정한 실제 장시간 영상 평가셋 + 실패 사례셋**을 구축해 모델이 바뀌어도 동일한 기준으로 성능을 비교 |
| 특정 프롬프트 문구에 의존해 결과를 개선 | AI가 어떤 사건 근거를 어떤 형식으로 내야 하는지 **구조화된 사건 근거 형식(structured evidence schema)**을 정의 |
| 결과가 애매할 때 정밀 검증(Fine)을 반복 실행 | 정답 사례와 **헷갈리기 쉬운 정상 사례(Hard-negative)**를 모아 모델·프롬프트·참고자료 방식의 성능을 반복 비교할 수 있는 평가체계를 구축 |
| 사용자에게 시간·차량·위치 등의 검색 단서를 처음부터 많이 요구 | 사용자가 자연어로 대략적인 기억부터 입력하고, 결과를 보며 수정할 수 있도록 **자연어 보정 + 사건 상태(Case State) 관리** |
| 특정 AI 모델에 맞춰 검색·검증 로직을 각각 구현 | 어떤 모델을 사용하더라도 교체할 수 있도록 **후보 탐색과 정밀 검증의 공통 입출력 규격(I/O contract)**을 정의 |
| — | 발생시각·위치·번호판 정보에 대해 **값뿐 아니라 출처와 확신 상태를 함께 관리**하고, 확실하지 않을 때는 판단을 보류(abstention)할 수 있도록 설계 |
| — | 사건 탐색 결과를 **신고요건 검사(Evidence Rule)와 안전신문고 제출 준비 단계(Handoff)**까지 연결하는 흐름을 제품 구조로 남김 |

핵심은 특정 모델이나 특정 프롬프트를 잘 다루는 것이 아니라, **모델이 바뀌어도 평가하고 교체하고 개선할 수 있는 구조를 만드는 것**이다.

## 3. AI-Hub 데이터의 역할

1.3에서는 AI-Hub 경찰청 원천 데이터를 단순한 파인튜닝(fine-tuning)용 데이터로만 보지 않고 다음과 같이 활용할 수 있는 후보로 둔다.

```
AI-Hub
├─ 평가 데이터 출처(Evaluation source)
├─ 정답 / Hard-negative 참고 사례 출처
└─ 향후 모델 학습 데이터 출처(Future Training source)
```

같은 사건의 연속 프레임이 학습 데이터와 평가 데이터에 동시에 섞이지 않도록 **사건(event) 또는 사례(case) 단위로 분리해 관리해야 한다.**

## 4. 범용 AI 모델의 발전은 대신고에 유리하다 — 1.3의 판정

1.3에서는 이 항목을 **순풍**으로 판정했다.

> 범용 VLM의 성능이 좋아지고 비용이 낮아질수록 장시간 영상의 후보 탐색과 정밀 검증 성능·비용은 자연스럽게 개선된다. 반면 대신고가 쌓는 평가·실패 데이터, 근거와 출처 관리, 신고요건 규칙, 사건 상태, 사용자 보정 흐름, 안전신문고 연결 구조는 그대로 남거나 더 가치가 커진다.

### 모델이 훨씬 좋아지면 없어질 수 있는 것

- 저해상도·희소 샘플링에 대응하기 위한 일부 임시 우회 방식
- 정밀 검증(Fine)의 반복 재시도
- 사용자에게 상세한 검색 단서를 많이 요구하는 UX
- 특정 기초 시각 인식 모델(primitive detector)의 보조
- 일부 대안 모델 분기(routing) 구조의 복잡성

### 모델이 훨씬 좋아지면 새롭게 가능해질 수 있는 것

- 사용자가 시간대를 거의 기억하지 못해도 수시간 영상이나 SD카드 전체를 탐색
- 한 영상에서 여러 사건을 자동으로 후보화
- 전방·후방 등 여러 채널을 통합 탐색
- 시간적 전후 관계가 모호한 사건에서도 높은 재현율(Recall) 확보
- 사고·보험·분쟁 등 다른 **장시간 영상 → 근거자료 준비** 영역으로 확장

위 항목은 1.3에서 기록한 향후 가능성이며 현재 MVP 범위는 아니다.

## 5. 비용에 대한 원칙

운영 비용 목표를 임의의 금액으로 먼저 정하지 않는다. 실제 평가를 통해 다음 항목을 측정한다.

- 처리 지연시간(latency)
- 사용 토큰 수(tokens)
- 전체 영상 중 정밀 검증에 투입되는 비율(Fine exposure ratio)
- 원본 영상 1시간당 처리 원가(source-video-hour당 원가)
- 사용자 1건당 평균 탐색 범위와 재탐색 횟수

`원본 영상 1시간당 처리 원가`(runtime 분모)에 어떤 비용을 포함할지는 `modules/eval/initial-evaluation-plan.md` §2에서 관리한다. 평가용 clip 단위 비용과 runtime 원가를 섞지 않는 원칙은 `architecture/module-architecture.md` §9-3이 정한다. 이 문서에는 중복해서 적지 않는다.

1.3에서 기록한 비용 절감 방향은 다음과 같다. **사용자의 시간 단서로 탐색 범위를 먼저 줄이고, 저비용 1차 탐색(Coarse)을 사용하며, 후보 구간에만 정밀 검증(Fine)을 적용한다.** 필요하면 프록시(proxy), 색인(index), 캐시(cache)를 검토하고 AI 에이전트의 반복 실행 횟수에도 상한을 둔다.

## 6. 공개 / 비공개 원칙

### 공개해도 되는 것으로 기록된 것

- 문제 정의
- 비식별화된 데모(Demo)
- 평가 방법
- 집계된 성능 비교 결과(aggregate benchmark)
- 적용 전·후 비교(Before/After)

### 출시 후에도 비공개로 관리할 것으로 기록된 것

- 실제 사용자의 원본 영상
- 차량번호와 정확한 위치
- 세부 실패 사례와 Hard-negative 데이터셋
- 악용(abuse) 대응 방식
- 민감한 모델 분기(routing) 정보

## 7. 가격과 재사용 가능성(Retention)

- 대신고가 제공하는 가치는 기능 목록 자체보다 **장시간 영상에서 찾던 사건과 신고 준비 자료가 이미 정리되어 있는 상태**라는 결과에 있다.
- 가격은 **아직 정하지 않는다.** 실제 불편의 크기, 사용 빈도, 사용자가 절약하는 시간의 가치를 확인한 뒤 결정한다.
- 신고기록·신고기한·처리결과·통계처럼 사용자가 다시 서비스를 찾게 만드는 기능(retention pattern)은 참고할 가치가 있지만, 10주 프로젝트의 핵심 개발 범위는 아니다.

## 8. 사용자 보정 데이터의 선순환 가설 (Correction Flywheel)

```
AI가 사건 후보와 근거를 제시
→ 사용자가 사건·신고유형·번호판 등을 확인·수정
→ 수정 결과를 실패 사례·평가 데이터에 반영
→ 다음 모델·프롬프트·참고 사례 방식의 성능 비교에 활용
```

즉 사용자의 수정이 일회성으로 끝나는 것이 아니라, **다음 평가와 개선에 활용할 수 있는 데이터 자산으로 축적되는 선순환 구조**를 만든다는 가설이다.

이 흐름을 실제 데이터 자산으로 만드는 구체적인 구조는 모듈 아키텍처와 평가(`eval`)·사례(`case`) 관련 문서에서 관리한다. 재사용 정책(평가 재사용 / 학습 재사용 2단계 · 동의 · 익명화)은 `modules/case/decisions/correction-log-reuse.md`가 소유한다.
