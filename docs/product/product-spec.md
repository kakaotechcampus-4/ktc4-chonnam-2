# 대신고 Product Spec

> Migration source: 서비스 기획안 1.3. 새 결정을 추가하지 않고 제품 수준 내용만 추출했다.
> **변경 절차:** 이 문서의 Must/Won't·불변 경계·지원 범위를 바꾸는 최종 승인자는 PM(김준영) 1명이다. module Owner가 변경을 제안할 때는 주간 회의 안건으로 올린다(`management/cross-cutting-decisions.md` B-1).

## 1. 타깃

핵심 타깃은 **위험한 교통위반을 목격했고 이미 신고할 의향이 생겼지만, 운전 중 정확한 사건 시각·위치를 별도로 기록하지 못한 블랙박스 운전자**다.

초기 최소 시장은 **PC에서 전방 1채널 블랙박스 영상을 직접 확인해 안전신문고 교통위반 신고를 준비하는 운전자**, 특히 신고 의향은 있지만 사건 시각을 정확히 기록하지 못한 사람이다.

제품은 신고할 마음이 없던 사람을 게임화·보상으로 자극하는 것이 아니라, **이미 생긴 신고 의향이 준비 과정의 마찰 때문에 사라지지 않도록 하는 것**을 지향한다.

> **이 타깃은 아직 검증되지 않은 Proto-persona다.** 1.3의 `박신고(가명) / 32세`는 실제 신고 경험의 행동 흐름을 바탕으로 만든 **Proto-persona**이며, `매일 자가용으로 출퇴근하는 직장인` 같은 세부 설정은 **스토리용 가정**이다. 위에 적은 행동 속성(신고 의향이 있고, 사건 시각·위치를 기록하지 못함)만이 핵심이며, 이것이 실제 사용자에게도 맞는지는 `user-validation-plan.md`가 검증할 대상이다.

## 2. 문제

> 교통위반을 이미 신고하려고 마음먹은 운전자는 사후 신고를 준비할 때 블랙박스에서 사건을 다시 찾고, 증거구간·시간·장소·차량번호·신고요건을 재구성해야 하므로 실제 제출 전 준비 단계에서 이탈할 수 있다.

긴 영상 탐색·편집·용량 조정의 불편 자체는 정성적으로 확인됐지만, **사건 재탐색이 최우선 pain인지, 실제 준비 시간이 얼마인지, 준비 마찰이 신고 포기에 얼마나 영향을 주는지는 아직 검증 대상**이다.

## 3. 제품 약속 / 포지셔닝

> 사용자가 기억나는 시간·차량·상황·위치 단서를 자연어로 말하면 장시간 블랙박스에서 사건 후보와 전후 증거 구간(Evidence Interval)을 먼저 구성하고, 사용자는 구조화된 확인·수정만 거쳐 신고 준비 완료 상태까지 도달하도록 돕는다.

대신고의 차별점은 **사용자가 위반 순간을 이미 찾은 뒤 후처리하는 것**이 아니라, **장시간·다중 블랙박스에서 사건 후보와 전후 증거 구간 자체를 먼저 구성한 뒤 후속 단계(downstream) 신고 준비까지 연결하는 것**이다.

## 4. 2단계 핵심 가설

> 기억 단서만으로 장시간 블랙박스에서 사건 후보와 전후 증거구간을 먼저 구성하고 신고정보를 구조화해 제공하면, 기존 수동 workflow보다 사용자 직접 작업시간·검토부담이 줄고 실제 신고 준비 완료/제출 전환이 증가한다.

- **기술 하위가설:** 초기 지원 4종의 교통위반 사건을 실제 장시간 블랙박스 영상에서 **상위 3개 후보 안에 높은 확률로 포함되도록 탐색하면서도, 처리 비용과 시간을 현실적인 수준으로 유지할 수 있다.**
- **제품 하위가설:** 위반 장면과 신고자료가 자동 준비된 상태라면 기존 방식보다 실제 신고 완료 의향/행동이 증가한다.

## 5. Must / Won’t

| Must — 2단계까지 만들 것 | Won’t — 이번에는 하지 않을 것 |
| --- | --- |
| 자연어로 입력한 기억 단서 → 시간·차량·상황 정보 구성 및 수정 | 신고 의향이 없는 사용자를 게임화·보상으로 적극 유도 |
| 초기 4종 교통위반 사건 탐색 | 모든 도로교통법 위반 유형 지원 |
| 1차 탐색(Coarse)으로 상위 후보 생성 + 후보 장면 정밀 검증 | AI가 법적 위반 여부를 최종 확정 |
| 사건 전후 증거 구간 구성 + 영상 파일 경계에 걸친 사건 처리 | 사용자 승인 없는 무인 자동신고 |
| Top-3 구조화 카드 + 사용자 `맞음/아님/다른 후보/조금 전·후` 보정 | 자율형 다중 AI 에이전트 기반 영상 탐색 |
| 대상 차량 번호판 best frame/OCR + 사용자 수정 | baseline 전에 ADAS/CV Candidate Generator 선행 구축 |
| timestamp 값 + 출처(영상 내 표시(Video overlay) / 파일명(Filename) / Metadata / User / Unknown) 관리 | 신뢰 가능한 출처가 없는 시각을 AI가 임의 생성 |
| GPS 정보가 있으면 위치 후보·주소·장소명·검색어를 보강하고, 없으면 사용자 입력 단서를 유지 | 자체 지도 UI / GPS 없는 위치 완전자동 확정 |
| 파일규격 검사 + 신고용 파생영상 + 신고요건 점검 + handoff | 얼굴 모자이크를 신고 필수 Must로 구현 |
| 원본 영상과 신고용 파생 영상을 구분하고 개인정보 처리·삭제 정책 설계 | 신고기록·CSV 내보내기·통계 등 후속 관리 기능을 10주 핵심 개발 범위에 모두 포함하지 않음 |

### Won’t의 두 종류 — 버린 것 / 보류한 것

위 Won’t 표는 “이번에 만들지 않는다”만 말할 뿐 **다시 열 수 있는지**를 구분하지 않는다. 1.3은 그 구분을 별도 표로 남겼고, 그것이 이 제품에서 재논의를 막거나 허용하는 유일한 근거다. **아래 표가 그 canonical 위치다.**

- **버림** — 다시 열지 않는다. 재논의하려면 Product Spec 변경 절차를 거친다.
- **버림(MVP)** — 이번 범위에서 제외. 제품 방향 자체를 부정한 것은 아니다.
- **보류** — 폐기하지 않았다. **failure가 필요성을 증명할 때만** 연다(조건과 개방 절차는 `modules/search/decisions/challenger-policy.md`).

| 안 | 상태 | 이유 |
| --- | --- | --- |
| 사진 1장 기반 신고 Agent | 버림 | Long-video problem/Agent workflow가 약하고 영역 중복 |
| 신고콕과 동일한 편집·압축 중심 제품 | 버림 | downstream에 실제 경쟁서비스 존재, 차별점 부족 |
| 상세한 사건설명 필수입력 | 버림 | 자연어 기억 단서와 correction으로 시작 |
| AI 법적 최종판정 | 버림 | visual event + Evidence + 사용자 확인으로 분리 |
| 우리 서비스 자체 지도 UI | 버림(MVP) | 안전신문고에 검색/핀조정 존재, 이중작업 |
| GPS 없는 위치 완전자동추정 | 버림(MVP) | 위험 대비 가치 낮음, user hint fallback |
| 얼굴 모자이크 신고 Must | 버림(MVP) | 필수 제출요건으로 확인 안 됨. privacy architecture는 별도 필수 |
| 2시간 원본을 무조건 전체 서버 업로드 | 버림 | 전송·비용·privacy 부담, 범위축소/proxy/clip 전략 필요 |
| VideoChat3 처음부터 필수 | **보류** | 기본 검색 방식이 사건을 잘 찾지 못하거나, 사건의 전후 흐름·시간 관계를 이해하는 데 한계가 확인되면 대안으로 검토 |
| SentrySearch 처음부터 필수 | **보류** | 현재 검색 방식의 사건 탐색 성능이 부족하다고 확인되면 대안으로 검토 |
| ADAS/CV Candidate Generator | **보류** | 현재 방식이 차선·차량·신호 등 기본 시각 정보나 대상 차량을 안정적으로 인식하지 못할 때 재검토 |
| TrafficRAG 전체 시스템 | **보류** | 먼저 고정된 참고 사례를 제공했을 때 실제 성능 향상이 있는지 A/B 테스트한 뒤, 효과가 확인되면 자동 검색 방식으로 확장 검토 |
| 자체 VLM fine-tuning / GPU VM | **보류** | 외부 모델/API만으로는 필요한 성능을 달성하기 어렵거나 운영 비용이 지나치게 높다고 확인될 때 검토 |
| 자율 multi-agent video exploration | **보류** | 우선 단순하고 재현 가능한 `1차 탐색 → 정밀 검증` 방식부터 구축·평가한 뒤 필요성이 확인되면 검토 |
| 사용자 승인 없는 자동신고 | 버림 | 외부 시스템에 실제 영향을 주며 되돌리기 어려운 행동 |
| 참교육/벌금/신고 게임화 | 버림 | 안전·공정·완료·처리결과 중심 UX |

> 위 Won’t 표에서 `자율 multi-agent video exploration`과 `baseline 전 ADAS/CV 선행 구축`은 **버림이 아니라 보류**다. 10주 안에는 만들지 않지만, 조건이 충족되면 열린다.

**challenger는 현재 기본으로 쓰는 방식(baseline)이 잘 안 될 때 비교·대체 후보로 꺼내는 기술**

## 6. 초기 지원 교통위반 사건 4종

- 신호위반
- 중앙선 침범
- 진로변경(백색 실선 침범)
- 이륜차 안전모 미착용

선정 이유는 다음과 같다.

1. 실제 주행 중 운전자가 위험하거나 불공정하다고 느끼기 쉬운 대표적인 위반 유형을 포함한다.
2. 신호 상태 → 정지선 → 차량 통과처럼 **시간 순서와 전후 맥락을 함께 판단해야 하는 상황**을 검증할 수 있다. 또한 차선 종류와 차량 이동 경로, 선을 넘는 순간 등을 함께 분석해야 하는 유형도 포함한다.
3. 신호등·정지선, 차선·차량 이동 경로, 이륜차·사람·안전모 여부 등 **서로 다른 시각 정보 인식 능력**을 함께 검증할 수 있다.
4. 평가 및 향후 학습에 사용할 수 있는 데이터 확보 가능성을 고려했다. AI-Hub 등에서 관련 교통 데이터와 주석 정보를 평가, 참고 자료, 향후 모델 학습에 활용할 수 있다. **특히 이륜차 안전모 미착용은 관련 데이터가 존재하고, 팀 논의에서도 상대적으로 구현 난도가 지나치게 높지 않을 것으로 판단해 추가했다.**
5. 10주 MVP에서는 모든 교통법규 위반을 지원하지 않고 이 4종에 집중한다. 먼저 **사건 탐색 성능, 헷갈리기 쉬운 정상 사례에 대한 오탐, 처리 비용, 처리 시간**을 검증하고, 실제 실패 원인 분석에서 필요성이 확인될 때만 지원 범위를 넓힌다.

AI가 찾는 것은 **법적으로 위반이 확정된 사건이 아니라, 신고 대상일 가능성이 있는 장면과 사건 후보**다. 최종 신고 유형과 신고 여부는 규칙 검토와 사용자 확인을 거쳐 결정한다.

## 7. 제품 수준 불변 경계

- 중요한 Evidence는 원본/근거와 함께 사용자가 확인·수정할 수 있어야 한다.
- 번호판·시각·위치가 불확실하면 값을 만들어내지 않고 출처와 `확인 필요`/UNKNOWN 상태를 보여준다.
- 실제 안전신문고 제출은 사용자가 직접 수행한다.
- 자체 지도 UI는 MVP 범위가 아니다. 최종 위치 핀은 안전신문고에서 사용자가 확인한다.
- 얼굴 모자이크는 안전신문고 신고의 필수 Must로 확정하지 않는다.
- Source video를 덮어쓰지 않는다.
- 운전 중 스마트폰 조작이나 수동저장 버튼 사용을 필수로 요구하지 않는다. 사후에 자연어 기억 단서로 시작할 수 있어야 한다.
- 사용자의 수정 기록(correction)은 익명화한 뒤에만 평가·개선에 재사용하고, 평가 재사용과 모델 학습 재사용을 구분해 고지하고 동의를 받는다. 재사용 정책의 설계는 `modules/case/decisions/correction-log-reuse.md`가 소유한다.

**사용자 검증 가능성 — 높음.**

AI의 결과는 사용자가 직접 확인하고 수정할 수 있는 형태로 제공한다. 사건 후보는 원본 영상 구간으로 확인할 수 있어야 하고, 정밀 검증 결과는 판단에 사용한 관찰 근거를 함께 보여준다. 번호판은 가장 선명한 장면과 함께 제시하고, 사건 시각과 위치는 각각 어떤 정보에서 가져왔는지 출처를 표시한다. 추천된 신고 유형 역시 사용자가 직접 확인하고 필요하면 수정할 수 있어야 한다.

## 8. 제품 성공 정의

제품 수준에서 확인할 것은 다음이다.

- 사용자가 신고 준비 완료·안전신문고 handoff까지 도달하는가
- 기존 수동 방식보다 검토 후보 수가 줄어드는가
- 사용자 직접 작업시간이 줄어드는가
- handoff/실제 접수 행동으로 이어지는가

`약 20분 → 약 3분`은 평균이나 성과 실측값이 아니라 **사용자 직접 작업시간을 줄일 수 있는지 확인하는 제품 목표 시나리오**다.

## 9. 가장 큰 위험

> 실제 장시간·다중 블랙박스 영상에서 몇 초 동안 발생하는 초기 4종 교통위반 사건을, 사용자가 기다릴 수 있는 처리 비용과 시간 안에서 **최종 상위 3개 후보(Final Top-3)**에 안정적으로 포함시킬 수 있는가.

### 왜 위험한가

- 긴 영상의 대부분은 정상 주행이며, 실제로 찾아야 하는 **대상 사건(target event)**은 몇 초에 불과하다.
- 신호 상태·정지선·차선·차량 이동 경로처럼 **시간 순서와 전후 관계를 판단해야 하는 정보**와, 이륜차·운전자·안전모 착용 여부처럼 **객체 간 관계와 속성 정보**를 함께 분석해야 한다.
- 야간·우천·역광·번호판 반사·가림 등으로 영상 품질의 편차가 크다.
- 하나의 사건이 여러 블랙박스 파일의 경계에 걸쳐 발생할 수 있다.
- 사용자가 기억하는 사건 시각이 부정확하거나 차량 특징에 대한 기억이 불완전할 수 있다.
- 장시간 원본 영상을 처리할 때 발생하는 **업로드 부담, AI/API 사용 비용, 처리 지연 시간(latency), 개인정보 보호 문제**가 사용자 경험을 동시에 제한한다.
- **법적으로 실제 위반인지 여부와 영상에서 관찰되는 교통위반 의심 사건(visual event)을 섞어서 평가하면 성능 기준 자체가 불안정해질 수 있다.** 따라서 AI는 먼저 영상에서 관찰 가능한 사건과 근거를 제시하고, 최종 위반 여부는 규칙과 사용자 확인을 통해 구분한다.

제품 측의 또 다른 핵심 위험은, 이러한 기술적 결과가 실제로 **신고자료 준비(Evidence Preparation)에 드는 사용자 작업과 시간을 줄이고, 최종 신고 완료까지 이어지는가**이다.
