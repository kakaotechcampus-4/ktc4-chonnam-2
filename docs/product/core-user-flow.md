# 대신고 Core User Flow

> **판본과 출처.** 이 문서는 `core-user-flow-1.2`(2026-08-29 작성, 아카이브의 `문서-초안/`)를 정본으로 되돌린 것이다. 그 전까지 이 자리에 있던 것은 2026-08-27 노션 내보내기본으로, 1.2·목업·프로토타입 세 세대를 반영하지 못한 판본이었다.
>
> **갱신 범위.** 1.2를 기준으로 두고, **`apps/prototype`에서 실제로 클릭해 확인한 결과 달라진 부분만** 고쳤다. 1.2에 이미 정확히 적혀 있던 항목은 손대지 않았다. 프로토타입에서 확인한 내용은 `[프로토타입]`으로 표시한다.
>
> **관련 문서.** 화면 구성·문구·컴포넌트 상세는 `design/PROTOTYPE-SPEC.md`와 `modules/web/`이 소유한다. 그쪽이 바뀌는 것은 이 문서를 고칠 이유가 아니다.

## 문서 목적

이 문서는 대신고에서 사용자가 **교통위반 상황을 설명한 순간부터 AI가 장시간 블랙박스 영상을 탐색하고, 사건 후보와 신고자료를 준비하며, 사용자가 필요한 부분만 확인·수정하여 신고 준비를 완료하는 전체 흐름**을 정의한다.

이 문서는 세부 화면 디자인이나 기술 구현 명세가 아니다.

핵심적으로 다음을 정의한다.

* 사용자가 어떤 일을 AI에게 맡기는가
* AI가 어떤 범위까지 자동으로 처리하는가
* 사용자가 언제 확인하거나 개입하는가
* AI 결과가 불확실하거나 시스템이 실패했을 때 어떻게 복구하는가
* 신고자료가 어떤 상태가 되면 안전신문고 제출 단계로 넘어가는가

구체적인 화면 컴포넌트와 세부 마이크로카피는 `modules/web/ux/`, 실제 모델·모듈 구현과 상태값은 각 모듈 문서에서 관리한다.

## 1. 핵심 AI UX 원칙

대신고의 사용자 경험은 다음 구조를 따른다.

> **사용자 목표 → AI에게 위임 → 작업 상태 관찰 → 필요한 순간에만 개입 → 최종 확인**

AI가 많이 개입하는 것 자체가 목표가 아니다.

사용자가 원래 직접 해야 했던

`긴 영상 다시 보기 → 사건 찾기 → 필요한 구간 자르기 → 번호판·시간·위치 확인 → 신고자료 준비`

과정에서 반복적이고 시간이 많이 드는 부분을 AI가 대신하고, 사람은 **자신만이 판단할 수 있거나 오류 비용이 큰 부분**에 집중하도록 한다.

### AI는 다음을 담당한다

```text
사용자 기억 단서 이해
→ 우선 탐색 범위 구성
→ 사건 후보 탐색
→ 후보 비교·검증
→ 사건 근거 정리
→ 번호판 후보 추출
→ 발생시각 확인
→ 위치 정보 보강
→ 신고유형 추천
→ 신고용 파생영상 생성
→ 신고요건 검사
→ 신고자료 정리
```

### 사용자는 다음을 담당한다

```text
내가 찾던 사건이 맞는가?
AI가 이해한 기억 단서가 맞는가?
불확실한 번호판이 맞는가?
AI가 설명한 사건 상황이 내가 본 것과 맞는가?
최종 신고자료가 실제 상황과 맞는가?
실제로 신고할 것인가?
```

AI는 법적 위반 여부를 최종 확정하거나 사용자 승인 없이 신고를 제출하지 않는다.

# 2. 기본 화면 구조

`[프로토타입]` **대신고는 대화형 작업공간(Conversational Workspace)이 아니라 단계형 구조 화면을 사용한다.** 1.2까지 유지되던 `대화형 작업공간` 구조는 목업·프로토타입 단계에서 폐기했다.

자연어는 **§5 「기억 단서 입력」 한 곳에서만** 받는다. 그 이후의 모든 보정과 판단은 **명시적인 버튼과 입력칸**으로 한다.

폐기한 이유는 셋이다.

1. 중요한 판단은 사용자가 **원본·근거를 직접 보고** 확인해야 한다. 채팅 답변으로 대신할 수 없다.
2. 채팅 로그는 되돌아가 고치기 어렵다. 이 제품은 되돌아가 고치는 일이 잦다(§9).
3. 자연어 보정은 「무엇이 유지되고 무엇이 바뀌는지」를 사용자에게 보장하지 못한다. 버튼은 보장한다.

바뀐 것은 **입력 수단**이지 원칙이 아니다. 아래 「구조화 UI가 적합한 영역」과 「중요한 판단을 모두 채팅으로 처리하지 않는다」는 1.2 그대로 유효하며, 오히려 더 강하게 지켜진다.

### 대화 대신 무엇으로 하는가

| 1.2에서 대화로 하려던 것 | 지금 |
| --- | --- |
| AI가 잘못 이해한 내용 수정 | §6 단서 4칸을 그 자리에서 편집 |
| 「조금 전이었어」 같은 자연어 보정 | §9 `조금 전이에요` / `조금 후예요` 버튼 |
| 분석 진행상황 설명 | §7 작업 목록 + 시간축 + 경과시간 |
| 결과가 없거나 실패했을 때 다음 행동 안내 | §22·§23 전용 화면과 출구 버튼 |

### 구조화 UI가 적합한 영역

* 사건 후보 영상
* 상위 후보 비교
* 사건 근거
* 번호판 이미지
* 발생시각과 출처
* 위치 단서
* 신고유형
* 신고요건
* 최종 신고자료

중요한 판단을 모두 채팅으로 처리하지 않는다.

# 3. 정보 상태와 작업 상태

정보의 신뢰 상태와 AI 작업 진행 상태는 서로 구분한다.

## 3-1. 정보 상태

번호판·발생시각·위치 등 중요한 값에는 가능한 경우 **값 + 출처 + 상태**를 함께 표시한다.

### AI 추정

AI가 영상 또는 사용자 단서를 바탕으로 추론한 값.

### 출처 확인됨

영상 화면, 파일 메타데이터, GPS 등 확인 가능한 출처에서 얻은 값.

### 사용자 확인됨

사용자가 직접 보고 확인하거나 수정한 값.

### 확인 필요

일부 정보가 불확실하여 사용자의 확인이 필요한 값.

### 알 수 없음(UNKNOWN)

신뢰할 만한 근거가 없어 값을 확정하지 않는 상태.

`AI 인식`, `사용자 확인 필요` 등 별도의 유사 상태 표현을 추가하지 않고 위 상태를 일관되게 사용한다.

## 3-2. 작업 상태

AI 분석 진행은 별도로 표현한다.

```text
완료
진행 중
대기
부분 완료
중단
실패
```

정보의 신뢰도와 작업 진행 여부를 같은 표시 체계로 섞지 않는다.

# 4. 전체 핵심 흐름

```text
블랙박스 영상 올리기
        ↓
영상에서 읽은 정보 확인 (촬영 시간 · 화면 시각 유무 · GPS 유무)
        ↓
AI가 할 수 있는 일과 한계 안내
        ↓
사용자가 기억나는 사건 설명
        ↓
AI가 시간 / 차량 / 상황 / 위치 단서를 구조화
        ↓
사용자가 AI의 이해와 우선 탐색 범위 확인
        ↓
AI 분석 시작
        ↓
진행상황과 현재 탐색 범위 표시
        ↓
사건 후보 탐색·비교·검증
        ↓
결과 상태에 따라 분기
        │
        ├─ 유력 후보 있음
        │      → 가장 유력한 후보 + Top-3 접근
        │
        ├─ 여러 후보가 비슷함
        │      → 후보 비교
        │
        ├─ 정보 부족
        │      → 필요한 단서만 추가 질문
        │
        ├─ 유사 후보만 있음
        │      → 부분 결과 + 범위 조정
        │
        └─ 실제 분석 실패
               → 복구 / 재시도
        ↓
사용자가 사건 선택 또는 보정
        ↓
AI가 후속 신고 준비 자동 수행
        ↓
필요한 정보만 사용자 확인·수정
        ↓
신고요건 검사
        ↓
신고자료 최종 확인
        ↓
사용자 최종 승인
        ↓
신고자료 묶음 생성
        ↓
안전신문고 제출 단계로 연결
        ↓
실제 제출은 사용자
```

결과 분기의 구체적인 임계값은 현재 고정하지 않는다.

**어떤 결과를 단일 유력 후보로 보여줄지, 여러 후보 비교로 보낼지는 실제 평가 결과를 바탕으로 결정한다.** 임계값이 정해지기 전까지는 **항상 비교 화면**으로 보낸다(§8-2).

`[프로토타입]` **「정보 부족 → 필요한 단서만 추가 질문」 분기는 만들지 않았다.** 단서가 부족하면 되묻지 않고 그대로 탐색한 뒤, 결과가 없을 때 §22의 출구를 준다. 되묻는 편이 나은지는 사용자 평가에서 확인한다.

## 4-1. 진행 단계 표시

`[프로토타입]` 사용자에게는 위 흐름을 **7단계**로 압축해 보여준다.

| 단계 | 사용자가 하는 일 | 이 문서의 절 |
| --- | --- | --- |
| 1 영상 올리기 | 블랙박스 파일·폴더를 올린다 | §4 |
| 2 사건 설명 | 기억나는 만큼 자연어로 적는다 | §5 |
| 3 범위 확인 | AI 해석과 탐색 범위를 고친다 | §6 |
| 4 사건 찾기 | 기다리거나, 중단하거나, 조건을 고친다 | §7 · §22 · §23 |
| 5 사건 선택 | 후보를 비교하고 고르거나 보정한다 | §8 · §9 |
| 6 정보 확인 | 번호판과 신고 상황을 확인한다 | §10–§19 |
| 7 신고자료 | 전체를 읽고 자료를 만들어 넘긴다 | §20 · §21 |

**후보 없음·분석 실패도 4단계로 표시한다.** 실패는 다른 단계가 아니라 같은 단계의 다른 결과다. 이 표시는 **읽기 전용이며, 눌러서 이동하지 않는다.**

# 5. 시작과 기억 단서 입력

`[프로토타입]` 영상을 올리는 즉시 **영상에서 읽은 것을 먼저 보여준다** — 촬영 시간, 화면에 시각이 찍혀 있는지, GPS 기록이 있는지. **GPS가 없다는 사실은 여기서 말한다.** 마지막 handoff(§21)에서 처음 알게 해서는 안 된다.

`[프로토타입]` **「화면에 시각이 없다」와 「확인하지 못했다」는 다른 말이다.** 앞은 사실이므로 그대로 적고(그러면 파일 기록으로 계산한다 — §13), 뒤는 §3-1의 `알 수 없음(UNKNOWN)`으로 적는다. **둘을 하나로 합쳐 「없음」이라고 쓰지 않는다** — 없다고 하면 사용자는 화면을 다시 보지 않는다. 이 시점에 읽는 것은 **표시가 있는지 없는지뿐이고 시각 값은 읽지 않는다**(`architecture/module-architecture.md` §7-1). 둘을 구분하는 판정 기준은 `readout` Technical Spec의 미결 항목이다. 읽을 수 없는 파일은 건너뛰되 건너뛴 사실을 보여주고, 전체를 중단시키지 않는다(§23).

그리고 현재 서비스 범위를 짧게 안내한다.

```text
대신고는 블랙박스 영상에서
신고할 가능성이 있는 사건을 찾아드립니다.

현재 지원
• 신호위반
• 중앙선 침범
• 진로변경
• 이륜차 안전모 미착용

AI가 보여주는 결과는 법적 위반 확정이 아니라
신고할 가능성이 있는 사건 후보입니다.

실제 사건과 주요 신고정보는
제출 전에 직접 확인해주세요.
```

이후 사용자는 자연어로 상황을 설명한다.

```text
무슨 일이 있었는지
기억나는 만큼 말씀해주세요.

예)
시간     6시 반쯤 / 퇴근길 7시 전후
상황     빨간불인데 직진 / 실선을 넘어 끼어듦
차량     흰색 SUV / 검은 승용차 / 오토바이
위치     미금역 근처 / ○○IC 지난 뒤
```

사용자:

> “6시 반쯤 흰 SUV가 실선을 넘어 끼어들었어요. 미금역 근처였던 것 같아요.”

필수 정보를 모두 정확하게 기억할 필요는 없다.

`[프로토타입]` 여기에 두 가지 규칙을 더한다.

* **입력 중에 실시간으로 파싱 결과를 보여주지 않는다.** 문장이 끝나기 전의 틀린 해석은 도움이 아니라 방해다. 구조화 결과는 제출 후 §6에서 한 번에 보여준다.
* **빈 입력을 막지 않는다.** 「시간 단서 없이 전체 찾기」로 안내하고 그대로 진행한다.

# 6. AI의 이해와 탐색 범위 확인

AI는 바로 분석을 시작하지 않고 사용자의 말을 먼저 구조화해서 보여준다.

```text
제가 이렇게 이해했어요.

시간
18:30 전후

차량
흰색 SUV

상황
백색 실선을 넘어 차로를 변경한 상황

위치
미금역 근처

우선 확인 범위
18:15 ~ 18:45
해당 구간의 영상 9개
```

사용자는 다음 중 하나를 선택한다.

```text
[맞아요, 찾아주세요]
[내용 수정]
[탐색 범위 조정]
```

여기서의 확인 목적은 AI의 내부 계획을 승인받는 것이 아니라 **잘못 이해한 조건으로 장시간 분석을 수행하여 시간과 비용을 낭비하는 것을 막는 것**이다.

`42개 중 9개`처럼 탐색 범위를 줄이는 경우에도 나머지 영상을 폐기하는 것이 아니라 **우선 탐색 범위를 정한 것**임을 명확히 한다. `[프로토타입]` 이것은 **문장과 그림 둘 다로** 말한다 — 「나머지 33개는 그대로 남습니다」와 시간축 위의 흐린 구간.

`[프로토타입]` 단서를 보여줄 때 두 가지를 지킨다.

* **원문의 어느 부분에서 나왔는지 함께 보여준다** — 「"흰 SUV"에서」. 사용자가 AI의 해석을 자기 말과 대조할 수 있어야 한다.
* **못 알아들은 항목은 「못 알아들었어요」로 표시한다. 지어내지 않는다.** 빈 값을 그럴듯한 기본값으로 채우면 사용자가 고칠 기회를 잃는다.

각 단서는 그 자리에서 편집할 수 있고, 탐색 범위도 사용자가 직접 조정할 수 있다.

# 7. AI 분석 진행

분석 중에는 로딩 화면만 보여주지 않는다.

```text
사건을 찾고 있어요.

✓ 우선 확인 범위 구성
  42개 중 9개 파일

● 사건 가능성이 있는 장면 확인 중
  9개 중 4개 파일 확인

○ 후보 장면 비교

경과시간 01:42
```

필요하면 중간 결과를 설명한다.

```text
현재까지 흰색 SUV가 등장하는
후보 장면 5개를 찾았습니다.

실선과 차량 이동을 추가로 확인하고 있습니다.
```

충분한 실측 데이터가 확보되기 전에는 부정확한 남은 시간(ETA)을 임의로 표시하지 않는다.

`[프로토타입]` **진행률 퍼센트도 표시하지 않는다.** ETA를 금지한 것과 같은 이유다 — 뒤로 갈수록 느려지는 작업에서 퍼센트는 남은 시간을 잘못 약속한다. 보여줄 것은 셋이다.

```text
시간축이 확인되어 가는 모습
영상 9개 중 4개 확인
경과시간 01:42
```

후보는 **도착하는 대로** 목록에 쌓인다. 끝날 때까지 아무것도 보여주지 않는 화면이 아니다.

사용자는 분석 중 다음 행동을 할 수 있다.

```text
[찾는 조건 수정]
[분석 중단]
```

### 사용자가 분석을 중단한 경우

현재까지 얻은 결과를 버리지 않는다.

```text
분석을 중단했습니다.

현재까지 사건 후보 3개를 찾았습니다.

[현재 후보 보기]
[이어서 찾기]
[조건 수정]
```

`[프로토타입]` **중단은 확인 대화 없이 즉시 실행한다.** 멈추겠다는 사람을 붙잡지 않는다. 곧바로 후보 화면(§8)으로 가되 상단에 **부분 결과임을 밝히고** `이어서 찾기`를 함께 둔다. 「조건 수정」으로 §6에 돌아가는 경우에도 **이미 찾은 후보를 버리지 않는다.**

# 8. 사건 후보 결과

## 8-1. 유력한 후보가 있는 경우

가장 유력한 후보를 먼저 강조할 수 있다.

```text
기억하신 상황과 가장 비슷한 후보입니다.

18:31:48

[영상 재생]
```

### 기억 단서와 비교

```text
✓ 시간대가 비슷함
✓ 흰색 SUV
✓ 백색 실선 확인
✓ 차량이 선을 넘어 이동
? 정확한 위치는 영상에서 확인하기 어려움
```

### AI가 관찰한 내용

```text
흰색 SUV가 백색 실선을 넘어
인접 차로로 이동하는 장면이 확인되었습니다.
```

사용자:

```text
[이 사건 맞아요]
[아니에요]
[조금 전/후예요]
[다른 후보 2개 보기]
```

가장 유력한 후보를 먼저 보여주더라도 **상위 3개 후보는 항상 접근할 수 있어야 한다.**

`[프로토타입]` **분기 임계값이 정해지기 전까지 이 8-1 단독 화면은 만들지 않았다.** 결과가 하나든 셋이든 항상 8-2의 비교 화면으로 보내고, 그 안에서 선택된 후보를 크게 보여준다. 8-1을 별도 화면으로 둘 가치가 있는지는 §26의 미결 항목이다.

### 판단 버튼 배치

`[프로토타입]` **두 종류의 「아니오」를 같은 줄에 두지 않는다.** 「이 후보가 아니라 조금 전이다」와 「전부 아니다」는 결과가 전혀 다른데, 나란히 있으면 잘못 누른다.

```text
시간 보정   [네, 이 사건이 맞아요]  [조금 전이에요]  [조금 후예요]

전체 거절                                        [다 아니에요]
```

---

## 8-2. 여러 후보가 비슷한 경우

```text
비슷한 장면을 여러 개 찾았습니다.

어느 장면을 말씀하신 건지
AI가 확실하게 구분하기 어렵습니다.
```

후보별로

* 원본 영상
* 시간
* 차량 특징
* 사건 근거
* 기억 단서와의 차이

를 보여준다.

```text
후보 1
18:31:48
✓ 흰색 SUV
✓ 백색 실선
✓ 차로 이동

[영상 보기]
[이 사건 선택]
```

Top-3까지 같은 구조로 직접 비교·선택할 수 있다.

`[프로토타입]` 두 가지를 더한다.

* **후보 카드의 번호는 시간축 마커의 번호와 같다.** 목록과 시간축을 눈으로 잇지 못하면 비교가 성립하지 않는다.
* **맞지 않는 관찰 근거를 감추지 않는다.** 「실선인지 점선인지 불분명」, 「차량 색이 더 어둡습니다」처럼 어긋나는 항목을 그대로 적는다. 맞는 항목만 보여주면 사용자는 비교가 아니라 승인을 하게 된다.

# 9. 사용자 보정

사용자가 AI 결과를 수정해도 가능한 경우 전체 작업을 처음부터 다시 하지 않는다.

`[프로토타입]` 보정은 **자연어가 아니라 버튼으로 받는다**(§2). 1.2가 예로 들던 「이 차는 맞는데 조금 전이었어」는 `조금 전이에요` 버튼 하나에 대응한다. 무엇이 유지되고 무엇이 바뀌는지를 제품이 보장해야 하는데, 자유 문장으로는 그 범위를 확정할 수 없기 때문이다.

`조금 전이에요` 를 누르면:

```text
같은 차량을 기준으로
이전 구간을 다시 확인할게요.

유지
차량: 흰색 SUV
상황: 실선 침범

변경
시간 범위: 이전 2분
```

```text
18:29:48 ~ 18:31:48을 다시 확인하고 있습니다.
```

### 사건 안에서 수정하는 정보

* 번호판
* 발생시각 관련 단서
* 위치 단서
* 신고 상황 설명

### 다시 탐색이 필요한 수정

* 시간 범위 변경
* 차량 특징 변경
* 다른 사건 요청

다시 탐색이 필요한 경우 사용자가 추가 분석이 발생함을 알 수 있게 한다.

### 불필요한 재확인 금지

`[프로토타입]` **한 번 `사용자 확인됨`이 된 값은 다시 묻지 않는다.**

* §20 최종 확인에서 §10으로 되돌아와도 상태를 유지한다.
* **시간 보정으로 재탐색해도 번호판·신고 상황 확인은 초기화하지 않는다.** 같은 차량, 같은 상황이기 때문이다.
* 단 **다른 후보를 선택하면 사건에 종속된 값**(발생시각·사건 구간·신고 상황)**만** 초기화한다. 번호판은 유지한다.
* 다른 후보를 선택하면 **AI는 번호판을 다시 읽는다**(새 사건 구간에 대한 새 관찰이다 — `architecture/module-architecture.md` §7-4). 그래도 **사용자가 이미 확인한 값은 유지되고 다시 묻지 않는다.** 관찰과 확정은 분리돼 있어서(§3-1) 다시 읽는 것과 확정값이 바뀌는 것은 다른 일이다. `case` Owner 확인.

같은 것을 두 번 묻는 것은 사용자가 이 제품을 신뢰하지 않게 되는 가장 빠른 길이다.

사용자가 사건을 선택하면 새로운 메뉴를 직접 찾아다니지 않는다.

AI가 후속 작업을 이어서 수행한다.

```text
확인할 항목 2개

1. 차량번호
2. 신고 상황
```

# 12. 번호판

## 번호판을 판독한 경우

```text
차량번호

12가 3456

출처
영상에서 가장 선명한 번호판 장면과
주변 장면을 함께 확인

상태
AI 추정

[번호판 이미지 보기]
[맞아요]
[수정]
```

사용자가 `[맞아요]`를 누르거나 직접 수정한 이후에만:

```text
상태
사용자 확인됨
```

으로 바뀐다.

## 일부 문자가 불확실한 경우

```text
차량번호 확인이 필요해요.

[번호판 확대 이미지]

AI 추정
12가 34?6

5번째 문자를 확실하게 읽지 못했습니다.

상태
확인 필요

[다른 장면 보기]
[확대]
[직접 입력]
```

전혀 판독할 수 없는 경우 값을 만들지 않는다.

```text
차량번호
알 수 없음

상태
UNKNOWN
```

`UNKNOWN` 상태의 번호판을 그대로 신고자료에 포함할 수 있는지는 별도 Product Decision으로 관리한다. `[프로토타입]` 현재 가정은 **허용**이다 — `읽을 수 없음`으로 둬도 **경고 대화 없이 끝까지 진행된다.** 번호 없이 만든 자료도 자료다.

## `[프로토타입]` 「맞아요」 버튼을 만들지 않는다

`12가 34?6`처럼 **물음표가 든 값을 「맞다」고 확인할 방법이 사용자에게 없다.** 그래서 불확실한 번호판에 확인 버튼을 두지 않고, 선택지를 둘로만 준다.

```text
[번호 직접 입력]
[읽을 수 없음으로 두기]
```

선명하게 판독된 경우에도 같은 선택지를 유지했다. 「맞아요」 하나로 확정 상태를 만들면 사용자가 실제로 대조하지 않고 누르게 되고, 그 값은 `사용자 확인됨`이라는 이름만 얻는다. 1.2 §12의 판독한 경우에 있던 `[맞아요]`는 이 이유로 뺐다.

## `[프로토타입]` 번호판 장면 넘겨보기

한 장면만 보여주고 판단을 요구하지 않는다. 여러 장면을 넘겨보게 하고, **각 장면이 왜 잘 안 보이는지 함께 말한다.**

```text
선명 · 흔들림 · 반사 · 가림

2번은 흔들렸고, 3번은 빛이 반사됐고, 4번은 뒷차에 가렸습니다.
```

「안 보인다」와 「왜 안 보이는지」는 다르다. 뒤쪽만이 사용자가 다음에 무엇을 할지 정할 수 있게 한다.

## `[확정]` 차량번호 표기 규칙

| 층 | 규칙 |
| --- | --- |
| 입력 | `12가3456`과 `12가 3456`을 **모두 받는다** |
| 내부 처리 | 비교·검증할 때만 공백을 지운다 |
| 표시 | 확정된 값을 **그대로** 보여준다. 임의로 공백을 넣거나 빼지 않는다 |
| 안내 문구 | 「띄어쓰기 없이 입력」류 문구를 **넣지 않는다** |

형식이 어긋나도 **저장을 막지 않는다.** 지역·구형 번호판 등 예외가 있고, 최종 판단은 사용자와 접수기관의 몫이다. 형식이 이상하면 경고만 한다.

이 항목은 확정됐다. §26 미결에서 제외한다.

# 13. 발생시각

## 영상 화면에 시각이 있는 경우

```text
발생시각

2026-08-24 18:31:48

출처
영상 화면에 표시된 시각

상태
출처 확인됨
```

## 파일 기록을 이용해 계산한 경우

```text
발생시각 후보

2026-08-24 18:31:48

출처
원본 파일에 기록된 촬영 시각과
영상 내 사건 위치를 기준으로 계산

주의
영상 화면에 원래 표시된 시각은 아닙니다.

상태
확인 필요
```

## 파일 기록끼리 시각이 다른 경우

```text
발생시각 후보

2026-08-24 18:31:48

출처
원본 파일명에 기록된 시각 기준

주의
파일 메타데이터의 시각과 다릅니다.
영상 화면에 원래 표시된 시각은 아닙니다.

상태
확인 필요
```

값을 비우지 않는다. 파일명 시각을 기본값으로 쓰고 **충돌 사실을 함께 보여준다.** 어느 기록이 맞는지 사용자에게 고르게 하는 별도 단계를 두지 않으며, §20 최종 확인에서 수정할 수 있다. 어느 기록을 기본값으로 삼는지는 `architecture/module-architecture.md` §3-2가 정한다.

사용자가 실제로 검증할 방법이 없는 정보에 억지로 “확인” 버튼을 요구하지 않는다.

필요하면 안전신문고 제출 시 참고해야 할 정보로 고지한다.

```text
미금역 사거리

[검색어 복사]
[위치 단서 수정]
```

## GPS가 없는 경우

```text
위치 단서

미금역 근처

출처
사용자 기억

상태
확인 필요

안전신문고 검색어
미금역

[검색어 복사]
[위치 단서 수정]
```

정확한 위치를 임의로 확정하지 않는다.

최종 지도 핀은 안전신문고에서 사용자가 선택한다.

---

# 15. 신고 상황 확인

AI는 법률적 최종 판정을 요구하지 않는다.

대신 영상에서 관찰한 상황을 사용자에게 확인시킨다.

```text
이 사건을 이렇게 정리했습니다.

"흰색 SUV가 백색 실선을 넘어
인접 차로로 변경한 상황"

근거
• 백색 실선 확인
• 차량이 선을 넘어 이동
• 인접 차로 진입

상태
AI 추정

[맞아요]
[다른 상황]
[잘 모르겠어요]
```

사용자가 전문적인 법적 유형을 직접 판정하도록 요구하지 않는다.

구체적인 신고유형 매핑은 신고 규칙을 기반으로 별도로 처리한다.

`[프로토타입]` **`잘 모르겠어요`도 진행을 막지 않는다.** 값은 `AI 추정`으로 남고 §20 최종 확인에 그렇게 표시된다. 모르겠다는 대답에 벌을 주면 사용자는 다음부터 아무거나 누른다.

---

# 16. 파일 경계 사건

사건이 두 블랙박스 파일 사이에 걸쳐 있더라도 하나의 사건으로 처리한다.

```text
이 사건은 두 영상 파일에 걸쳐 있습니다.

원본
FILE_001.mp4
FILE_002.mp4

신고용 사건 구간
18:31:52 ~ 18:32:09

[이어진 사건 영상 보기]
[원본 파일 보기]
```

사용자에게는 하나의 연속된 사건 구간으로 보여주되, 어떤 원본 파일에서 만들어졌는지는 확인할 수 있게 한다.

구체적인 병합 방식(파일 경계 해석·이어진 사건 구간 생성)은 recording 모듈이 관리한다(`architecture/module-architecture.md` §3-3).

> `[프로토타입]` 이 절은 프로토타입에서 다루지 않았다. 흐름 검증용 mock 사건이 파일 하나 안에 들어 있었기 때문이며, **결정이 철회된 것이 아니다.** 실제 구현에서 처음 검증된다.

---

# 17. 원본과 신고용 파생영상 구분

대신고는 원본 블랙박스 파일을 수정하지 않는다.

```text
원본 영상
FILE_001.mp4
상태: 원본 유지

신고용 영상
daesingo_event_001.mp4
상태: 원본에서 생성된 파생영상
```

사용자가 다운로드하는 신고용 영상이 **원본이 아니라 파생영상**임을 명확히 표시한다.

원본과 파생영상의 실제 저장기간·삭제정책은 개인정보 및 운영 정책 문서에서 관리한다.

---

# 18. 신고요건 확인

AI는 신고자료 생성 전에 현재 신고 규칙을 기준으로 필요한 항목을 확인한다.

예:

```text
신고용 영상

20초
84MB / 허용 한도 130MB

상태
요건 충족
```

용량을 초과한 경우:

```text
신고용 영상의 용량이 허용 한도를 넘었습니다.

[영상 다시 압축]
[사건 구간 조정]
```

신고기한 역시 현재 신고 규칙을 기준으로 확인한다.

```text
신고기한
기한 내

또는

신고기한
확인 필요 / 기한 초과
```

규칙 값 자체는 Core User Flow가 아니라 신고 규칙 문서에서 관리한다.

---

# 19. 신고 준비 상태

같은 정보를 반복해서 전체 확인시키지 않는다.

이 화면은 **무엇이 남았는가**만 보여준다.

```text
대신고에서 준비할 항목

✓ 사건 영상
✓ 차량번호
✓ 발생시각
✓ 신고 상황
✓ 파일규격
```

### 안전신문고에서 직접 확인할 항목

```text
• 최종 위치 핀 선택
```

GPS가 없어 제품 안에서 완료할 수 없는 정보를 `4/5` 같은 실패 상태로 표시하지 않는다.

## `[프로토타입]` 다음으로 넘어가는 조건

**사용자에게 확인을 요구하는 항목은 두 개뿐이다.**

| 항목 | 확인 요구 | 이유 |
| --- | --- | --- |
| 차량번호 | **요구함** | 사용자가 영상을 보고 실제로 판별할 수 있다 |
| 신고 상황 | **요구함** | 사용자가 그 자리에 있었으므로 판별할 수 있다 |
| 발생시각 · 위치 · 신고유형 | 요구하지 않음 | §13의 원칙 — **사용자가 실제로 검증할 방법이 없는 정보에 억지로 「확인」 버튼을 요구하지 않는다** |

차량번호는 `확인 필요`가 아니기만 하면 된다. `읽을 수 없음`도 통과한다(§12).

**넘어갈 수 없을 때는 버튼을 비활성만 시키지 말고 무엇이 남았는지 문장으로 말한다** — 「차량번호를 확인해주세요」. 눌리지 않는 버튼은 이유를 설명하지 않는다.

# 20. 신고자료 최종 확인

전체 정보를 다시 읽는 화면은 **여기 한 번만 제공한다.**

```text
신고자료를 최종 확인해주세요.

사건
18:31:42 ~ 18:31:57

차량번호
12가 3456
상태: 사용자 확인됨

발생시각
2026-08-24 18:31:48
출처: 영상 화면에 표시된 시각

위치
미금역 사거리 인근
안전신문고에서 최종 위치 선택 필요

사건 설명
흰색 SUV가 백색 실선을 넘어
인접 차로로 이동한 상황

신고용 영상
20초 · 84MB
원본에서 생성된 파생영상
```

### 신고문

```text
[자동 작성된 신고문 전체 내용]

[신고문 수정]
```

사용자는 실제로 자신이 제출하게 될 신고문을 읽고 수정할 수 있어야 한다.

```text
[원본 영상과 비교]
[정보 수정]
[신고자료 만들기]
```

# 21. 안전신문고 제출 단계로 연결

최종 확인이 끝난 뒤 같은 정보를 다시 나열하지 않는다.

```text
신고자료가 준비되었습니다.

최종 위치는 안전신문고 지도에서 확인해주세요.

[신고용 영상 다운로드]
[신고내용 복사]
[안전신문고로 이동]
```

## `[프로토타입]` 붙여넣을 것과 직접 고를 것을 나눈다

**이 단계의 정확성이 제품 신뢰를 좌우한다.** 사용자가 실제 안전신문고 화면에서 헤매면 여기까지 아낀 시간이 전부 사라진다.

안전신문고의 입력칸은 성격이 두 가지인데, 그것을 화면이 먼저 갈라서 보여준다.

| 묶음 | 항목 | 표기 |
| --- | --- | --- |
| **붙여넣을 것** | 제목 · 차량번호 · 신고 내용 | 각각 복사 버튼. 전체 복사는 **칸 이름을 붙여** 복사한다 |
| **직접 고를 것** | 신고유형 · 발생일자 · 발생시각 · 발생장소 | **복사 버튼을 두지 않는다.** 각 항목에 어디를 눌러야 하는지 한 줄로 안내한다 |

**직접 고를 것에 복사 버튼을 두지 않는 이유:** 있으면 누르고, 왜 안 붙는지 헤맨다. 붙여넣을 수 없는 칸에 복사 버튼을 주는 것은 없는 기능을 약속하는 것이다.

**발생장소만 예외다** — 검색어를 복사해 지도 검색창에 붙여넣되, **핀은 안전신문고 지도에서 사용자가 놓는다**(§14). 자체 지도 UI는 MVP 범위가 아니다.

신고용 영상은 **파생영상**임을 표시해 내려받게 하고(§17), 안전신문고는 새 창으로 연다. 이 화면은 그대로 두고 옆에 놓고 볼 수 있어야 한다.

실제 신고 제출은 사용자가 직접 수행한다.

AI는 사용자 승인 없이 신고를 제출하지 않는다. **「접수」 버튼은 제품 어디에도 존재하지 않는다.**

# 22. AI 불확실성 대응

AI가 정상적으로 동작했지만 결과가 불확실한 상황과 시스템 자체가 실패한 상황을 구분한다.

| 상황             | 대응                      |
| -------------- | ----------------------- |
| 확실한 사건 후보 없음   | 유사 후보 제공 + 탐색 범위 조정     |
| 후보 여러 개        | Top-3 비교                |
| 사건은 맞지만 조금 앞/뒤 | 주변 시간만 재탐색              |
| 차량 특징이 틀림      | 차량 조건 수정 후 재탐색          |
| 번호판 일부 불확실     | 확대 이미지 + 다른 장면 + 직접 입력  |
| 번호판 판독 불가      | UNKNOWN                 |
| 발생시각 출처가 약함    | 출처와 주의사항 표시             |
| 위치 근거 없음       | 사용자 기억 유지 또는 UNKNOWN    |
| 신고 상황이 애매함     | 관찰 내용 제시 + `잘 모르겠어요`    |
| 시간 제한 도달       | 현재까지 확보한 후보 유지 + 이어서 탐색 |

### 유사 후보만 있는 경우

```text
확실한 사건은 찾지 못했습니다.

다만 기억하신 상황과 비슷한 장면을 찾았습니다.

[유사 후보 보기]
[시간 범위 조정]
[차량 특징 수정]
[상황 다시 설명]
```

### 실제 후보가 하나도 없는 경우

```text
현재 탐색 범위에서는
사건 후보를 찾지 못했습니다.

[탐색 범위 넓히기]
[기억 단서 수정]
```

## `[프로토타입]` 결과 없음 화면에서 지킬 것

**출구를 넷으로 준다.** 「범위 넓히기」 하나만 주면 사용자는 같은 실패를 반복한다.

```text
[앞뒤 30분 더 찾아보기]   ← 기본
[시간을 다시 말할게요]
[차량 특징 고치기]
[비슷하지만 다른 장면 보기]
```

**범위를 넓히기 전에 비용을 미리 말한다.**

```text
영상 9개 → 21개 · 약 4분 더 걸립니다
```

이미 확인한 구간과 새로 확인할 구간을 시간축에 **겹쳐서** 보여준다. 얼마나 더 기다려야 하는지 모른 채 누르게 하지 않는다.

**유사 후보를 진짜 후보와 같은 위계로 두지 않는다.** 「말씀하신 조건과 일부만 맞습니다」를 명시하고, 카드도 후보와 구분되게 표시한다. 섞어두면 사용자는 그중 하나를 정답으로 고른다.

## `[프로토타입]` 「직접 타임라인」 화면은 두지 않는다

1.2 이전 판본(서비스 기획안 1.3 계열)은 결과 0개와 timeout의 출구로 `[직접 타임라인]`을 제시했다. **1.2에서 이미 빠졌고, 프로토타입도 만들지 않았다.** 대신 §6의 「탐색 범위 직접 조정」과 「조건 수정」이 그 자리를 맡는다.

다른 문서에 아직 `[직접 타임라인]`을 전제한 서술이 남아 있다면 그것은 8/27 판본의 잔재다(2026-09-04 확인: `management/cross-cutting-decisions.md` A-1이 이 절을 따른다). 사용자가 영상 타임라인을 직접 훑는 화면이 따로 필요한지는 §26의 미결 항목으로 둔다.

# 23. 시스템 실패 및 복구

AI의 낮은 확신과 시스템 오류를 같은 것으로 취급하지 않는다.

## 분석 실패

```text
영상 분석 중 문제가 발생했습니다.

지금까지 완료된 작업은 저장되어 있습니다.

[다시 시도]
[현재까지의 후보 보기]
```

## 연결 끊김

```text
연결이 끊겼습니다.

작업 상태를 확인하고 있습니다.

[다시 연결]
```

## 지원하지 않는 파일 또는 손상 파일

```text
일부 영상을 처리할 수 없습니다.

FILE_017.mp4
지원하지 않는 형식 또는 손상된 파일입니다.

[다른 영상은 계속 분석]
[파일 확인]
```

## 신고용 영상 생성 실패

```text
사건은 찾았지만
신고용 영상 생성에 실패했습니다.

[다시 만들기]
[구간 조정]
```

가능한 경우 이미 완료된 분석 결과를 보존한다.

`[프로토타입]` **`다시 시도`는 처음부터 다시 돌리지 않고 이어서 진행한다.** 0%부터 다시 돈다면 「지금까지 완료된 작업은 저장되어 있습니다」라는 문장이 거짓이 되고, 이 화면이 존재할 이유도 없어진다.

이 화면은 **제품에서 유일하게 실패색(빨강)을 쓰는 곳**이다. AI의 낮은 확신(§22)은 실패가 아니므로 같은 색을 쓰지 않는다.

# 24. 사용자 행동 기록

Core Flow에서는 어떤 행동을 기록할지만 정의한다.

예:

```text
첫 후보 선택
다른 후보 선택
Top-3 전체 거절
시간 전/후 보정
차량 특징 수정
번호판 수정
위치 수정
신고 상황 수정
```

이 데이터를 어떤 평가 지표로 계산할지는 Evaluation 문서에서 관리한다.

사용자 영상을 모델 개선이나 학습에 활용하는 경우 별도의 개인정보 처리 및 동의 정책을 따른다. 정책은 `modules/case/decisions/correction-log-reuse.md`가 소유한다(평가 재사용 / 학습 재사용 2단계).

# 25. 완료 조건

하나의 사건에 대해 다음 상태에 도달하면 대신고 내부의 신고 준비가 완료된 것으로 본다.

```text
사건 선택
+
사건 근거 확인
+
필요한 신고정보 준비
+
불확실한 값의 상태·출처 표시
+
필요한 사용자 수정
+
신고 규칙 검사
+
신고용 파생영상 생성
+
신고문 포함 최종 자료 확인
+
사용자 최종 승인
```

이후 안전신문고 제출 단계로 연결한다.

실제 신고 제출은 사용자가 직접 수행한다.

## `[프로토타입]` 흐름의 합격 기준

위 상태에 도달하는 경로가 **네 가지 모두 처음부터 끝까지 끊기지 않아야** 한다. 정상 경로 하나만 되는 것은 완료가 아니다.

1. **정상** — 올리기 → 설명 → 범위 확인 → 찾기 → 선택 → 정보 확인 → 최종 확인 → handoff
2. **보정** — §9의 시간 보정 후 새 후보를 골라 끝까지
3. **불확실** — 번호판을 장면을 넘겨보며 입력하거나, `읽을 수 없음`으로 둔 채 끝까지
4. **복구** — 분석 실패에서 이어서 재시도 / 결과 0개에서 범위를 넓혀 끝까지

# 26. 아직 결정되지 않은 UX 정책

다음 값과 정책은 지금 임의로 고정하지 않는다.

| 항목 | 현재 상태 | 무엇으로 정하는가 |
| --- | --- | --- |
| 단일 유력 후보 / 후보 비교 분기와 그 임계값 | `[프로토타입]` **항상 비교**(§8-1 단독 화면 없음) | 사용자 평가 결과 |
| 분석 제한시간(timeout)의 실제 값 | 미정 | baseline 실측 후. 담당은 `case`(`modules/case/decisions/timeout-fallback.md`) |
| 사용자 보정·재탐색 횟수와 비용 정책 | 상한 없음 | 비용·지연 실측 후 |
| 남은 시간(ETA) 제공 여부 | `[프로토타입]` **제공하지 않음**(퍼센트도 표시하지 않음, §7) | 실측이 쌓인 뒤 재검토 |
| 장시간 분석 완료 알림 방식 | 미정 | — |
| `AI 추정` 상태로 신고 준비 완료를 통과할 수 있는 정보 | `[프로토타입]` **차량번호·신고 상황만 확인 요구**(§19) | 미정 |
| 번호판 `UNKNOWN` 상태에서 신고자료 생성 허용 | `[프로토타입]` **허용** | 별도 Product Decision이 뒤집기 전까지 유지 |
| **안전신문고 입력 규칙**(붙여넣기 3 / 직접 고르기 4, §21) | `[프로토타입]` 가정 | **실제 안전신문고 화면 확인 필요** |
| 「직접 타임라인」 화면 필요 여부 | 만들지 않음(§22) | 사용자 평가에서 필요가 드러나면 |

> **가장 위험한 항목은 안전신문고 입력 규칙이다.** 신고유형 분류 이름과 시·분 선택 단위는 실물 화면을 보고 맞춰야 하며, 다르면 §21의 두 묶음 구성과 안내 문구가 함께 바뀐다.

**차량번호 표기 규칙은 확정됐다**(§12). 미결에서 제외한다.

`[프로토타입]`에 등장하는 구체적 수치(대기 시간, 보정 폭, 넓히는 범위, 추가 소요 시간)는 **연출값이지 제품 결정이 아니다.** 실제 구현에서 실측으로 대체한다.

이러한 미결 항목의 실제 값과 담당은 각 모듈의 baseline·평가 결과를 근거로 결정하며, 여러 모듈이 관련된 항목은 주간 회의 안건으로 올리고, 결정은 `management/cross-cutting-decisions.md`에 기록한다.

## 핵심 정의

대신고는 AI가 법적 판단과 신고를 대신하는 서비스가 아니다.

> **사용자가 기억하는 사건을 설명하면 AI가 장시간 영상 탐색과 신고자료 준비를 대신 수행하고, 불확실하거나 중요한 판단이 필요한 순간에만 사용자에게 확인을 요청하는 인간-AI 협업형 신고 준비 도구다.**

따라서 핵심 사용자 경험은 다음과 같다.

```text
설명
→ 위임
→ AI 작업
→ 필요한 순간만 개입
→ 수정·확인
→ 신고자료 완성
→ 사용자 최종 승인
```

AI가 얼마나 많은 기능을 사용하는지가 아니라, **사용자가 얼마나 적은 노력으로 사건을 찾고 신뢰할 수 있는 신고자료까지 도달할 수 있는가**를 중심으로 설계한다.
