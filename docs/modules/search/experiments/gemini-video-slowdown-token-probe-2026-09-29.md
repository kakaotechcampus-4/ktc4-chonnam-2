# Gemini 프록시 경유 느린 영상: 배속을 늦추면 모델이 보는 프레임이 늘어나는가

실행일: 2026-09-29. 호출별 조건·길이·프레임 수·파일 크기·입력 토큰은 [구조화 결과](./gemini-video-slowdown-token-probe-2026-09-29-results.json)에 기록했다. 영상 파일과 API 키는 저장하지 않았다. 실행 스크립트: `scripts/gemini_video_slowdown_token_probe.py`.

## 질문

[영상 샘플링 실험](./gemini-proxy-video-sampling-2026-09-28.md)에서 프록시는 영상을 **재생 시간 1초당 1프레임·low(66토큰)**로 재샘플링했고 fps 파라미터는 전달되지 않았다. 그렇다면 영상을 느리게 늘려 재생 시간을 키우면 원본 1초에서 더 많은 프레임이 모델에 들어가는가. 들어간다면 [이미지 전송](./gemini-image-frame-probe-2026-09-28.md)(프레임당 1,100토큰)보다 싸게 시간 밀도를 올릴 수 있다.

## 방법

- 앞선 두 probe와 같은 설정(`GeminiSearchConfig.from_dotenv`)·프록시 `base_url`·`gemini-3.8-flash`·`reasoning_effort=low`로 호출했다. 요청 형식은 `provider.py`와 같은 `type: file` base64 인라인이다.
- 원본은 앞선 probe와 같은 `20260620_141628_EVT_1.avi`의 0–7초다. ffmpeg `setpts=PTS/speed`로 늘린 뒤 `fps`·downscale-only 필터를 적용하고 오디오를 제거했다. 길이·프레임 수는 ffprobe로 셌다.
- 프롬프트는 `Reply with the single word OK.`로 고정했다. 영상 없이 보낸 입력 토큰(8)을 빼서 영상 토큰으로 본다.
- 첫 실행은 `-t`를 출력 옵션으로 둬서 늘어난 영상이 7초로 잘렸다(모든 조건 462토큰). `-t`를 입력 옵션으로 옮겨 다시 실행했고, 아래는 그 결과다.

## 해석과 한계

- 0.5x는 원본 1초당 2프레임, 0.25x는 4프레임을 모델에 넣는다. 원본 7초 기준 2 fps는 영상 924토큰으로, 이미지 2 fps(15,400토큰)의 약 1/17이다.
- 프레임당 66토큰(low)은 그대로다. 공간 해상도는 오르지 않는다. [Fine 이미지 정확도 실험](./gemini-fine-image-accuracy-2026-09-28.md)에서 fps를 올려도 실선 판별이 나아지지 않았으므로, 배속만으로 먼 거리 선 종류 판별이 개선될 근거는 없다.
- 늘어난 영상에서는 인코딩 fps를 재생 1초당 1장 넘게 넣어도 토큰이 같다. 준비 fps는 `1/speed`면 충분하고 그 이상은 전송 크기만 키운다.
- 모델은 늘어난 영상 기준 시각으로 답한다. 파이프라인에 쓰려면 응답 시각에 speed를 곱해 원본 시각으로 되돌려야 한다.
- 서버가 재생 1초 중 어느 프레임을 고르는지는 토큰으로 알 수 없다. 원본 1개·구간 1개·조건당 1회다.
