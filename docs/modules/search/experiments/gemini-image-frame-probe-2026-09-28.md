# Gemini 프록시 경유 이미지 프레임 전송: 해상도·프레임 밀도가 모델에 전달되는가

실행일: 2026-09-28. 호출별 조건·요청 바이트·입력 토큰은 [구조화 결과](./gemini-image-frame-probe-2026-09-28-results.json)에 기록했다. 영상 파일과 API 키는 저장하지 않았다. 실행 스크립트: `scripts/gemini_image_frame_probe.py`.

## 질문

[영상 샘플링 실험](./gemini-proxy-video-sampling-2026-09-28.md)에서 프록시는 인라인 영상을 1 fps·low(프레임당 66토큰)로 강제하고 `media_resolution`·`fps`를 받지 않았다. 그렇다면 남은 경로 — 로컬에서 프레임을 뽑아 **이미지 여러 장(`image_url`)으로 전송** — 은 (a) 프록시가 수용하는가, (b) `detail`·해상도가 실제로 전달되는가, (c) 이미지 장당 토큰은 얼마인가, (d) 18 MiB 요청 상한 내 몇 장까지 되는가.

계기: fine-coarse 판별에는 1 fps·low가 불충분하다고 판단됨(실선/점선·신호색). 이미지가 프레임 밀도·화질을 모델에 실제로 전달할 수 있으면 Fine 전송 방식 후보가 된다.

## 방법

- 영상 실험과 같은 설정(`GeminiSearchConfig.from_dotenv`)·프록시 `base_url`·`gemini-3.8-flash`·`reasoning_effort=low`로 호출했다. content 파트를 `type:"image_url"`(base64 data URL, jpeg)로 보냈다.
- 프롬프트는 모든 호출에서 `Reply with the single word OK.` 하나로 고정했다. 같은 프롬프트를 이미지 없이 보낸 입력 토큰(8)을 빼서 이미지 토큰으로 본다.
- 원본은 영상 실험과 같은 `20260620_141628_EVT_1.avi`의 0–7초다. `media.py`와 같은 downscale-only 필터(`fps=N,scale=-2:'min(H,ih)'`)로 프레임을 추출했다.
- 실험 1은 1장 고정으로 `detail`(low/high/생략)과 프레임 해상도(360p/720p/native 1080p)를 바꾼다. 실험 2는 장수를 늘린다(7·14·28 = 7초 × 1·2·4 fps).

## 결과 1: 1장 — detail·해상도

| 조건 | 요청 바이트 | 이미지 토큰 |
| --- | --- | --- |
| 720p / detail=low | 110,380 | 1,100 |
| 720p / detail=high | 110,381 | 1,100 |
| 720p / detail=생략 | 110,365 | 1,100 |
| 360p / detail=high | 37,877 | 1,100 |
| native 1080p / detail=high | 191,789 | 1,100 |

`detail`(low/high/생략)에도, 해상도(360p→1080p)에도 이미지 토큰은 **1,100으로 고정**이다. 서버가 이미지를 고정 작업 해상도로 리사이즈해 타일링한다는 해석과 일치한다(1,100 ≈ default 타일 258 × 약 4).

## 결과 2: 장수 (프레임 밀도·요청 상한)

| 조건 | 장수 | 요청 바이트 | 이미지 토큰 |
| --- | --- | --- | --- |
| 7초 @ 1 fps / 720p | 7 | 787,647 | 7,700 |
| 7초 @ 2 fps / 720p | 14 | 1,578,432 | 15,400 |
| 7초 @ 4 fps / 720p | 28 | 3,171,250 | 30,800 |

장당 정확히 1,100토큰으로 **선형**이다. 28장(720p)에서도 요청은 3.2 MB로 18 MiB 상한에 멀다 — **바이트가 아니라 토큰·비용이 먼저 막는다.**

## 해석과 한계

- **프록시는 이미지를 수용한다**(모든 호출 200). 영상과 달리 **프레임 밀도(fps)를 실제로 제어**할 수 있다 — 28장 = 4 fps가 그대로 모델에 도달한다.
- **프레임당 토큰은 66(영상 1fps·low) → 1,100(이미지)으로 약 16.7배.** 멀티타일로 들어가므로 프레임당 공간 정보가 영상보다 많다 = Fine 판별에 유리할 개연성이 있다.
- **대가:** 영상 Fine(7초 462토큰) 대비 이미지 1 fps(7장 7,700)는 약 16.7배, 2 fps(14장 15,400)는 약 33배 비싸다.
- **해상도 노브는 없다.** `detail`·source 해상도가 토큰을 바꾸지 않으므로 세밀 조절이 불가능하고, 720p·1080p 전송은 360p와 토큰이 같아 payload만 낭비다. 이미지로 간다면 **360p로 보내는 것이 바이트상 유리**하다.
- **토큰이 못 답하는 것:** 1,100토큰/프레임이 *실제로* Fine 정확도(실선/점선·신호색)를 올리는지, 어느 source 해상도에서 고정 그리드가 포화되어 360p 전송이 화질 손실을 내는지는 이 실험(토큰 차감)으로 알 수 없다. `video/정답지.md` 대조 정확도 실험이 필요하다.
- 원본 1개·구간 1개·조건당 1회다. 토큰 수는 결정적으로 보이나 다른 영상·모델 버전에서 재확인하지 않았다.
