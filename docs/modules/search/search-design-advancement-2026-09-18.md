# Search 설계 고도화 문서

> 작성일: 2026-09-18  
> 대상: 장시간 블랙박스 영상의 교통위반 사건 탐색  
> 상태: W7 Quality / Risk Burn-down 실행 기준 초안  
> 범위: 기능 흐름, 사용자 경험, 품질·운영 개선 방향  
> 제외: API 명세, 데이터 구조, DB 설계, 세부 구현 코드

## 1. 문서 목적

이 문서는 현재 Search 기능이 어떤 방식으로 사건 후보를 찾고 사용자에게 전달하는지 정리하고,
현재 확인된 한계와 향후 고도화 방향을 제시한다.

이 문서는 W7에서 실제 고도화 항목을 선택하고 완료 여부를 판단하는 기준선으로 사용한다.
다만 아래 단계별 순서는 고정 일정이 아니다. **이번 Real E2E에서 실제로 드러난 병목과 실패 유형을
먼저 반영한 뒤 W7 착수 시점에 우선순위를 다시 정한다.**

Search의 목표는 AI가 교통법규 위반을 최종 판정하는 것이 아니다. 사용자가 기억하는 단서를
바탕으로 장시간 블랙박스 영상에서 **신고 대상일 가능성이 있는 장면을 놓치지 않고 찾은 뒤,
검토할 후보를 줄여 주는 것**이 목표다.

### W7 사용 원칙

1. 이 문서의 As-Is, To-Be, 성과지표는 W7 변경의 비교 기준으로 유지한다.
2. 기존 실험에서 예상한 위험과 Real E2E에서 실제로 관찰한 실패를 구분한다.
3. Real E2E를 막거나 결과 신뢰성을 훼손한 항목을 문서상의 원래 순서보다 먼저 처리한다.
4. 각 고도화 항목은 동일한 E2E 시나리오의 변경 전·후 결과로 효과를 확인한다.
5. 새로운 모델이나 기술 도입은 실제 실패 유형이 필요성을 증명한 경우에만 검토한다.

## 2. 설계 범위

### 포함 범위

- 사용자의 기억 단서를 이용한 우선 탐색 범위 구성
- 장시간 영상에서 사건 후보 구간 탐색
- 후보 구간의 시각적 근거 재검증
- 초기 지원 4종 사건에 대한 탐색
- 후보 정렬과 Top-3 제공
- 결과 없음, 불확실, 분석 실패 시 복구 흐름
- 사용자 보정에 따른 재탐색
- 정확도, 시간, 비용 관점의 평가 및 개선 방향

### 제외 범위

- API 요청·응답 명세
- 클래스, 필드, DB 등 데이터 구조
- 번호판 OCR 및 발생시각 최종 확정
- 신고유형과 법적 위반 여부의 최종 판단
- 신고용 영상 파일 생성
- 안전신문고 자동 제출

## 3. 현재 설계(As-Is)

### 3.1 Search의 역할

현재 Search는 긴 영상에서 사건이 있을 가능성이 높은 시간 구간을 찾고, 해당 구간에서
관찰 가능한 시각적 근거를 구조화한다.

초기 지원 사건은 다음 4종이다.

1. 신호위반 의심 장면
2. 중앙선 침범 의심 장면
3. 백색 실선 진로변경 의심 장면
4. 이륜차 안전모 미착용 의심 장면

Search는 사건 후보와 관찰 결과까지만 제공한다. 신고 규정 적용, 신고유형 확정, 법적 판단은
후속 단계와 사용자의 확인을 통해 이루어진다.

### 3.2 현재 처리 흐름

```text
사용자가 기억 단서 입력
  ↓
시간·차량·상황·위치 단서 구조화
  ↓
사용자가 우선 탐색 범위 확인·조정
  ↓
Coarse Search
- 긴 영상을 낮은 해상도로 넓게 탐색
- 정확한 판정보다 후보 누락 방지 우선
- 사건 후보 시간 구간 생성
  ↓
Fine Verification
- 각 후보의 짧은 구간을 높은 해상도로 재검토
- 사건 유형별 필수 시각 정보와 시간 순서 확인
- OBSERVED / NOT_OBSERVED / UNCERTAIN으로 구분
  ↓
후보 비교 및 Top-3 제공
  ↓
사용자 선택 또는 보정
- 맞는 사건 선택
- 조금 전·조금 후 재탐색
- 조건 수정 또는 탐색 범위 확대
```

### 3.3 단계별 역할

| 구분 | Coarse Search | Fine Verification |
| --- | --- | --- |
| 핵심 질문 | 어느 구간을 다시 봐야 하는가? | 해당 구간에서 필요한 시각적 사건이 관찰되는가? |
| 목적 | 후보 누락 최소화 | 오탐 제거 및 근거 확인 |
| 처리 범위 | 긴 영상 전체 또는 우선 탐색 범위 | Coarse가 찾은 짧은 후보 구간 |
| 현재 기준 | 낮은 해상도, 1fps | 높은 해상도, 2fps |
| 결과 | 후보 시간 구간과 대표 시점 | 관찰 여부, 시각 근거, 불확실성 |

Fine 결과의 의미는 다음과 같다.

- `OBSERVED`: 사건에 필요한 시각적 요건이 관찰됨
- `NOT_OBSERVED`: 필요한 장면을 확인했으나 해당 요건이 성립하지 않음
- `UNCERTAIN`: 가림, 흐림, 화면 밖 등의 이유로 판단에 필요한 장면을 확인할 수 없음

`OBSERVED`는 법적 위반 확정을 의미하지 않는다. 영상에서 요구한 장면과 시간 관계가
관찰됐다는 뜻이다.

### 3.4 현재 사용자 경험

- 분석 중에는 현재 탐색 범위와 진행 상태를 보여 준다.
- 후보는 분석이 모두 끝난 뒤 한 번에 보여 주는 것이 아니라 도착하는 대로 목록에 추가한다.
- 단일 후보를 자동 확정하지 않고 현재는 항상 후보 비교 화면으로 이동한다.
- 가장 유력한 후보를 우선 표시하더라도 Top-3는 항상 확인할 수 있다.
- 사용자는 `맞아요`, `조금 전이에요`, `조금 후예요`, `전부 아니에요`와 같은 명시적 동작으로
  결과를 보정한다.
- 결과가 없으면 범위 확대, 조건 수정, 유사 후보 확인, 종료 중 하나를 선택할 수 있다.
- 분석을 중단하거나 일부 단계가 실패해도 이미 찾은 후보는 유지한다.

### 3.5 현재 설계·실험 기준

- `develop`에는 Search 제품 runtime 구현이 아직 병합되지 않았으며, 현재 기준선은 Architecture와
  Search 실험·결정 문서다.
- 마지막으로 실행 근거가 남은 baseline 모델은 `gemini-3.7-flash`다.
- 처리 방식은 Gemini 기반 Coarse/Fine 2단계 구조다.
- Coarse는 low resolution, 1fps를 기준으로 넓게 탐색한다.
- Fine은 high resolution, 2fps를 기준으로 후보 구간을 정밀 검증한다.
- 영상 업로드 결과를 Coarse와 Fine에서 재사용하는 방식이 단독 탐침에서 확인됐다.
- 모델 변경과 프록시 적용 등 feature 브랜치의 변경은 `develop` 병합 및 Real E2E 확인 후 현재
  기준선에 반영한다.

## 4. 현재까지 확인된 결과

2026-09-12 영상 탐침 실험에서는 약 39분 8초의 주행 영상을 대상으로 다음 결과를 확인했다.

| 항목 | 결과 | 해석 |
| --- | --- | --- |
| Coarse 실행 | 8개 영상 구간, 실패 0건 | 2단계 흐름이 기술적으로 실행됨 |
| Coarse 후보 | 45개 | 후보를 넓게 수집함 |
| Fine 검증 | 유효 후보 41개, 실패 0건 | 짧은 구간 재검증이 동작함 |
| Fine 결과 | NOT_OBSERVED 40개, OBSERVED 1개 | 일반 차로 변경 등 다수 후보를 제거함 |
| 잘못된 후보 시간 | 4개 | 영상 길이를 벗어난 시간 구간 생성 문제 확인 |
| Fine 처리량 | 원본 길이의 약 17.3% | 전체가 아닌 후보 구간만 정밀 분석함 |
| 비용 비중 | Fine 약 69% | Fine이 전체 비용의 중심임 |
| 전체 추정 비용 | 약 $0.906/source-hour | 실측 영상 길이와 토큰 기준 추정치 |

이 실험은 파이프라인의 실행 가능성과 비용 구조를 확인한 실험이다. 정답지가 없었기 때문에
Recall, 전체 Precision, 사건 유형별 정확도는 아직 측정되지 않았다. 따라서 현재 결과만으로
“Search 정확도가 충분하다”고 판단할 수 없다.

> **증거 구분:** 위 수치는 2026-09-12 Search 단독 탐침 결과이며 이번 Real E2E 결과가 아니다.
> 현재 저장소에는 이번 Real E2E의 Search 병목·실패 결과가 아직 기록되어 있지 않다. W7 착수
> 전 실제 실행 결과가 전달되면 §9의 기록표에 추가하고 §10의 순서를 갱신한다.

## 5. 현재 설계의 문제점

아래 항목은 기존 설계와 단독 탐침에서 확인한 **초기 위험 목록**이다. W7의 최종 우선순위는
Real E2E에서 재현된 빈도, 전체 흐름에 미친 영향, 사용자 결과의 신뢰성에 따라 다시 정한다.

### 5.1 품질을 판단할 기준이 부족하다

현재는 충분한 사람 정답지가 없어 실제 사건을 얼마나 놓쳤는지, 잘못된 후보를 얼마나
제시했는지 알 수 없다. 실행 성공률이나 후보 수만으로는 Search 품질을 설명할 수 없다.

### 5.2 후보 시간의 신뢰성이 부족하다

Coarse가 실제 영상 길이 밖의 시간을 후보로 반환한 사례가 확인됐다. 후보가 존재하더라도
사용자가 해당 장면으로 이동할 수 없으면 검색 결과로서 가치가 없다. 사건 유무뿐 아니라
대표 시점의 오차를 별도의 핵심 품질 지표로 관리해야 한다.

### 5.3 후보가 특정 유형에 편중되어 있다

기존 실험의 후보 45개 중 44개가 일반 차로 변경이었고, 중앙선 침범과 안전모 미착용 후보는
없었다. 데이터 특성의 영향이 있으므로 이를 모델 성능으로 단정할 수는 없지만, 4종 전체의
동작을 검증하지 못한 상태다.

### 5.4 Fine 비용이 후보 수에 따라 크게 증가한다

Fine은 짧은 구간만 처리했음에도 전체 비용의 약 69%를 차지했다. Coarse가 불필요한 후보를
많이 만들면 후보마다 고해상도 검증 비용이 추가된다. 단순히 Fine의 화질을 낮추기보다
Coarse의 후보 품질과 중복 후보 정리가 먼저 개선되어야 한다.

### 5.5 불확실성과 실패의 사용자 설명이 더 필요하다

결과 없음, 유사 후보만 있음, 분석 실패, 비용·시간 제한 도달은 원인이 서로 다르다. 이를 모두
“검색 실패”로 보여 주면 사용자는 같은 조건으로 재시도하거나 결과를 오해할 수 있다.

### 5.6 사용자 보정의 개선 효과가 측정되지 않았다

`조금 전·후`, 시간 범위 변경, 차량 조건 수정과 같은 보정 흐름은 정의되어 있지만, 실제로
재탐색 성공률과 사용자 작업시간을 얼마나 개선하는지는 아직 검증되지 않았다.

## 6. 고도화 목표(To-Be)

고도화된 Search는 다음 상태를 목표로 한다.

1. **놓치지 않는 검색**: 실제 사건이 Final Top-3 안에 포함되는지를 정답지로 측정한다.
2. **정확한 위치 안내**: 후보 대표 시점이 실제 사건 시점과 얼마나 차이 나는지 관리한다.
3. **설명 가능한 결과**: 후보마다 선택 이유, 관찰 근거, 불확실성을 사용자가 확인할 수 있다.
4. **예측 가능한 비용과 시간**: 영상 길이와 후보 수에 따른 처리 시간·비용을 측정하고 안내한다.
5. **복구 가능한 흐름**: 일부 실패나 사용자 보정이 발생해도 기존 결과를 보존하고 필요한
   범위만 다시 탐색한다.
6. **실패 근거 기반 확장**: 새로운 모델이나 CV 기술은 현재 방식의 구체적 실패가 반복되고,
   동일한 정답지에서 개선이 확인될 때만 도입한다.

## 7. 고도화 설계

### 7.1 목표 처리 흐름

```text
기억 단서 입력 및 탐색 범위 확인
  ↓
Coarse 후보 탐색
  ↓
후보 유효성 검사
- 영상 범위 밖 시간 제거
- 겹치거나 같은 사건인 후보 묶기
- 대표 시점과 원본 시간축 연결 확인
  ↓
후보 우선순위화
- 기억 단서 일치도
- 사건 유형별 관찰 가능성
- 중복 여부와 불확실성
  ↓
Fine 정밀 검증
- 사건 유형별 필수 시각 근거 확인
- 관찰되지 않음과 관찰 불가를 구분
- 필수 근거가 부족하면 UNCERTAIN 유지
  ↓
결과 구성
- Top-3 후보
- 선택 이유와 시각 근거
- 불확실성 및 확인이 필요한 항목
  ↓
사용자 확인·보정
  ├─ 사건 선택 → 후속 신고 준비
  ├─ 조금 전·후 → 주변 범위만 재탐색
  ├─ 조건 수정 → 영향받는 범위만 재탐색
  └─ 후보 없음·실패 → 원인별 복구 동작 제공
```

### 7.2 후보 품질 고도화

- 실제 영상 범위를 벗어난 후보는 Fine 실행 전에 차단한다.
- 동일 사건으로 보이는 겹친 후보는 묶어 불필요한 Fine 호출을 줄인다.
- 넓은 후보 구간 자체보다 대표 시점의 정확도를 우선 평가한다.
- Coarse는 후보 누락 방지를 유지하되, 사건 유형별 편중과 반복 오탐을 별도로 분석한다.
- 특정 사건 유형의 실패가 반복되면 해당 유형의 프롬프트와 검증 기준을 분리해 개선한다.

### 7.3 Fine 검증 고도화

- 신호, 정지선, 차선, 대상 차량처럼 사건별 필수 시각 요소를 명시적으로 확인한다.
- 한 장면의 외형만 보지 않고 사건 전·중·후의 시간 관계를 검증한다.
- 화면에 보이지 않는 정보를 추정하지 않고 `UNCERTAIN`으로 유지한다.
- 일반 차로 변경과 실선 침범처럼 혼동하기 쉬운 정상 사례를 검증용 사례에 포함한다.
- 화질, FPS, 후보 구간 길이 조정은 비용만 보고 적용하지 않고 동일한 정답지로 품질을 비교한다.

### 7.4 결과 설명 고도화

각 후보에는 최소한 다음 내용을 사용자 관점에서 제공한다.

- 이 후보가 선택된 이유
- 기억 단서와 일치하거나 다른 부분
- 영상에서 실제로 관찰된 사실
- 확인하지 못한 사실과 그 이유
- 후보의 대표 시점과 전후 맥락
- 다음에 사용자가 할 수 있는 동작

AI 내부 점수만으로 후보를 확정하지 않는다. 후보가 하나이더라도 자동 정답으로 처리하지 않고
사용자가 원본 장면과 근거를 확인할 수 있어야 한다.

### 7.5 보정 및 재탐색 고도화

- `조금 전·후` 보정은 기존 후보 주변의 제한된 범위만 다시 탐색한다.
- 시간 범위나 차량 조건을 수정할 때 어떤 부분을 다시 분석하는지 미리 안내한다.
- 재탐색 전 예상 추가 시간과 비용을 안내할 수 있도록 실측값을 축적한다.
- 재탐색하더라도 이미 찾은 후보와 사용자가 확인한 정보는 유지한다.
- 같은 조건의 무의미한 반복 실행을 막기 위해 이전 실패 원인과 변경된 조건을 비교한다.

### 7.6 실패 및 복구 고도화

| 결과 상태 | 사용자에게 보여 줄 의미 | 제공할 동작 |
| --- | --- | --- |
| 유력 후보 있음 | 기억 단서와 일치하는 후보를 찾음 | Top-3 비교 및 선택 |
| 유사 후보만 있음 | 일부 조건만 일치함 | 유사 후보 확인, 조건 수정 |
| 후보 없음 | 현재 범위에서 후보를 찾지 못함 | 범위 확대, 조건 수정, 종료 |
| 불확실 | 장면은 있으나 가림·흐림 등으로 확인 불가 | 원본 확인, 다른 후보 보기 |
| 시간·비용 제한 | 분석이 완료되기 전에 제한에 도달함 | 현재 후보 보기, 이어서 탐색 |
| 시스템 실패 | 모델·연결·처리 과정에서 오류 발생 | 현재 결과 유지, 실패 지점부터 재시도 |

## 8. As-Is / To-Be 비교

| 항목 | As-Is | To-Be |
| --- | --- | --- |
| 품질 판단 | 실행 성공과 후보 분포 중심 | 사람 정답지 기반 Recall@K·오탐·시간 오차 측정 |
| 후보 시간 | 모델 반환값 중심 | 영상 범위 검사와 대표 시점 정확도 관리 |
| 후보 처리 | 후보별 Fine 검증 | 중복 후보 정리 후 우선순위에 따라 Fine 검증 |
| Fine 비용 | 후보 수에 비례해 증가 | 후보 품질 개선과 조건별 설정 A/B로 최적화 |
| 불확실성 | 구조화 결과에 기록 | 사용자에게 원인과 다음 행동까지 설명 |
| 재탐색 | 보정 흐름 정의 | 영향 범위만 재분석하고 기존 결과 보존 |
| 기술 확장 | Gemini Coarse/Fine baseline | 실패 유형이 증명한 경우에만 challenger 검토 |
| 사용자 결과 | 항상 후보 비교 화면 | 평가 전까지 비교 화면 유지, 임계값 검증 후 분기 결정 |

## 9. W7 Quality / Risk Burn-down 운영 기준

### 9.1 W7 입력과 산출물

W7은 이 문서만 보고 계획을 고정하는 단계가 아니다. 다음 두 근거를 함께 사용한다.

```text
설계 기준선
- 현재 설계와 책임 범위
- 목표 설계와 성과지표
- 기존 탐침에서 확인한 위험

Real E2E 실행 근거
- 실제로 멈춘 단계
- 잘못되거나 누락된 결과
- 반복된 실패 유형
- 지연·비용이 집중된 구간
- 사용자가 복구하지 못한 흐름

        ↓ 결합

W7 우선순위와 고도화 작업
```

W7의 산출물은 구현 변경 자체뿐 아니라 다음 내용을 포함한다.

- 어떤 Real E2E 실패를 해결했는지
- 설계 문서의 어떤 To-Be 항목과 연결되는지
- 변경 전·후 동일 시나리오 결과가 어떻게 달라졌는지
- 남은 위험과 다음 우선순위가 무엇인지

### 9.2 우선순위 기준

| 우선순위 | 선정 기준 | Search 예시 |
| --- | --- | --- |
| P0 | Real E2E 완료를 막거나 결과를 사용할 수 없게 만든 문제 | 탐색 실행 불가, 후보가 원본 장면으로 연결되지 않음, 실제 사건이 후보에 없음 |
| P1 | E2E는 완료되지만 품질·복구·비용 위험이 큰 문제 | Top-3 오탐 과다, Fine 반복 비용, 불확실성 오표시, 재시도 시 결과 유실 |
| P2 | 실제 실패로 아직 확인되지 않았거나 효과 검증이 필요한 개선 | 신규 모델, CV 보조, UI 편의 개선, 처리 설정 최적화 실험 |

같은 우선순위에서는 다음 순서로 처리한다.

1. 여러 E2E 시나리오에서 반복되는 문제
2. 사용자가 잘못된 사건을 선택하게 만드는 문제
3. 후속 모듈의 진행을 막는 문제
4. 비용과 지연이 큰 문제
5. 국소적이거나 우회 가능한 문제

### 9.3 Real E2E 병목·실패 기록표

아래 표는 W7 시작 전에 실제 실행 결과로 채운다. 추측이나 기존 단독 실험 결과를 Real E2E
관찰로 대신 기록하지 않는다.

| ID | E2E 시나리오 | 병목·실패 유형 | 관찰 근거 | 영향 | 재현 빈도 | 연결된 설계 항목 | W7 우선순위 | 상태 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 입력 대기 | Real E2E 결과 전달 후 작성 | 실제 관찰 결과 필요 | 실행 로그·화면·산출물 | 미정 | 미정 | 미정 | 미정 | 대기 |

각 항목의 `관찰 근거`에는 실행 식별자, 실패 단계, 사용자에게 보인 결과, 재현 조건 중 확인 가능한
내용을 남긴다. 해결 후에는 같은 행 또는 연결된 W7 결과 기록에 변경 전·후 증거를 추가한다.

### 9.4 우선순위 조정 규칙

- §10의 단계는 **초기 순서**이며 Real E2E P0 항목이 있으면 해당 작업을 먼저 수행한다.
- E2E에서 재현되지 않은 개선은 삭제하지 않고 P2 후보로 유지한다.
- Search 외 모듈이 원인인 실패는 임의로 Search 문제로 고치지 않고 해당 Owner에게 전달한다.
- 하나의 증상에 여러 원인이 있으면 측정 가능한 실패 단위로 분리한다.
- 문제를 해결했다고 판단하려면 동일 시나리오가 통과하고 관련 품질지표가 악화되지 않아야 한다.
- 우선순위가 바뀌면 변경 이유와 근거를 이 문서에 기록한다.

## 10. 단계별 고도화 계획

아래 계획은 Real E2E 결과 반영 전의 초기 기준이다. W7에서는 §9의 P0 → P1 → P2 원칙에 따라
단계 내부 순서와 단계 간 순서를 조정한다.

### 1단계: 품질 기준 확립

- 4종 사건과 정상·유사 장면을 포함한 사람 정답지 구성
- Final Top-3 포함 여부, 대표 시점 오차, 사건 유형별 오탐 측정
- `NOT_OBSERVED`와 `UNCERTAIN` 판정의 사람 검토
- 현재 Gemini Coarse/Fine baseline 결과 고정

**완료 기준:** 같은 입력과 정답지를 이용해 이후 모든 개선안을 비교할 수 있다.

### 2단계: 후보 시간과 안정성 개선

- 영상 범위를 벗어난 후보 차단
- 대표 시점과 원본 시간축의 연결 검증
- 겹치는 후보와 동일 사건 후보 정리
- 부분 실패 시 기존 후보 보존 및 재시도 동작 확인

**완료 기준:** 모든 후보가 실제 원본 장면으로 이동하며, 시간 오차를 수치로 확인할 수 있다.

### 3단계: 정확도와 비용 개선

- 사건 유형별 Coarse/Fine 프롬프트 비교
- hard-negative 및 경계 사례 검증
- Fine 후보 수, FPS, 해상도, 후보 길이별 A/B 평가
- 품질 저하 없이 줄일 수 있는 비용과 처리 시간 확인

**완료 기준:** 기준선 대비 품질·비용·처리 시간의 변화가 동일한 정답지로 설명된다.

### 4단계: 사용자 보정 흐름 검증

- Top-3 비교 이해도와 후보 선택 성공률 확인
- `조금 전·후`, 범위 확대, 조건 수정 후 재탐색 성공률 측정
- 결과 없음과 분석 실패의 복구 동작 사용자 평가
- 전체 수동 탐색 대비 사용자 직접 작업시간 비교

**완료 기준:** 사용자가 실패 원인을 이해하고, 필요한 경우 스스로 다음 동작을 선택해 사건 확인까지
도달할 수 있다.

### 5단계: 조건부 기술 확장

다음 기술은 기본 설계에 즉시 포함하지 않는다. 현재 baseline의 실패 유형이 반복되고, PM 승인과
동일 정답지 비교를 통과했을 때만 검토한다.

| 반복되는 실패 | 검토할 확장 방향 |
| --- | --- |
| 사건 자체를 찾지 못함 | 다른 장시간 영상 검색 모델 또는 retrieval 방식 |
| 사건 전후 순서 판단 실패 | temporal verifier 또는 고정 참고사례 제공 |
| 차선·신호·차량 인식 실패 | 선택적 CV perception 보조 |
| 대상 차량 연결 실패 | 객체 추적 및 차량 association 보조 |
| Fine이 실제 후보를 제거 | Fine 모델·프롬프트·참고사례 개선 |
| 비용·지연이 허용 범위 초과 | 로컬 모델, CV, 처리 설정 최적화 검토 |

## 11. 고도화 성과 지표

목표 수치는 1단계 baseline 측정 후 PM·Search·Eval 담당자가 확정한다.

| 관점 | 지표 | 의미 |
| --- | --- | --- |
| 탐색 품질 | Recall@1 / Recall@3 / Recall@10 | 실제 사건이 상위 후보에 포함되는 비율 |
| 위치 품질 | 대표 시점 절대 오차 | 후보가 실제 사건 시점과 얼마나 가까운지 |
| 오탐 | 후보 Precision, Fine HN-FPR | 불필요한 검토 후보가 얼마나 남는지 |
| 불확실성 | UNCERTAIN 적정성 | 볼 수 없는 장면을 억지로 판단하지 않는지 |
| 유형 균형 | 사건 유형별 Recall·오탐 | 특정 유형에 성능이 편중되지 않는지 |
| 처리 성능 | 영상 1시간당 처리 시간 | 사용자가 기다려야 하는 시간 |
| 비용 | source-hour당 비용, 후보당 Fine 비용 | 운영 가능한 비용인지 |
| 사용자 효율 | 사건 확인까지의 직접 작업시간 | 수동 탐색보다 부담이 줄었는지 |
| 보정 효과 | 보정 후 재탐색 성공률 | 사용자 개입이 실제 결과 개선으로 이어지는지 |
| 복구성 | 부분 실패 후 결과 보존율 | 실패해도 처음부터 다시 시작하지 않는지 |

## 12. 결정이 필요한 항목

다음 항목은 현재 확정하지 않고 평가 결과를 바탕으로 결정한다.

1. 단일 유력 후보 화면과 후보 비교 화면을 나누는 기준
2. 사용자 보정·재탐색 횟수와 비용 상한
3. 사건 유형별 목표 Recall과 허용 오탐 수준
4. 사용자에게 안내할 예상 시간·비용의 표현 방식
5. 성능 부족 시 먼저 열 challenger와 적용 사건 유형
6. 이번 Real E2E에서 확인된 Search 병목·실패의 P0/P1/P2 분류

## 13. 기대 효과

- 사용자는 장시간 영상을 직접 반복 재생하는 대신 Top-3 후보와 근거만 검토할 수 있다.
- 잘못된 시간 구간과 중복 후보가 줄어 후보 카드의 신뢰도가 높아진다.
- 불확실성과 실패 원인을 구분해 사용자가 다음 행동을 선택할 수 있다.
- 품질과 비용을 같은 정답지에서 비교하여 근거 없이 모델을 교체하는 일을 줄인다.
- 일부 실패나 사용자 보정이 발생해도 기존 결과를 유지해 전체 작업의 반복을 줄인다.
