## 1. 현재 추천 결론

**① 평가의 정규화 단위를 `1분 clip`으로 고정한다**

> **결론:** 모든 분모를 clip으로 통일한다. `FP/hour → FP/clip`, `source-video-hour당 원가 → cost_per_clip`. 외부 비교 시에만 시간당 환산치를 병기한다.
**근거:** `[확인]` 제품 입력 형태가 "1시간 원본 1개"에서 "1분 클립 다수 업로드"로 바뀌었다. 블랙박스 Normal 녹화의 사실상 표준이 1분이다.
**Architecture 영향:** **있음** — 공통 기반 사용량 장부의 집계 단위가 `source-video-hour`로 문서에 박혀 있다(모듈구조 v3 §6-1, 테크스펙 §3).
> 

**② 예측(prediction)과 채점(scoring)을 물리적으로 분리한다**

> **결론:** 모델을 호출하는 `runners/`와 점수를 내는 `scorers/`를 분리하고, 같은 예측 파일을 여러 GT 버전으로 재채점할 수 있게 한다.
**근거:** `[확인]` 정답지·지표 정의는 10주 동안 여러 번 바뀐다. 합쳐두면 정의가 바뀔 때마다 유료 API를 다시 호출해야 한다. MLflow는 "1 run = 1 결과" 전제라 재채점 구조와 충돌해 채택하지 않았다.
**Architecture 영향:** **있음(작음)** — 결과 파일 필수 필드가 늘어난다(§4 참조). 폴더 구조 자체는 모듈 내부 사정이다.
> 

**③ 지표를 3개 tier에 명시적으로 귀속시킨다**

> **결론:** A(AI-Hub 이미지) = 분류 4종 / B(유튜브 1분 클립) = 탐색·오탐·비용 / C(팀원 SD카드 원본) = 번호판·시각. **한 데이터셋으로 13개 지표를 다 잴 수 없다.근거:** `[확인]` 유튜브는 재인코딩으로 메타데이터가 소실되고 번호판이 모자이크된 경우가 많다. AI-Hub는 위반만 모아 둔 데이터라 정상 주행 비율이 없어 `fp_per_clip`의 분모가 없다.
**Architecture 영향:** **있음** — A tier는 현재 `search` 공개 인터페이스로 진입할 방법이 없다(§3, §6-A).
> 

**④ Classification(위반 유형 판정)을 독립 채점 대상으로 둔다**

> **결론:** 후보 탐색의 뒷단이 아니라, 클립·프레임을 직접 넣어 유형과 대상 차량을 채점하는 **단독 작업**으로 다룬다.
**근거:** `[확인]` A tier는 다른 모듈 구현을 기다리지 않고 지금 돌릴 수 있는 유일한 tier다. 파이프라인에 묶으면 `search`가 완성될 때까지 분류 성능을 한 번도 못 잰다.
**Architecture 영향:** **있음** — v3의 `verify_candidate(candidate_ref)`는 후보 참조를 요구하므로 이 형태로는 호출할 수 없다.
> 

**⑤ 분류 지표는 macro만 보고하고 micro는 전 구간 금지한다**

> **결론:** `recall_macro` · `precision_macro` · `confusion_matrix`(5×5 필수) · `target_correct`. 보고 계층은 macro → 4종 → 8세부유형.
**근거:** `[확인]` 4종 + NONE의 5-way이고 유형별 빈도가 크게 다르다. micro는 다수 유형이 희소 유형을 가린다.
**Architecture 영향:** **없음** (지표 정의. 단 v3 §3-5·§9-3 표의 지표 이름은 갱신 대상)
> 

**⑥ 결과 저장은 JSON 파일 + git으로 한다**

> **결론:** 실험 추적 도구를 도입하지 않는다. Notion은 판단·요약 레이어로 JSON 위에 얹고, 숫자의 출처는 항상 JSON이다.
**근거:** `[확인]` 재채점 구조와의 충돌(②) + `eval`이 제품 DB를 갖지 않는다는 v3 결정(테크스펙 §3-7 "제품 DB 아님 — 파일 기반")과 정합.
**Architecture 영향:** **없음**
> 

**⑦ locked test 개봉 규칙을 코드로 강제한다**

> **결론:** `[제안]` locked는 실제 영상만·총 3회 개봉·2인 승인. `group_key` 단위로 분리해 dev와 섞이지 않게 한다.
**근거:** `[확인]` v3 §9-2 규칙 5가 "버전이 다르면 비교를 거부한다"까지만 정하고, **누가 어떤 조건에서 locked를 여는지는 비어 있다.Architecture 영향:** **있음(운영 정책)** — 승인 주체 지정은 PM 결정 사항이다.
>

## 3. 현재 Module Architecture에 미치는 영향

### 3-1. 그대로 유지 가능한 것

- **`eval`은 제품 런타임이 아닌 형제 패키지** (v3 §9-1) — 유지.
- **의존 방향 `eval → {search, readout, recording}` 단방향** — 유지. `case`·`evidence`·`web`을 모른다는 규칙도 유지 가능하다. CI 검색 규칙(`eval/`에서 `import case`·`import evidence` 0건)을 그대로 쓸 수 있다.
- **구현을 이름표로 지정** (`-impl gemini-coarse@c7`) — 유지. 여러 구현을 같은 정답지로 비교하는 방식 그대로다.
- **`search`·`readout`은 `eval`의 존재를 모른다** (`if 평가모드:` 금지) — 유지.
- **사용자 수정 데이터는 파일(learning_log)로만 흐른다** — 유지. 지표에서 `사용자 수정률`을 뺐지만 **수집을 멈추는 것은 아니다.**
- **Product 지표는 코드 채점기가 아니다** (v3 §3-5 마지막 행) — 유지. baseline 측정은 별도 프로토콜.

### 3-2. 수정 검토가 필요한 것

**(1) `AnalysisScope`로는 평가 클립을 지정할 수 없다**

> **현재 구조:** `AnalysisScope`의 입력은 `time_ranges`(절대 시각) + `target_event_types` + `hint` + `budget`. **파일이나 자산을 가리키는 필드가 없다.** v3 §9-2 규칙 2는 "제품과 똑같은 `AnalysisScope`가 유일한 접점"이라고 못 박았다.
**조사 결과:** `[확인]` B tier 유튜브 클립에는 절대 시각이 아예 없다(재인코딩으로 소실). `time_ranges`로 표현할 방법이 원리적으로 없다.
**왜 검토가 필요한가:** 지금 상태로는 **"제품과 같은 입력을 쓴다"는 규칙을 지키면서 B tier를 돌리는 것이 불가능**하다. 이 규칙이 깨지면 "채점기 숫자가 곧 제품 성능"이라는 주장의 근거가 약해진다.
**영향받는 모듈:** `search`(서어진), `case`(유소연 — `AnalysisScope` 생산자), `recording`(정철원 — 자산 참조 형식)
> 

**(2) `search`에 A tier(프레임 시퀀스)를 넣을 진입점이 없다**

> **현재 구조:** `search_candidates(scope)` / `verify_candidate(candidate_ref)` 둘뿐. 둘 다 영상 기반이다.
**조사 결과:** `[확인]` AI-Hub는 프레임 시퀀스다. `[제안]` 현재 계획은 프레임 묶음을 모델에 직접 넣는 것이다.
**왜 검토가 필요한가:** `eval`이 모델을 직접 부르면 **가정 A4("외부 AI로 영상이 나가는 코드는 `search` 안 어댑터 한 곳뿐")를 정면으로 위반한다.** A4는 v3가 "반드시 지켜야 함"으로 표시한 항목이고, 깨지면 개인정보 검토 지점이 두 곳으로 늘어난다.
**영향받는 모듈:** `search`(서어진), 개인정보·보안 검토(김준영)
> 

**(3) `CandidateEvent.at`(절대 시각)과 `timestamp_error`의 정답 형식이 맞지 않는다**

> **현재 구조:** `CandidateEvent.at = "18:31:48"` + `at_provenance`. 절대 시각이다.
**조사 결과:** `[확인]` B tier 정답은 클립 내부 상대 초(`onset_sec`)다. 클립에 절대 시각이 없으므로 변환할 기준점도 없다.
**왜 검토가 필요한가:** `timestamp_error`(주지표)를 계산할 수 없다. **v3 §3-2가 "시간축 기준점과 사건 발생시각은 다른 값"이라고 이미 구분해 둔 것과 같은 문제**이므로, 계약에 상대 위치를 별도로 담을지 결정이 필요하다.
**영향받는 모듈:** `search`(서어진), `recording`(정철원 — 기준점 제공 주체)
> 

**(4) v3의 채점 대상 표가 옛 지표를 담고 있다**

> **현재 구조:** v3 §3-5 / §9-3, 테크스펙 §3에 `Recall@10` · `FP/hour` · `source agreement` · `offset error` · `사용자 수정률` · `Fine exposure ratio`가 적혀 있다.
**조사 결과:** `[확인]` 지표 v2에서 삭제·대체됐다. (삭제 6 · 대체/재정의 6 · 분리 1 · 보류 2)
**왜 검토가 필요한가:** 문서 간 불일치가 남으면 다음 사람이 어느 쪽이 최신인지 알 수 없다.
**영향받는 모듈:** 문서 소유자(김준영 PM). **모듈 경계는 바뀌지 않는다 — 표 갱신만 필요하다.**
> 

**(5) 비용 지표를 `eval`이 산출할 경로가 없다**

> **현재 구조:** `cost_per_clip = Coarse + Fine + Plate OCR + Time Resolver + storage/transfer + geocoder`. 사용량 장부는 **공통 기반**이 소유하고 소유자는 김준영이다.
**조사 결과:** `[확인]` `search`의 `AnalysisRun.cost`만 합산하면 `readout` OCR·storage·geocoder가 빠진다(테크스펙 §3에 이미 경고되어 있음).
**왜 검토가 필요한가:** **의존 규칙에 `eval → 공통 기반` 경로가 없다.** 장부를 직접 읽으면 단방향 규칙이 흔들리고, 안 읽으면 `cost_per_clip`이 영원히 반쪽 숫자다.
**영향받는 모듈:** 공통 기반/운영(김준영), `readout`(신유민 — 판독 비용 보고)
> 

**(6) 결과 파일의 필수 필드가 v3 규정보다 늘어난다**

> **현재 구조:** v3 §9-2 규칙 5 = `contract_version` + 구현 이름표 + manifest 버전.
**조사 결과:** `[제안]` 예측과 채점을 분리했으므로 **"예측 시점의 impl"과 "채점 시점의 GT 버전"이 둘 다** 필요하다. 여기에 `polarity_rule`과 source(aihub/youtube)가 추가된다.
**왜 검토가 필요한가:** 이 필드들이 없으면 재채점 결과끼리 비교가 성립하지 않는다. v3 규칙 5의 취지를 지키기 위한 확장이지 반대가 아니다.
**영향받는 모듈:** `search`·`readout`(실행 기록에 담기는 필드 일부) / 나머지는 `eval` 내부
> 

**(7) `eval/` 폴더 구조가 v3 예시와 다르다**

> **현재 구조:** v3 §9-3 = `manifest/` · `cases/{search,plate,time}/` · `references/` · `locked_test/` · `runner.py` · `scorer.py` · `results/`**조사 결과:** `[제안]` 실제 구조는 `cases/{candidate,classification,plate}/` · `datasets/` · `predictions/` · `results/` · `failures/` · `module_records/` · `runners/` · `scorers/` · `common/` · `report/`. `time` 정답지는 C tier에 종속되어 착수 시점이 뒤로 밀린다.
**왜 검토가 필요한가:** **대부분은 모듈 내부 사정이라 알아서 정하면 된다.** 다만 `module_records/`(다른 사람이 돌린 케이스 기록)는 v3에 없는 개념이고, **다른 모듈 Owner가 결과를 넘겨주는 경로이므로 계약에 해당한다.영향받는 모듈:** 케이스 6·8·9·10을 실행하는 담당자들
> 

### 3-3. 판단 불가 (자료 부족)

| 항목 | 왜 판단할 수 없나 |
| --- | --- |

| B tier 목표 클립 수 | 무편집 주행영상은 위반 밀도가 낮다. 파일럿 1~2개를 라벨링해 밀도를 본 뒤에야 총량이 정해진다 |

| 공통 기반 | `장부 → eval` | clip 단위 비용·토큰·지연 | 장부 단위가 `source-video-hour`. `eval → 공통기반` 의존 경로가 없다 | 장부를 파일로 내보내 `eval`이 읽는 형태로 할지. 단위를 clip으로 바꿀지 |

| 각 모듈 Owner | `사람 → eval` | 케이스 6·8·9·10 실행 기록 | v3에 없는 경로(`module_records/`) | 남이 돌린 결과를 **어떤 형식으로** 넘기는가. 형식이 없으면 현황판이 손으로 채워진다 |

**특히 결정이 필요한 성격들**

- **필수 vs optional:** `at`(절대 시각)은 B tier에서 채울 수 없으므로 optional이어야 한다. 반대로 상대 offset은 평가에서 필수다.
- **UNKNOWN/ABSTAIN 표현:** 시각은 `UNKNOWN`(정보 없음)과 `ERROR`(시도 실패)가 이미 다른 상태로 존재한다(v3 §3-6). **평가는 이 둘을 반드시 구분해서 세야 한다.** 번호판은 `abstained`가 분모를 가르므로 없으면 `wrong_accept_rate`를 계산할 수 없다.
- **불변이어야 하는 값:** 실행 기록(`AnalysisRun`)과 예측 파일. 재실행은 항상 새 기록이어야 한다.
- **배열로 보존해야 하는 값:** 후보(상위 3개 이상, 순위 포함), 시각 후보(출처별), 번호판 프레임별 후보.
- **Reference만 필요한 값:** 원본 영상 실물이 아니라 클립 ID/경로 참조로 충분하다.
- **downstream으로 넘겨야 하는 값:** 비용·지연·실패 분류. 이게 실행 기록에 없으면 Efficiency 지표가 성립하지 않는다.

## 6. 충돌 / 상대 담당자 확인 필요

### A. 기존 Architecture와 충돌

**A-1. `AnalysisScope` 단일 입력 원칙 ↔ 시각 없는 평가 클립**
v3 §5-③은 "제품과 채점기가 **똑같은** `AnalysisScope`를 쓴다. 이래야 채점기 숫자가 제품 성능이라고 말할 수 있다"고 못 박았다. 그런데 `AnalysisScope`의 유일한 위치 표현은 `time_ranges`(절대 시각)이고, **B tier 클립에는 절대 시각이 존재하지 않는다.** 원칙을 지키려면 계약을 바꿔야 하고, 계약을 안 바꾸면 원칙이 깨진다.
→ **함께 볼 사람: 서어진(`search`) · 유소연(`case`) · 김준영(PM)**

**A-2. 가정 A4(외부 전송은 `search` 어댑터 한 곳) ↔ A tier 직접 호출**
v3는 A4를 "**반드시 지켜야 함**"으로 표시했다. 그런데 A tier는 프레임 시퀀스라 `search`의 어떤 공개 함수로도 들어가지 않는다. 현재 계획대로면 `eval`이 외부 모델을 직접 부르게 되고, 이는 **개인정보 검토 지점이 흩어지는 상황**을 A4가 막으려던 바로 그 사고다.
→ **함께 볼 사람: 서어진 · 김준영(개인정보·보안)**

**A-3. `verify_candidate(candidate_ref)` ↔ Classification 단독 실행**
v3에서 Fine은 후보 참조를 받는 함수다. 그런데 `eval`은 Classification을 **후보 없이 단독으로** 채점하려 한다(다른 모듈을 기다리지 않기 위해). 현재 인터페이스로는 호출할 수 없다.
→ **함께 볼 사람: 서어진**

**A-4. `timestamp_error` ↔ `CandidateEvent.at`의 절대 시각 전제**
후보의 시각은 절대 시각으로만 표현된다. 평가 정답은 클립 내 상대 초다. **주지표 하나가 계산 불가 상태다.**
→ **함께 볼 사람: 서어진 · 정철원(`recording`)**

**A-5. `eval → 공통 기반` 경로 부재 ↔ `cost_per_clip`**
의존 규칙은 `eval → {search, readout, recording}`뿐이다. 비용 구성식의 절반(storage/transfer·geocoder)은 공통 기반에만 있다.
→ **함께 볼 사람: 김준영**

**A-6. v3 §3-5·§9-3 채점 대상 표와 지표 v2 불일치 (문서 수준)**`Recall@10` · `FP/hour` · `source agreement` · `offset error` · `사용자 수정률`이 v3에 남아 있다. **모듈 경계는 바뀌지 않으므로 표 갱신만 하면 된다.**
→ **함께 볼 사람: 김준영(PM)**

### B. 다른 모듈과 충돌 가능

**B-1. 서비스가 업로드된 클립을 다시 분할하는가 (서어진)**
재분할하면 평가의 clip 단위와 서비스의 처리 단위가 어긋난다. `fp_per_clip` / `fp_per_minute` 선택과 Recall 계산이 함께 바뀐다. **지표 문서 확정이 이 답변을 기다리고 있다.**

**B-2. 실패 분류 이름의 현행 버전 (김준영)**
v3 §12 RT12에서 `PLATE_*` 접두어 규칙을 정했다. 이 이름이 현재도 유효한지, 아니면 갱신된 목록이 있는지 확인이 필요하다. `eval`이 stage별 집계를 하려면 이름이 고정돼야 한다.

**B-3. 메타데이터 신뢰도 실측 (정철원)**`ffprobe`에 시각 필드가 실제로 있는지, 제조사별로 믿을 만한지에 따라 **화면 시각 OCR 지표가 살거나 죽는다.** 없는 기능의 지표를 미리 만들면 채점기만 무거워진다.

**B-4. C tier 착수 시점 (정철원)**
plate 3종 + time 2종, 총 **5개 지표가 통째로 여기 묶여 있다.** 늦어지면 동시에 막힌다. 번호판 샘플만이라도 먼저 확보하는 우회 경로를 검토 중이다.

**B-5. clip당 비용 실측 (서어진)**`AnalysisRun.cost` 필드가 확정되고 실측이 나와야 Efficiency 지표가 숫자로 채워진다.

**B-6. 대상 지목 책임 귀속 (서어진 + 신유민)**`target_correct`(Fine)와 Plate `Target Association`은 같은 질문을 두 단계에서 묻는다. 정하지 않으면 오지목이 났을 때 **어느 모듈의 실패인지 아무도 책임지지 않는다.**

### C. Product / 정책 결정 필요

**C-1. 시각 허용 오차 (±1초? ±1분?)**
안전신문고가 요구하는 정밀도가 분 단위인지 시 단위인지에 따라 `time_accuracy`와 `timestamp_error`의 합격선이 **동시에** 정해진다. 규정 확인 사안이다. → 김준영(`evidence`)

**C-2. A tier를 제품 성능 주장에 쓸 수 있는가**
이미지와 영상 결과가 어긋날 때 무엇을 말할지는 기술이 아니라 제품 주장의 문제다. → PM

**C-3. locked test 개봉 권한**
"2인 승인"의 2인이 누구인지, 3회를 언제 쓰는지는 운영 규칙이다. → PM

**C-4. 평가 데이터의 개인정보 취급** `[검토]eval/cases/plate/`에는 **실제 번호판 문자열이 평문으로** 저장되고 git으로 관리된다. C tier는 팀원 SD카드의 실제 촬영본이므로 **타인의 번호판**이다. v3의 마스킹 로거 규칙은 "로그"를 대상으로 하고 정답지는 다루지 않는다. **정답지 저장소의 보관·공유 범위를 별도로 정할 필요가 있다.** → 김준영(개인정보) · PM

## 7. 후속 Data Contract에서 반드시 다룰 질문

1. `AnalysisScope`는 **자산(클립) 참조를 가질 수 있는가?** 아니면 평가는 시각 기반 표현만 쓰도록 강제되는가?
2. 절대 시각이 존재하지 않는 입력(유튜브 클립)을 `AnalysisScope`에서 **어떻게 표현하는가?** `time_ranges`를 optional로 만들 수 있는가?
3. `CandidateEvent`는 절대 시각(`at`) 외에 **클립 내 상대 offset(초)** 을 함께 가져야 하는가? 아니면 `recording`이 기준점을 제공해 `eval`이 계산하는가?
4. `search`에 **프레임 시퀀스 입력 경로**를 만들 것인가? 만들지 않는다면 A tier 평가는 가정 A4의 공식 예외로 문서화되어야 하는가?
5. Classification을 **후보 참조 없이** 호출할 수 있는 공개 함수가 필요한가? (`verify_candidate`의 입력을 넓힐 것인가)
6. `search` 실패를 **빈 후보 배열로 표현할 것인가, 별도 실패 상태로 둘 것인가?** — `recall`의 분모와 `fp_per_clip`의 계산이 갈린다.
7. 후보 배열의 **순위는 보장되는가?** 동점일 때 순서 규칙은 무엇인가? (`recall@1`과 `recall@3`의 차이가 여기서 나온다)
8. `readout`의 **abstain 임계값을 실행 기록에 남길 것인가?** 남기지 않으면 두 실행을 비교할 수 없다.
9. 사용량·비용 장부를 **파일로 내보내 `eval`이 읽는 형태**로 할 것인가? 장부의 집계 단위를 clip으로 바꿀 것인가?
10. 다른 Owner가 실행한 케이스 기록(`module_records/`)은 **어떤 최소 필드**를 갖춰야 하는가? (실행자 · 구현 이름표 · 입력 · 결과 · 날짜)

## 8. 아키텍처 반영 우선순위

### 🔴 Architecture v4 전에 반드시 결정

| 항목 | 왜 여기인가 |
| --- | --- |
| `AnalysisScope`가 평가 클립을 지목하는 방법 (§6-A-1) | 계약 자체의 필드가 바뀐다. `case`가 생산자이므로 모듈 경계에 걸린다 |
| A tier의 외부 모델 호출 주체 (§6-A-2) | 가정 A4가 유지되는지 깨지는지의 문제다. 개인정보 검토 범위가 달라진다 |
| Coarse / Fine 2단계 구조 유지 여부 | `AnalysisRun.stage` 값과 `search` 내부 구성이 함께 달라진다 |
| Classification 단독 호출 경로 (§6-A-3) | `search` 공개 인터페이스가 늘어난다 |
| `eval`이 비용 장부를 읽는 경로 (§6-A-5) | 의존 규칙 자체를 건드린다 |

### 🟡 Data Contract 단계에서 결정

- `CandidateEvent`에 클립 상대 offset 추가 여부
- 후보 배열 순위·동점 규칙, 실패의 표현 형태(빈 배열 vs 실패 상태)
- 실패 분류 이름 목록 확정 (`PLATE_*` 접두어 현행 여부)
- 결과 파일 필수 헤더 확장 (GT 버전 · `polarity_rule` · source)
- `abstained` + 임계값 기록 필드
- `target` 표현 형식 (bbox / track_ref / 설명문)
- `module_records/`에 넘기는 최소 필드
