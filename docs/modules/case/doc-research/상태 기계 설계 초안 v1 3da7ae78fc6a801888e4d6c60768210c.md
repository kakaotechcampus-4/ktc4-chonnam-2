# 상태 기계 설계 초안 v1

## case 상태 기계 설계 (초안 v1)

### 1. stage 5개

| stage | 의미 | 진입 조건 | 근거 |
| --- | --- | --- | --- |
| INTAKE | 자연어 단서를 LLM이 구조화한 직후, 사용자가 확인·수정 중 | create_case 호출 시 | 테크스펙 §7 Runtime Flow, "case 소유범위 5: 자연어 단서 해석" |
| SEARCHING | 1·2차 탐색 진행 중 (세부는 progress[]가 SCOPE/COARSE/FINE로 추적) | start_search 호출 시 | 테크스펙 p.28-29 CaseView 예시 |
| CANDIDATE_REVIEW | Top-3 후보 검토 중 (후보 0개인 경우 포함) | 1·2차 탐색 완료 시 | §10/§8-3 "1차 탐색 후보 0개"를 정상 결과로 취급 — 후보 0개도 이 stage에 머물고 notices로만 구분 |
| EVIDENCE_REVIEW | 증거 확정·요건검사·패키지 조립 진행 중 | select_candidate 호출 시 | 테크스펙 §7 Runtime Flow |
| READY | 패키지 완성, handoff 대기 | build_package 성공 시 | 별도 stage로 둔 이유는 아래 "왜 READY는 따로 뒀나" 참고 |

**왜 READY는 따로 뒀나 (후보 0개와 다르게 취급한 이유)**: web 모듈 설계 원칙이 "화면이 규칙을 다시 계산하면 백엔드와 다른 답을 내놓는다"(테크스펙 p.26, v3 p.26). "패키지가 준비됐는지"는 requirements.readiness나 package 필드를 보고 web이 직접 판단해야 하는 규칙이라, 그걸 web이 스스로 계산하게 두면 이 원칙을 어김. 반면 "후보가 0개인지"는 그냥 candidates 배열 길이를 보면 됨. 

EvidenceRecord.state의 `READY_WITH_WARNINGS`(테크스펙 p.22)는 evidence 쪽 필드고, case.stage는 그걸 그냥 READY로 뭉뚱그려 받고 "경고가 있다"는 사실 자체는 notices로 따로 보여주는 걸 추천해 — 부분실패=notices 원칙과 일관되게.

### 2. 전이 표 (정방향)

| from | 트리거 | to | 비고 |
| --- | --- | --- | --- |
| INTAKE | start_search | SEARCHING | update_hints는 INTAKE 안에서 반복 가능(비용 0) |
| SEARCHING | 1·2차 탐색 완료 (search_candidates+verify_candidate 종료) | CANDIDATE_REVIEW | 후보 수와 무관하게 항상 여기로 |
| CANDIDATE_REVIEW | select_candidate | EVIDENCE_REVIEW | selection_rev +1 |
| EVIDENCE_REVIEW | build_package 성공 | READY | requirements 충족 여부와 무관하게 패키지 생성 시점 기준 |

### 3. 역방향 전이 (정정 트리거) — 지난 대화에서 확정한 대로 재실행표 근거

| 트리거(corrections.kind) | 발생 가능 stage | 이동 stage | 재실행표 근거(행) |
| --- | --- | --- | --- |
| TIME_HINT_EDIT | CANDIDATE_REVIEW / EVIDENCE_REVIEW / READY | SEARCHING | 1행: 후보·2차확인·선택·증거 전부 폐기, 1차 탐색부터 |
| TIMELINE_REBASE(범위 자체가 틀린 경우) | 어디서든 | SEARCHING | 9행: 후보 이후 전부 폐기 |
| OTHER_CANDIDATE | EVIDENCE_REVIEW / READY | CANDIDATE_REVIEW (또는 즉시 재선택 후 EVIDENCE_REVIEW로 재진입) | 2행: 증거 기록 무효화, 1차 탐색은 안 건드림 |
| PLATE_MANUAL_EDIT / PLATE_REREAD / SPAN_ADJUST / REPORT_TYPE_CHANGE / EVENT_TIME_MANUAL | EVIDENCE_REVIEW / READY | 제자리(EVIDENCE_REVIEW로 회귀, READY였으면 패키지 무효화) | 3~7행: 전부 요건검사 이하만 재실행, 탐색 안 건드림 |
| TIMELINE_REBASE(경미한 경우) | 어디서든 | 제자리 | 8행: 시간축만 재계산, 1차 탐색 안 건드림(범위가 그대로면) |

핵심 규칙: **READY에서 어떤 정정이 들어와도 package는 즉시 무효화(null)되고, 표의 규칙대로 필요한 만큼만 되돌아간다.** ReportPackage는 "파생값, 언제든 재계산"이라(계약⑨, 두 문서 동일)

그리고 여기서 update_hints(INTAKE 전용, 무료)와 corrections.kind=TIME_HINT_EDIT(SEARCHING 이후, 비용 발생)의 차이가 명확해짐 — **같은 종류의 수정이라도 INTAKE에서 하면 그냥 편집이고, 이미 탐색이 시작된 뒤엔 정식 "정정"으로 취급돼서 재실행 비용이 붙는다**는 게 이 설계의 논리.

### 4. stage별 허용 액션 (web이 뭘 부를 수 있는지)

| stage | 허용 | 의미 없는 호출 |
| --- | --- | --- |
| INTAKE | update_hints, start_search | select_candidate, request_correction |
| SEARCHING | (조회만: get_view) | select_candidate — 아직 후보 없음 |
| CANDIDATE_REVIEW | select_candidate | request_correction(PLATE_* 등 — 아직 선택 전) |
| EVIDENCE_REVIEW | request_correction (전체 8종) | select_candidate(이미 선택함, 다른 후보로 바꾸려면 OTHER_CANDIDATE 정정으로) |
| READY | request_correction (전체 8종, 패키지 무효화), 다운로드/handoff | — |

### 5. 부분 실패 표현 — 지난 답변 그대로

stage에는 안 담고, `notices`에 job_id/field 단위로 담는다. §10/§8-3의 11가지 케이스는 전부 notices 후보고, 이건 CaseView 설계(항목 5)에서 신유민과 스키마 확정할 때 같이 정리하면 됨.

### 아직 열려 있는 것 (내가 확정 못 짓고 남긴 것)

- **READY에서 실제로 사용자가 안전신문고에 제출을 완료했는지 case가 알 방법이 없음**(API 연동 안 함, 두 문서 다 명시) — case의 상태 기계엔 "제출완료" 상태가 없고 READY가 사실상 종단. web이 자체적으로 "제출함" 체크 같은 걸 원하면 이건 case의 stage가 아니라 web 쪽 로컬 UI 상태로 둬야 할지 논의 필요

상태 기계란?

핵심 요소는 세 가지: (1) 있을 수 있는 상태들의 목록(state), (2) 각 상태에서 다른 상태로 넘어갈 수 있는 길(transition)과 그 조건, (3) 각 상태에서 허용되는 행동이 뭔지(예: EVIDENCE_REVIEW 상태에서는 request_correction을 부를 수 있지만 select_candidate는 이미 의미가 없다든가).

→ case는 "사용자가 지금 어디까지 왔는지"를 스스로 기억하고 있어야 하는 유일한 모듈
