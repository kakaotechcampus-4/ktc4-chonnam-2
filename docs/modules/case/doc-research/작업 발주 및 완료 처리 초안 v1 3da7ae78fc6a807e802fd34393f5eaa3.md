# 작업 발주 및 완료 처리 초안 v1

## 늦게 온 결과를 버리는 규칙

### A. case_rev / selection_rev 관계 — 제안

**설계**: selection_rev를 case_rev의 부분집합으로 둔다. 즉 **selection이 바뀌거나 무효화되는 이벤트는 항상 case_rev와 selection_rev를 같이 올리고, 그 외의 모든 case-level 이벤트는 case_rev만 올린다.**

⇒**case_rev = 전체 늦은 결과 거르는 용도, selection_rev = 증거 값이 어느 후보에 속하는지 구분하는 용도**

| 이벤트 | case_rev | selection_rev |
| --- | --- | --- |
| start_search | 올림 | - |
| select_candidate(최초) / OTHER_CANDIDATE | 올림 | 올림 |
| TIME_HINT_EDIT, TIMELINE_REBASE(범위자체틀림) | 올림 | 올림 (표의 "폐기되는 것"에 "선택"이 포함돼 있어서 — 재실행표 1·9행) |
| PLATE_MANUAL_EDIT, PLATE_REREAD, SPAN_ADJUST, REPORT_TYPE_CHANGE, EVENT_TIME_MANUAL, TIMELINE_REBASE(경미) | 올림 | 그대로 (표의 "폐기되는 것"에 "선택"이 없음) |

### B. input_fingerprint 공식 — 최종 제안

: input_fingerprint가 같으면 다시 돌리지 않고 이전 결과를 쓰기. 사용자가 단서를 고쳤다가 되돌렸을 때 비용을 두 번 쓰지 않기 위한 장치

```
input_fingerprint = hash(
  AnalysisScope의 정규화된 값 (time_ranges + target_event_types + hint + budget)
  + 현재 활성 구현 이름표 (search/readout의 list_impls()에서 얻은 문자열, 예: "gemini-coarse@c7")
)
```

- 이 재사용 검사는 `start_search`/`select_candidate` 경로에서만 적용되고, `request_correction`(PLATE_REREAD)과 needs_map을 통한 발주는 이 검사를 건너뛴다.

### C. 회의에서 언급할 "외부 정보 확인 필요" 목록

**1. usage_ledger 조회 인터페이스가 없음**

- 문제: 비용 상한 초과 시 발주를 거부하려면(N8, §8-2) case가 usage_ledger(공통기반)에 "지금까지 얼마 썼는지"를 물어봐야 하는데, 이 조회용 함수/시그니처가 두 문서 어디에도 없음 — 표(DB 스키마)만 있고 API가 없음
- 필요한 것: **김준영(공통기반 오너)에게 case가 예산 확인 시 호출할 함수 이름·시그니처를 확인**
- 출처: 테크스펙 §3-6(p.23), v3 p.14/43

> usage_ledger가 case가 발주 전에 실시간으로 조회해야 하는 테이블인지, 아니면 eval의 사후 집계용 장부일 뿐이고 case의 실시간 예산 체크는 그냥 JobRecord.cost 합산으로 자체 해결하면 되는 건지
> 

→ 상한 초과시 발주 거부라고 설명 되어 있는데, 비슷한 설명이 eval의 "Efficiency" 채점 항목(v3 p.46, "source-video-hour당 원가, latency, tokens, Fine 노출 비율") 에도 나와 있음.

**2. AnalysisScope.budget의 실제 숫자값 미정**

- 문제: max_cost_krw, max_latency_sec에 어떤 값을 넣을지가 "서어진의 비용·지연 실측 후 확정"이라고 스펙에 명시돼 있음(테크스펙 p.25) — 아직 실측 전이라 case 쪽에서 임의로 숫자를 정할 수 없음
- 필요한 것: **서어진의 1차 탐색 비용·지연 실측 결과**(둘 다 문서의 일정 §1~2주차 계획에 이미 포함된 작업)
- 출처: 테크스펙 p.25, 일정 §2(테크스펙 p.4, v3는 R&R 다루지 않아 해당 없음)
