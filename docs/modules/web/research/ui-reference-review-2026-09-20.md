# [web] UI 레퍼런스 대조 — 어디서 따왔나

작성 2026-09-20 · 김대원
대상: web 전체 와이어프레임 (아트보드 8개)

---

## 읽는 법

표의 **「바꾼 것」이 이 문서의 핵심**입니다. 그대로 가져온 패턴은 하나도 없습니다.

대신고는 **AI가 위반을 판정하는 제품이 아닙니다.** 신고할 가능성이 있는 후보를 제시하고, 최종 제출은 사용자가 안전신문고에서 직접 합니다. 그래서 레퍼런스가 「사용자를 설득하는 방향」으로 설계된 부분은 전부 「사용자가 판단하는 방향」으로 뒤집어야 했습니다.

같은 이유로 **장르가 다른 제품에서 더 많이 가져왔습니다.** 신고 앱·블랙박스 앱보다, 문제 구조가 같은 사진 관리 도구·문서 OCR 도구·CI 대시보드가 훨씬 쓸모 있었습니다.

## 1. 올리면 진행 (스트림)

> 이 화면은 원래 「찾는 중」이라는 별도 진행 화면이었습니다. 멘토 피드백(사용자 개입 최소화)에 따라 받기 → 찾기 → 후보 자동 채택 → 판독을 **한 스레드**로 합치면서, 아래 세 패턴이 전부 이 화면 안으로 들어왔습니다.

### 1-1. 단계별 상태 — GitHub Actions (Workflow visualization graph)

**패턴** — 하나의 큰 진행률 막대 대신 작업을 Job으로 나누고, 각 Job에 대기·진행·성공·실패 아이콘을 붙인다. 의존 관계는 선으로 잇는다.

**왜 맞는가** — 장면 찾기·번호판 판독·화면 시각 판독이 서로 다른 속도로 동시에 진행됩니다. 전체 실패와 번호판만 실패를 구분해야 합니다.

**바꾼 것**
- 그래프를 그리지 않았습니다. 사용자에게 중요한 단계만 **세로 스레드**로 쌓습니다. 의존 관계는 위아래 순서가 대신합니다.
- 실패에 빨강을 쓰지 않습니다. 「번호판은 직접 확인할 수 있어요」처럼 **영향과 다음 행동**을 같이 적습니다.
- 상태 점은 3종으로 줄였습니다 — 완료(초록) · 질문(오렌지) · 대기(회색 테두리).

### 1-2. 전체와 개별 분리 — GitLab CI (Pipeline jobs)

**패턴** — Pipeline 전체 상태와 개별 Job 상태를 분리한다. 일부가 실패해도 어느 단계인지 따로 보고, 실패한 것만 다시 돌린다.

**왜 맞는가** — 영상 12개 중 1개를 못 읽었다고 전체를 실패로 표시할 이유가 없습니다.

**바꾼 것**
- 개발자용 로그를 노출하지 않습니다. 「1개는 열 수 없었어요. **나머지 11개로 계속합니다**」처럼 결과 중심으로 적습니다.
- 재시도를 전면에 두지 않았습니다. 접힌 「어떤 영상인지」 안쪽으로 넣었습니다 — 자동 진행을 막지 않는 것이 우선입니다.

### 1-3. 닫아도 계속 — YouTube Studio (업로드 후 Checks)

**패턴** — 화면을 떠나도 서버에서 검사가 계속되고, 목록에서 상태 아이콘으로 알려준다.

**바꾼 것**
- **남은 시간을 숫자로 약속하지 않습니다.** 예측이 빗나가면 진행 표시 전체의 신뢰가 무너집니다. 대신 「영상 11개 확인 · 후보 3개」처럼 **무엇이 몇 개 끝났는지**를 셉니다.
- 「창을 닫아도 계속합니다」를 하단 고정 줄에 항상 둡니다.

## 2. 후보 비교

> 흐름이 바뀌면서 이 화면은 **기본 경로에서 빠졌습니다.** 스트림이 가장 유력한 후보를 자동 채택하고, 「다른 장면이었나요?」를 눌러야 열립니다. 아래 패턴들은 그대로 유효하되 **「고르는 화면」이 아니라 「바꾸는 화면」** 으로 읽어야 합니다.

### 2-1. 훑어보기와 견주기 — Adobe Bridge (Review Mode · Preview Panel)

**패턴** — Review Mode는 한 장씩 빠르게 넘기며 탈락시키고, Preview Panel은 고른 것들을 한 화면에서 비교한다. 두 동작을 별도 모드로 나눈다.

**왜 맞는가** — 「전체를 빠르게 훑기」와 「헷갈리는 둘을 집중 비교」는 다른 동작입니다.

**바꾼 것**
- 별도 페이지가 아니라 **한 화면 안의 탭**으로 만들었습니다 — `[모든 후보 3개] [2개 비교]`.
- 비교 모드에서 영상·시각·관찰·기억 단서를 **같은 행에 맞춰** 놓았습니다. 행이 어긋나면 비교가 성립하지 않습니다.
- 「다른 점만 보기」 토글을 더했습니다. Bridge에는 없지만, 항목이 많을 때 차이를 찾는 비용이 큽니다.

### 2-2. 상위 후보에 항상 접근 — Apple Photos (Burst 선택)

**패턴** — 큰 사진을 넘겨보면서도 아래 필름스트립에 전체와 선택 표시가 남는다.

**바꾼 것**
- 시간순 필름스트립이 아니라 **상위 3개 고정 선반**입니다.
- 순위를 「1위」라고 부르지 않습니다. 확정 판정처럼 읽히기 때문입니다 — 「지금 1등」처럼 **임시임이 드러나는 말**을 씁니다.
- ⚠️ 이 선반의 전제(무엇이 상위인가)가 계약에 없어 이슈 [#122](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/122)로 올렸습니다.

### 2-3. 맞는 근거와 어긋나는 근거 — Scite (Smart Citations) ★

**이 와이어프레임에서 가장 크게 쓴 패턴입니다.**

**패턴** — 인용을 「관련 있음」으로 뭉치지 않고 Supporting · Contrasting · Mentioning으로 나눈다. 반대 근거를 같은 수준으로 노출한다.

**왜 맞는가** — AI가 고른 후보를 **설득하는 화면이 아니라 사용자가 판단하는 화면**이어야 합니다. 맞는 항목만 보여주면 사용자는 비교가 아니라 승인을 하게 됩니다. `core-user-flow.md` §8-2도 「맞지 않는 관찰 근거를 감추지 않는다」를 명시합니다.

**바꾼 것**
- 연구용 용어를 일상어로 — **「기억과 맞아요」 · 「기억과 달라요」 · 「확인할 수 없어요」**
- **「달라요」에 빨강을 쓰지 않고 오렌지를 썼습니다.** 빨강이면 「이 후보 탈락」으로 읽히는데, 실제로는 「이 단서 하나가 어긋난다」일 뿐입니다. 이 제품에서 빨강은 후보에 쓰지 않습니다 — 쓰는 순간 대신고가 위반을 판정하는 제품이 됩니다.
- 기호는 `✓ / ≠ / ?` 세 개로 고정했습니다.

### 2-4. 아닌 것부터 지우기 — Adobe Bridge (Review Mode)

**패턴** — 아닌 이미지를 화면 아래로 밀어 현재 선택에서 뺀다. 남은 것으로 새 Collection을 만든다.

**왜 맞는가** — 처음부터 정답을 고르라고 요구하지 않고, 「이건 아니다」라는 쉬운 판단부터 하게 합니다.

**바꾼 것**
- **영구 삭제가 아닙니다.** 「제외한 후보 2개 보기」로 언제든 되돌립니다.
- ⚠️ **카드별 「아니에요」 버튼은 계약이 없습니다.** 지금 계약이 정의하는 「아니오」는 「조금 전/후예요」(고른 후보의 시간 보정)와 「다 아니에요」(전체 거절) 둘뿐이고, **개별 지목이 아닙니다.** 와이어프레임에는 그려 뒀지만 만들 수 없습니다 — 이슈 [#106](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/106) 참고.

### 2-5. 비슷한 후보 묶기 — Apple Photos (Duplicates)

**패턴** — 시각적으로 유사한 사진을 한 행으로 묶고 묶음 단위로 확인하게 한다.

**왜 맞는가** — 같은 차량이 몇 초 간격으로 찍힌 장면 10개를 후보 10개로 보여줄 이유가 없습니다.

**바꾼 것**
- **「중복」이라 부르지 않습니다.** 교통 영상 후보는 진짜 중복이 아닙니다 — 「같은 상황으로 보이는 장면」입니다.
- 묶은 기준을 보여주고 묶음 풀기를 제공해야 합니다.
- 📌 아직 와이어프레임에 없습니다. 후보가 여러 개인 실제 데이터가 확보되면 그립니다.

### 2-6. 겹친 마커 접기 — Figma (Comment cluster)

**패턴** — 축소했을 때 가까이 붙은 핀을 하나로 합치고 개수를 표시한다. 누르거나 확대하면 다시 나뉜다.

**왜 맞는가** — 공간은 2차원 캔버스지만 「좁은 영역에 마커가 겹친다」는 문제 구조가 영상 타임라인과 같습니다.

**바꾼 것**
- 확대 배율이 아니라 **시간 간격**으로 묶습니다 — 5초 안의 후보를 하나로 접고 개수를 적습니다.
- **마커 번호와 카드 번호를 같게** 했습니다. §8-2가 요구한 사항입니다 — 목록과 시간축을 눈으로 잇지 못하면 비교가 성립하지 않습니다.

## 3. 결과 없음

### 3-1. 다음 행동 제시 — Google Search (검색어 수정 안내)

**패턴** — 결과가 없을 때 검색이 고장 났다고 하지 않고 수정 방법을 제시한다.

**바꾼 것**
- 일반 도움말을 나열하지 않습니다. **「영상 12개는 정상적으로 모두 확인했습니다」를 초록 배지로 먼저 띄웁니다** — 「분석 실패」와 「분석했지만 후보가 없음」을 가르는 것이 이 화면의 전부입니다.

### 3-2. 조건을 하나씩 완화 — Airbnb (검색 필터)

**패턴** — 조건이 너무 좁을 때 특정 조건만 바꿔 다시 탐색하게 한다. 입력 전체를 버리지 않는다.

**바꾼 것**
- **AI가 자동으로 완화하지 않습니다.** 자동으로 넓히고 결과를 섞으면 사용자는 왜 이 후보가 나왔는지 모릅니다. 「아침 7시쯤 → 6~9시로 넓히기」처럼 **무엇을 바꾸는지 먼저 보여주고** 누르게 합니다.
- 기본 버튼은 「기억 단서 고치기」(`EDIT_HINT`), 보조가 「같은 조건으로 다시 찾기」(`RETRY_SEARCH`)입니다. 둘 다 계약에 등재돼 있습니다.

## 4. 확인 (어떻게 정했는지)

> 흐름이 바뀌면서 이 화면도 **「묻는 곳」에서 「펼쳐 보는 곳」** 으로 바뀌었습니다. 값은 이미 정해져 있고, 여기서는 근거를 보고 틀렸으면 되돌립니다.

### 4-1. 확신도가 다른 값 구분 — Azure Document Intelligence (Field confidence)

**패턴** — 추출한 필드마다 Confidence가 붙고, 낮은 필드는 사람 검토로 보낸다. 문서 전체 점수와 필드별 점수를 구분한다.

**왜 맞는가** — 번호판은 OCR이 읽었고 시각은 파일명에서 추정했고 위치는 사용자가 말한 것입니다. 한 화면에 출처와 확신도가 다른 값이 섞여 있습니다.

**바꾼 것**
- **숫자를 전면에서 뺐습니다.** `87%` · `62%`는 확률이고, 화면이 말해야 하는 건 「출처가 무엇이고 확정됐는가」입니다. 둘은 다른 개념이라 하나의 색으로 합치면 안 됩니다.
- 대신 **상태 배지 5종**을 씁니다 — 사용자 확인됨 / 출처 확인됨 / AI 추정 / 확인 필요 / 알 수 없음. 이건 `docs/modules/web/ux/value-state-display.md`가 이미 소유한 규칙입니다.

### 4-2. 값과 출처를 연결 — UiPath (Validation Station) ★

**패턴** — 추출된 필드와 원본 문서를 나란히 보여주고, 필드를 고르면 원본에서 그 값이 나온 영역을 연결한다. OCR Confidence와 Extraction Confidence를 따로 다룬다.

**왜 맞는가** — 「14:32」만 보여주면 그 값을 믿을지 알 수 없습니다.

**바꾼 것**
- 모든 수치를 노출하지 않고 **출처 두 개가 어긋날 때만** 나란히 놓습니다 — 파일명 `18:31:51` vs 영상 화면 `18:31:48`.
- **합치거나 평균내지 않습니다.** 어긋난 채로 두고 어느 쪽을 썼는지 적습니다.
- 흐름이 바뀌면서 여기서 **묻지 않게** 됐습니다. 「검증된 영상 화면 시각을 썼습니다」로 결과를 알리고, 되돌리기 버튼 하나만 둡니다.

### 4-3. 「알 수 없음」을 빈칸으로 두지 않기 — Azure DI (NULL 처리)

**패턴** — 값을 못 뽑은 경우를 빈 문자열로 보지 않고, 실제로 없는지 모델이 놓친 것인지 구분한다.

**왜 맞는가** — 빈 입력란은 「처리 중인지」·「AI가 못 읽었는지」·「원본에 없는지」를 구분해 주지 않습니다.

**바꾼 것**
- 내부 원인 코드를 그대로 내보내지 않고 **사람이 이해할 이유 + 해결 방법**으로 바꿉니다.
- 발생 장소가 그 예입니다 — 「영상에 위치 정보가 저장되어 있지 않고, 화면만으로는 어디인지 짚기 어렵습니다」 + 사용자가 말한 단서를 같이 보여주고, **여기서는 묻지 않고 안전신문고로 넘깁니다.**

---

## 5. 번호판 확인

> **이 화면만 자동화하지 않습니다.** 번호판이 틀리면 엉뚱한 차가 신고됩니다. 개입 최소화가 여기까지 오면 안 됩니다.

### 5-1. 맥락을 잃지 않는 확대 — Adobe Bridge (Loupe Tool)

**패턴** — 전체 이미지를 유지하면서 클릭한 부분만 확대경으로 키운다. 여러 이미지에서 확대경 위치를 동기화할 수도 있다.

**바꾼 것**
- 원본 프레임에 **번호판 영역을 초록 사각형으로 표시**해 어디를 보고 있는지 유지합니다.
- 확정하지 못한 자리를 **오렌지로 남깁니다** — 그럴듯한 값으로 채우지 않습니다.
- 프레임 넘겨보기는 **MVP 밖**으로 확정돼 있어 자리만 표시했습니다.
- ⚠️ **화면 전체가 계약 대기입니다.** `CaseView`에 번호판 프레임을 가리키는 필드가 없습니다 — 이슈 [#47](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/47).

## 6. 신고자료

### 6-1. 미완성 상태로 다음 단계 — YouTube Studio (Checks 진행 중 공개)

**패턴** — 검사가 안 끝났다는 상태를 유지하면서도 다음 단계로 갈 수 있게 하고, 기다려야 하는 이유를 같이 보여준다.

**바꾼 것**
- **「그래도 신고자료 받기」를 보조 버튼으로 내렸습니다.** YouTube는 「기다리기 권장」 정도지만, 신고는 행정적 결과가 생깁니다. 기본 버튼은 「확인 필요한 항목 보기」입니다.

### 6-2. 필수와 선택 분리 — DocuSign (Required and Optional Fields)

**패턴** — 필수 필드와 선택 필드를 시각적으로 구분하고, 선택 필드가 비어도 완료할 수 있게 한다.

**왜 맞는가** — 미확정 항목이 모두 같은 심각도를 갖지 않습니다.

**바꾼 것**
- **우리가 안전신문고의 실제 필수조건을 보장한다고 단정하지 않습니다.** 「현재 자료에서 확인 필요」와 「안전신문고에서 반드시 입력」을 따로 적습니다.
- 「대신고는 신고를 **대신 접수하지 않습니다**」를 버튼 아래 고정 문구로 둡니다.

## 쓰지 않기로 한 것

| 후보 | 왜 안 썼나 |
| --- | --- |
| Azure DI의 **Confidence 숫자 노출** | 확률과 「출처가 확인됐는가」는 다른 개념입니다. 일반 사용자에게 `62%`는 판단을 돕지 않고 책임만 떠넘깁니다. 필요하면 펼침 안쪽으로 |
| GitHub Actions의 **의존 그래프** | 사용자가 알아야 할 단계는 3~4개뿐입니다. 그래프는 과합니다 |
| 목업의 **가짜 도로 SVG 썸네일** | 실제와 무관한 그림이라 「썸네일이 된다」는 오해를 만듭니다. 「미리보기 준비 중」 자리표시자로 대체 |
| Airbnb의 **자동 조건 완화** | 자동으로 넓히면 왜 이 후보가 나왔는지 사용자가 추적할 수 없습니다 |
| **빨강**(후보·근거 불일치에) | 대신고가 위반을 판정하는 제품처럼 보입니다. 빨강은 쓰지 않습니다 |
