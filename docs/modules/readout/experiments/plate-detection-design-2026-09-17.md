## 1. 이 실험이 재는 것과 재지 않는 것

`ocr-baseline-2026-09-15`(AI Hub 번호판 crop 500장 + 영상 pilot)는 **인식**을 쟀다. 이 실험은
**검출**을 잰다. 두 숫자를 섞어 읽으면 안 된다.

| | 재나? | 근거 |
| --- | --- | --- |
| 번호판 영역 검출 위치·크기 | ✅ | 블러는 영역을 가릴 뿐 위치·크기는 보존한다 |
| `quality.plate_px_height` | ✅ | 같은 이유 |
| 연속 프레임 검출 지속성 | ✅ | 실제 영상이라 프레임 순서가 있다 |
| multi-frame consensus 성립 가능성 | ✅ | 한 인스턴스당 검출 프레임 수로 본다 |
| **`quality.sharpness`** | ❌ | **번호판 영역이 블러 처리되어 있다.** 측정되는 값은 원본 화질이 아니라 블러 커널 세기다 |
| 인식 정확도 · CER | ❌ | 읽을 글자가 없다 |
| 반사 · 각도 · 야간 영향 | ❌ | 블러가 표면 정보를 지웠다 |

> **이 실험 결과로 `sharpness` 기반 판정을 검증했다고 말하지 않는다.**
> `_best_index`를 `plate_px_height + sharpness`로 바꾸는 검토에서, 이 실험은 앞의 한 축만 뒷받침한다.

이 실험은 **정확도 목표치를 정하는 benchmark가 아니다.** 지금 코드에 근거 없이 잠정으로 박혀
있는 값(`MIN_PLATE_PX_HEIGHT = 20`, multi-frame 전제)이 실제 영상에서 말이 되는지 보는
기준선이다. 여기 숫자를 gate로 만들지 않는다.

## 2. 시작 전 반드시 확인할 것 — 정답지가 있는가

**이 설계 전체가 「블러 박스를 검출 정답지로 쓸 수 있다」는 전제 위에 있다.** 데이터를 받으면
가장 먼저 이것부터 확인한다.

> **결과: B도 아니고 「둘 다 아니다」였다.** 블러 박스는 물론 번호판 어노테이션 자체가 없었다.
> 위 폐기 블록 참조.

| 확인 | 결과가 A라면 | 결과가 B라면 |
| --- | --- | --- |
| 어노테이션에 번호판 영역 bbox가 있는가 | **A. 있다** → 그대로 GT로 쓴다. 추가 라벨링 0 | **B. 없다 (픽셀만 블러)** → 아래 대안으로 간다 |

### B일 때의 대안 (우선순위 순)

1. **차량 bbox가 있으면 그걸 쓴다.** 번호판 GT는 아니지만 「검출기가 엉뚱한 데를 잡았나」(오검출)는
   잴 수 있다. 커버리지는 못 잰다.
2. **블러 영역을 이미지 처리로 찾는다.** 블러 영역은 주변보다 고주파 성분이 급격히 낮다
   (Laplacian variance). 자동 추출 후 **육안으로 전수 검수**한다. 검수 안 한 자동 GT는 GT가 아니다.
3. **소규모 수동 라벨링.** 200~300 프레임만 손으로 박스를 친다. 표본은 작아지지만 GT가 확실하다.

**B로 확인되면 실험 범위를 줄이는 것도 정답이다.** 억지로 GT를 만들어 숫자를 내는 것보다,
「이 데이터셋으로는 오검출률만 잴 수 있다」고 기록하는 편이 낫다.

## 4. 지표 정의

매칭 기준은 **IoU ≥ 0.5** 하나로 고정한다. 바꾸면 그 사실을 결과에 적는다.

### ① 검출 커버리지 (Recall)

```
GT 박스 중 IoU ≥ 0.5로 매칭된 검출이 있는 것의 수
─────────────────────────────────────────────  = Coverage
                전체 GT 박스 수
```

「번호판이 화면에 있을 때 우리 검출기가 찾아내나」. 프레임 단위로 센다.

### ② 오검출 (Precision · FP)

```
Precision = TP / (TP + FP)
FP per frame = FP 총합 / 평가 프레임 수
```

**오검출은 커버리지보다 위험하다.** 엉뚱한 차의 번호판을 대상으로 잡으면 `target_association`
단계에서 못 걸러질 경우 전체 결과가 오답이 된다(Input Memo §1 「옆 차량 번호판을 읽으면 전체
결과가 오답」).

### ③ 검출 지속성 (연속성)

번호판 인스턴스 1건마다 다음을 센다.

| 값 | 정의 |
| --- | --- |
| `frames_visible` | GT 기준 그 번호판이 화면에 있는 프레임 수 |
| `frames_detected` | 그중 검출에 성공한 프레임 수 |
| `longest_run` | 끊기지 않고 연속 검출된 최장 구간 |
| `gaps` | 검출이 끊긴 횟수 |

**이 지표가 `tracker` 미결 항목에 답한다.** Input Memo가 *「실제 연속 영상이 없어 tracker 필요
여부는 미결」*로 남겨 둔 항목이다. `longest_run`이 길고 `gaps`가 적으면 tracker 없이 위치 근접
기반 묶기로 충분하다는 근거가 되고, 툭툭 끊기면 tracker가 필요하다는 근거가 된다.

### ④ `plate_px_height` 분포

검출된 박스 높이의 **p10 / 중앙값 / p90**, 그리고

```
plate_px_height < 20 인 검출의 비율
```

`api.py`의 `MIN_PLATE_PX_HEIGHT = 20`은 지금 **근거 없이 잠정으로 박힌 값**이다. 이 분포가 그
문턱이 말이 되는 숫자인지 처음으로 확인해 준다.

> **주의.** 2줄 번호판에서는 검출 박스가 아랫줄만 감싼다(`ocr-baseline-2026-09-15` §4-⑤).
> 1줄/2줄을 나눠서 분포를 낸다. 섞으면 이 지표는 의미를 잃는다.

### ⑤ multi-frame consensus 성립률

```
frames_detected ≥ 2 인 인스턴스 수
─────────────────────────────  = consensus 가능 비율
      전체 인스턴스 수
```

**지금 설계의 전제를 직접 검증하는 지표다.** `api.py`의 `_consensus_of`는 여러 프레임의
만장일치를 보고, `consensus.method`는 읽힌 프레임이 2장 이상일 때만 `MULTI_FRAME`이 된다.
실제 영상에서 한 번호판이 1프레임만 잡힌다면 **만장일치 합의라는 방어선 자체가 작동하지
않는다.** 그 경우 abstain 설계를 다시 봐야 한다.

## 6. 실행 절차

1. **§2 확인** — 어노테이션에 번호판 bbox가 있는가. 여기서 A/B가 갈리고 이후가 달라진다
2. GT 추출 → `instance_id` 부여 (같은 차량의 같은 번호판 = 같은 id)
3. 프레임 추출 (FPS 기록)
4. 검출기 실행 → 프레임별 박스 + confidence + 높이 저장
5. IoU 매칭 → ①②③④⑤ 계산
6. 결과 JSON + 위 표 + 한 문단 요약을 `plate-detection-<실행일>/`에 커밋

**`read_plate`를 부르지 않는다.** 이 실험은 검출 단계만 본다. 공개 함수는 인식·합의·보류까지
한 번에 도는데, 여기서는 그 앞단만 필요하다. `PaddleOcrProvider`가 준비되면 같은 데이터로
전 구간을 다시 돌려볼 수 있다.

## 8. 범위 밖

- **두 데이터셋 합성** — 번호판 crop을 블러 자리에 붙여 정답 있는 영상을 만드는 방안은 별도
  실험이다. 붙이는 코드·원근 처리·정답지 관리가 따로 필요하고, **합성 영상의 인식 수치는 실제보다
  낙관적으로 나온다**(모션 블러·압축 아티팩트·표면 반사·조명 불일치가 없다). 파이프라인 연결
  확인과 조건 통제 비교에는 쓸 수 있으나 제품 정확도로 보고하지 않는다.
- **인식 성능** — `ocr-baseline-2026-09-15`가 소유한다.
- **`sharpness` 검증** — §1 참조. 이 데이터로는 불가능하다.
