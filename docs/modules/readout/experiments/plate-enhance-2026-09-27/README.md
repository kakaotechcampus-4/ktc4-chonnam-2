# [readout] 번호판 crop 보정 — 확대·대비·선명화·다중 프레임 합성 (2026-09-27)

> 작성 신유민(`readout` Owner) · 입력은 `../paddleocr-real-video-2026-09-22.md`와 같은 프레임

**질문:** 대상 crop을 3배 확대만 하는 지금 방식에 보정을 더하면 한글까지 읽히나?

**답: 이 프레임에서는 아니다.** 10가지 모두 한글 `수`를 읽지 못했다. 원인은 화질이 아니라
**픽셀 수**다 — 원본에서 `수`는 높이 약 8px이고, 사람 눈에도 `÷`로 보인다. 보정은 있는 획을
또렷하게 할 뿐 없는 획을 만들지 않는다.

## 입력

| | |
| --- | --- |
| 프레임 | `20260810_183258_EVT_1.avi` · 10.013초 · 1920×1080 · 30fps |
| 수동 전체 번호판 bbox | `[618, 682, 105, 39]` — **원본 번호판은 105×39px** |
| crop | 번호판 둘레 25% 여백 → 157×91px |
| GT | `36수3105` |
| OCR | PaddleOCR 3.7 · PP-OCRv5 korean mobile (제품과 같다) |

| --- | --- | --- | ---: |

| 다중 프레임 합성 (±4프레임 ECC 정렬 평균) | 471×273 | `363105` | 0.998 |

| 합성 + CLAHE + unsharp | 471×273 | `36` · `3105` | 0.987 |

- **숫자 6자리는 CLAHE를 뺀 모든 보정에서 맞게 읽힌다.** 한글 자리만 전부 빠진다.
- **CLAHE는 해롭다** — 없는 `6`이 하나 생겼다. 대비를 올리면 압축 잡음도 글자처럼 보인다.
- **다중 프레임 합성은 conf만 올린다**(0.932 → 0.998). ±4프레임은 30fps에서 ±0.13초라 9장이 담은
  정보가 거의 겹친다 — 더 넓은 구간을 합치는 것은 따로 재야 한다.
- 3배 확대 시 번호판은 315×117px, 전체 crop은 471×273px이다.

## 하지 않은 것 — 초해상도(SR) 모델

Real-ESRGAN 같은 학습형 SR은 **없는 획을 그럴듯하게 그려 넣는다.** 번호판에서 그건 「값을
지어내는」 것이고, 틀린 한글이 높은 conf로 나오면 지금의 「한글 누락 → `PARTIAL_PLATE_READ`
보류」보다 나쁘다. 쓰려면 SR 결과를 판독 근거로 쓰지 않고 사용자 확인용 이미지로만 쓰는 선을
먼저 정해야 한다. [미결]

## 이 결과가 가리키는 곳

한글을 읽으려면 보정이 아니라 **번호판이 더 크게 찍힌 프레임**을 골라야 한다. 지금
`LocalVideoFrameSource`·`RecordingFrameSource`는 클립 길이의 30·50·70% 세 점만 본다. 번호판
높이가 가장 큰 프레임을 찾는 쪽이 다음 실험이다 — 단 프레임별 번호판 bbox GT가 먼저 있어야 한다
(`../two-line-merge-2026-09-23.md`의 같은 전제).

## 다시 돌리려면

```bash
D:/paddle-env/Scripts/python.exe plate_enhance.py <video> 10.013 618,682,105,39 36수3105 <out_dir>
```

**비교 이미지는 레포에 넣지 않았다** — 실제 차량 번호판이 찍힌 사진이다. `out_dir`에 다시 생긴다.
