## 0. 한 줄

1. **번호판 형식 검사 하나로 「틀린 값을 확정」이 0건이 됐다.** 어떤 전처리에서도. 못 읽는 번호판·
   오검출 4항목도 전부 보류로 떨어졌다.
2. **전처리(추적 7프레임 투표 · 기울기 보정 · 2줄 분할 · 대비 앙상블)는 정답 수를 늘리지 못했다.**
   전체 판독 7개 중 3개로 모든 방법이 같다.
3. **남은 실패는 한글 한 글자 누락이다** — 7개 중 4개. 숫자는 대체로 맞는다. 보정·합성·투표 어느
   쪽으로도 돌아오지 않았다. 딥리서치 정정 §4의 「recognition은 결국 학습이 필요할 수 있다」가
   **실제 블랙박스에서 처음 확인됐다.**
4. **2줄 번호판 윗줄은 나눠 읽어도 못 읽었다.**

## 1. GT를 어떻게 만들었나

| 단계 | 내용 |
| --- | --- |
| 후보 | 로컬 AVI 15개를 0.5초 간격으로 훑어 차량(yolo11n) → 차량 crop 안 번호판(KLPD ONNX) 검출. 번호판 비율 1.5~6 필터 · 높이 순 상위 6장 (`find_plates.py`) |
| 사람이 읽기 | 후보 crop을 확대·다중 프레임 합성·선명화·흑백 대비로 보여 주고(`enhance_sheets.py`, **생성형 복원 없음**) 사람이 보이는 만큼만 적었다. 못 읽은 자리는 `?` |
| 결과 | 14항목 — 전체 판독 7 · 부분 3 · 안 보임 3 · 번호판 아님 1. 검출 0건 영상 2개는 제외 |

**번호판 문자열은 이 문서와 [`results-masked.json`](results-masked.json)에서 끝 두 자리를 가렸다.**
실제 제3자 차량 번호다. 전체 GT와 crop 이미지는 레포 밖에 둔다.

**이 GT의 한계.** 한 사람이 한 번 읽었다. 2줄 번호판의 지역명 한 글자(「전남」의 「남」)는 사람이
상식으로 채운 값이다. 대상 차량이 아니라 **번호판이 가장 크게 잡힌 차**의 GT다 — association은
`../track-association-2026-09-27/`이 따로 잰다.

## 2. 방법 — 번호판 위치는 GT seed로 고정, 판독만 바꾼다

| | 방법 | 조사 ablation 대응 |
| --- | --- | --- |
| A | seed 프레임 1장 (지금 제품과 같은 단일 프레임) | A |
| B | CSRT로 ±1.5초 추적 → 7프레임 각각 OCR → 길이 다수결 후 자리별 conf 가중 투표 (과반 못 넘으면 `?`) | D |
| B+R | B + 기울기 보정(Hough 선 중앙값, ±15° 안) | C |
| B+RS | B+R + 가로/세로 < 2.6이면 위·아래를 나눠 윗줄은 2배로 따로 읽기 | C |
| B+RSV | B+RS + 원본·흑백 대비 두 전처리를 투표에 함께 | (E 대신) |

OCR은 전부 제품과 같은 PaddleOCR 3.7 · `korean_PP-OCRv5_mobile_rec`. 최종 판독은
`^(?:[가-힣]{2}\d{2}[가-힣]\d{4}|\d{2,3}[가-힣]\d{4})$`를 통과할 때만 낸다.

## 3. 결과 — [`results-masked.json`](results-masked.json)

| 방법 | 맞게 읽음 (전체 판독 7 중) | 틀린 값 확정 (14 중) |
| --- | ---: | ---: |
| A | 3 | **0** |
| B | 3 | **0** |
| B+R | 3 | **0** |
| B+RS | 3 | **0** |
| B+RSV | 2 | **0** |

맞힌 3개는 처음부터 A에서 읽히던 것이다(번호판 높이 39~58px, 정면·주간). B+RSV는 그중 하나를
`23?48**`로 흔들어 보류로 떨어뜨렸다 — 대비 전처리가 투표에 잡음을 넣는다.

### 실패의 모양

| `36수31**` | `3631**` (전 방법) | 한글 |

한글 누락은 전처리를 바꿔도 자리 그대로다. **입력 품질보다 인식기 쪽 한계로 읽힌다** — 같은
PaddleOCR이 AI Hub 172 근접 crop에서도 CER 55.3%였고, 같은 데이터로 학습한 모델은 0.76%였다
(딥리서치 정정 §4).

## 4. 이 결과로 정하는 것 · 정하지 않는 것

**정한다 — 형식 검사는 전처리와 무관하게 판독 경로에 필요하다.** 지금 `api.py._abstain_reason`은
형식 전체를 보지 않고 두 경우만 거른다 — 한글이 아예 없으면 `OCR_LOW_CONFIDENCE`, 「한글 1자 +
숫자 4자」면 `PARTIAL_PLATE_READ`. 그래서 한글은 있지만 자리 수가 틀린 판독(`12가345` 같은)은
`status=OK`로 나갈 수 있다. 어디에 어떤 이유 코드로 넣을지는 구현 PR에서 정한다.

> 🚨 **이 실험 중 발견 — `PARTIAL_PLATE_READ`가 develop에서 동작하지 않는다.**
> `api.py:335-336`의 정규식이 raw string 안에 `\\`를 써서(`r"[가-힣]\\d{4}"`) 「백슬래시 문자 + d×4」를
> 찾는다. `바5215`가 보류되지 않고 `status=OK`로 확정된다.
> `tests/readout/test_target_crop.py::test_two_line_lower_row_is_partial_not_an_accepted_plate`가
> develop(`742ca89`)에서 **실패한다**(`assert 'OK' == 'NEEDS_REVIEW'`). 수정은 별도 PR.

**정하지 않는다.**
- **파인튜닝을 시작하지 않는다.** 게이트 6개 중 「특정 한국 문자 혼동이 반복적·체계적」의 근거가
  생겼을 뿐이고, 「대상 차량 association 안정」은 아직 아니다(`../track-association-2026-09-27/`
  47.9%). [미결]
- **B(다중 프레임 투표)를 버리지 않는다.** 이 7개에서 이득이 0인 것은 틀리는 방식이 프레임마다
  **같기** 때문이다. 우연히 틀리는 오류에는 여전히 맞는 도구다.

## 5. ablation F — EasyOCR 1.7.2 (`korean_g2`)와 비교 (2026-09-28)

입력(추적 · crop · 기울기 보정 · 2줄 분할)은 위와 같고 인식기만 바꿨다(`easy_eval.py`).
EasyOCR은 **허용 글자 제한**(숫자 + 번호판에 쓰이는 한글)을 줄 수 있어 그 조건도 넣었다.

| 인식기 · 방법 | 맞게 읽음 (전체 판독 7 중) | 틀린 값 확정 (14 중) |
| --- | ---: | ---: |
| PaddleOCR `B+RS` (위 최고) | 3 | 0 |
| EasyOCR 1장 | 0 | **1** |
| EasyOCR + 허용 글자 제한 | 0 | **1** |
| EasyOCR + 허용 글자 + 7프레임 투표 · 보정 · 분할 | 1 | 0 |

- **EasyOCR이 전 조건에서 PaddleOCR보다 나쁘다.** 게다가 `23두48**`를 `23두40**`로 형식까지 맞춰
  **확정했다** — 형식 검사로도 못 막는 오답이다. 앙상블(ablation F)에 넣으면 오답 확정만 늘린다.
- **한글 누락은 EasyOCR도 같다**(`36수31**` → `3641**`). 범용 OCR 두 개가 같은 자리에서 실패하므로
  「PaddleOCR만의 문제」가 아니라 **범용 인식기 + 이 해상도의 한계**로 본다. 남은 길은 번호판 전용
  학습 인식기이고, 그건 §4의 파인튜닝 게이트를 거친다.
- **7프레임 투표는 EasyOCR에서는 효과가 있었다**(0 → 1, 오답 확정 1 → 0). 프레임마다 틀리는 방식이
  달라 투표가 걸러 낸 것이다 — §4 「B를 버리지 않는다」의 근거.
