## 0. 한 줄

1. **번호판 형식 검사 하나로 PaddleOCR의 「틀린 값 확정」이 27항목 전체에서 0건이다.** 어떤 전처리에서도.
   못 읽는 번호판·오검출 8항목도 전부 보류로 떨어졌다. **단, 추적 검증을 붙이자 한글을 다른 한글로 읽은
   오답 1건이 형식을 통과해 확정됐다**(§3-⑥) — 0건은 한글을 **빠뜨려서** 형식에 걸린 덕이 크다.
2. **전처리(추적 7프레임 투표 · 기울기 보정 · 2줄 분할 · 대비 앙상블)는 정답 수를 늘리지 못했다.**
   전체 판독 13개 중 4개로 방법 간 차이가 없다(대비 앙상블만 3개로 떨어진다).
3. **남은 실패의 대부분은 한글 한 글자다 — 틀린 9개 중 7개.** 빠지거나 숫자로 바뀐다. **번호판 높이
   112px에서도 같다.** 해상도가 아니라 인식기 한계다.
4. **EasyOCR이 전 조건에서 더 나쁘고, 형식까지 맞춘 오답을 확정한다.** 앙상블 후보가 아니다.
5. **2줄 번호판 윗줄은 나눠 읽어도 못 읽었다.** CSRT 추적은 편집된 클립에서 튄다.
6. **번호판 전용 학습 인식기는 한글을 읽는다 — 대신 못 읽는 번호판에도 번호를 지어낸다**(§3-⑤). 1장
   7/13 · 오답 확정 9. 「1장 = 7프레임 투표」일 때만 확정하면 5/13 · 오답 확정 0.
7. **추적한 프레임마다 번호판을 다시 검출하면 전용 인식기가 7/13 · 오답 확정 0이 된다**(§3-⑥). 조건은
   「1장 = 투표」에 **검증된 프레임 3장 이상**을 더한 것. PaddleOCR은 추적 검증으로 나아지지 않는다.

## 1. GT를 어떻게 만들었나

| 단계 | 내용 |
| --- | --- |
| 후보 | 로컬 영상 18개를 0.5초 간격으로 훑어 차량(yolo11n) → 차량 crop 안 번호판(KLPD ONNX) 검출. 번호판 비율 1.5~6 필터 (`find_plates.py`) |
| 차별 묶기 | 60초 영상은 한 차가 후보를 독차지해서, 후보를 번호판 트랙(= 차 한 대)으로 묶고 트랙마다 가장 큰 한 장을 고른다. 화면 맨 아래 띠(세로 88% 아래)는 블랙박스 시각 overlay 자리라 뺀다 — `MDR` 영상에서 overlay 글자가 번호판으로 12장 중 10장 검출됐다 (`group_tracks.py`) |
| 사람이 읽기 | 후보 crop을 확대·다중 프레임 합성·선명화·흑백 대비로 보여 주고(`enhance_sheets.py`, **생성형 복원 없음**) 사람이 보이는 만큼만 적었다. 못 읽은 자리는 `?` |
| 결과 | **27항목 — 전체 판독 13 · 부분 6 · 안 보임 6 · 번호판 아님 2** |

**번호판 문자열은 이 문서와 결과 JSON에서 끝 두 자리를 가렸다.** 실제 제3자 차량 번호다. 전체 GT와 crop
이미지는 레포 밖에 둔다.

**이 GT의 한계.**
- 한 사람이 한 번 읽었다.
- 전체 판독 13개는 **차 11대**다 — 두 대는 조건이 다른 두 장면(정차/출발 후 기울어짐, 44px/63px)을 따로
  넣었다.
- 2줄 번호판의 지역명 한 글자(「전남」의 「남」)는 사람이 상식으로 채운 값이다.
- 사람이 「예측해서 생각할 수 있다」고 한 번호(`174?5???`)는 정답으로 쓰지 않고 「안 보임」으로 분류했다.
- 대상 차량이 아니라 **번호판이 잡힌 차**의 GT다 — association은 `../track-association-2026-09-27/`이 잰다.

## 2. 방법 — 번호판 위치는 GT seed로 고정, 판독만 바꾼다

| | 방법 | 조사 ablation 대응 |
| --- | --- | --- |
| A | seed 프레임 1장 (지금 제품과 같은 단일 프레임) | A |
| B | CSRT로 ±1.5초 추적 → 7프레임 각각 OCR → 길이 다수결 후 자리별 conf 가중 투표 (과반 못 넘으면 `?`) | D |
| B+R | B + 기울기 보정(Hough 선 중앙값, ±15° 안) | C |
| B+RS | B+R + 가로/세로 < 2.6이면 위·아래를 나눠 윗줄은 2배로 따로 읽기 | C |
| B+RSV | B+RS + 원본·흑백 대비 두 전처리를 투표에 함께 | (E 대신) |
| E · EL · ELB | EasyOCR 1.7.2 `korean_g2` — 1장 / + 허용 글자 제한 / + B+RS와 같은 입력 | F |

PaddleOCR은 제품과 같은 3.7 · `korean_PP-OCRv5_mobile_rec`. 최종 판독은
`^(?:[가-힣]{2}\d{2}[가-힣]\d{4}|\d{2,3}[가-힣]\d{4})$`를 통과할 때만 낸다.

### ② 실패의 모양 — 한글이 크기와 무관하게 틀린다

그 설명은 틀렸다.** 인식기가 번호판 용도 기호 자리를 학습하지 않은 것으로 본다 — 같은 PaddleOCR이 AI Hub
172 근접 crop에서도 CER 55.3%였고, 같은 데이터로 학습한 모델은 0.76%였다(딥리서치 정정 §4).

### ③ EasyOCR

- **전 조건에서 PaddleOCR보다 나쁘다.** 게다가 `23두48**`를 `23두40**`로 형식까지 맞춰 **확정했다** —
  형식 검사로도 못 막는 오답이다. 앙상블(ablation F)에 넣으면 오답 확정만 늘린다.
- **한글 누락은 EasyOCR도 같다**(`36수31**` → `3641**`). 범용 인식기 두 개가 같은 자리에서 실패한다.
- **7프레임 투표는 EasyOCR에서는 효과가 있었다**(1 → 2, 오답 확정 1 → 0). 프레임마다 틀리는 방식이 달라
  투표가 걸러 냈다. PaddleOCR은 매 프레임 **똑같이** 틀려서 투표가 할 일이 없다.

### ④ 추적이 튄다

`youtube_clip_01`(편집된 짧은 클립)에서 CSRT 추적 박스가 seed `(1202, 880)`에서 `(765, 579)` ·
`(1700, 579)`로 옮겨 가, B 계열이 단일 프레임 A보다 나빴다. 추적한 프레임을 번호판 검출로 다시 확인하지 않으면
투표에 다른 영역이 섞인다.

### ⑤ 번호판 전용 학습 인식기 — 한글은 읽지만 지어낸다 (2026-09-28)

**왜 했나.** ②에서 범용 인식기 두 개가 크기와 무관하게 한글 자리를 틀렸다. 조사
(`../../research/korean-plate-hangul-recognition-2026-09-28.md`)는 한글 자리를 푼 사례가 전부 **번호판 전용
학습**이라고 했다. 그 주장을 우리 블랙박스에서 가장 싸게 확인하는 방법이 이미 로컬에 있는 전용 인식기를
돌려 보는 것이었다.

**무엇을.** `gyupro/EasyKoreanLpDetector`의 인식기 `best_acc`(EasyOCR 구조 VGG+BiLSTM+CTC, README 서술로는
AI Hub 172 번호판 약 8만 장으로 학습). 원본 앱과 같은 입력 — 여백 없는 번호판 crop → 224×128 → 흑백
(`ekld_eval.py`). **라이선스가 명시되지 않은 가중치라 평가에만 썼다.** 결과는
[`ekld-results-masked.json`](ekld-results-masked.json).

| 규칙 | 맞게 읽음 (13 중) | 틀린 값 확정 (27 중) |
| --- | ---: | ---: |
| PaddleOCR `B+RS` (기준) | 4 | 0 |
| 전용 인식기 1장 (`K1`) | **7** | **9** 🚨 |
| 전용 인식기 7프레임 투표 (`K2`) | 5 | 1 |
| `K1` 확신도 ≥ 0.85만 | 6 | 2 |
| **`K1` = `K2`일 때만 확정** | **5** | **0** |

**결과 1 — 한글 자리가 풀린다.** PaddleOCR이 숫자로 바꾸던 `36수31**` · `200허11**`(44px·63px 둘 다) ·
`125호11**`를 한글까지 맞게 읽었다. 「한글은 전용 학습으로 풀린다」가 우리 영상에서 처음 실측됐다.

**결과 2 — 대신 지어낸다.** 사람이 「안 보임」으로 적은 번호판에도 `49서95**`처럼 형식에 맞는 번호를 낸다.
틀린 확정 9건 중 **확신도 0.97 · 0.995짜리가 있다**(`05도32**` → `25도32**`, `340?23**` → `10부23**`).
**형식 검사도 확신도도 이 모델의 오답을 막지 못한다** — 전용 모델은 무엇을 보든 번호판 모양의 답을 낸다.

**결과 3 — 프레임 간 일치가 거른다.** 1장 결과와 7프레임 투표가 같을 때만 확정하면 오답 확정이 0이 되고,
PaddleOCR보다 1개 더 맞힌다. 지어낸 번호는 프레임마다 다르게 지어내기 때문이다. `125호11**`는 1장에서는
맞았지만 추적이 튀어(④) 투표가 달라져 보류로 떨어졌다 — 추적 검증이 붙으면 올라갈 여지가 있다.

**이 결과로 하지 않는 것.** 이 가중치를 제품에 넣지 않는다(라이선스 미명시). 확인한 것은 **방향** —
「번호판 전용 학습 + 프레임 간 일치 조건」이다.

### ⑥ 추적 검증 — 추적한 프레임마다 번호판을 다시 검출한다 (2026-09-28)

**왜 했나.** ④에서 CSRT가 튀어 투표에 다른 영역이 섞였고, ⑤의 `125호11**`가 그 때문에 보류로 떨어졌다.
프레임 간 일치를 확정 조건으로 쓰려면 투표에 들어가는 프레임이 **같은 번호판**이어야 한다.

**무엇을.** `verify_tracks.py` — 추적 구간(±1.5초, 3프레임 간격)의 각 프레임에서 `find_plates.py`와 같은 순서로
번호판을 검출하고, 조건을 통과한 **검출 박스**만 투표에 넘긴다. 두 방식을 비교했다.

| 방식 | 받는 조건 |
| --- | --- |
| CSRT+검증 | 추적 박스와 IoU ≥ 0.3 **그리고** 직전에 받은 박스에서 중심 이동 ≤ 그 박스 가로 1배 |
| 검출 체인 (`CHAIN=1`) | CSRT 없이, 직전 박스와 가로 크기 0.5~2배 **그리고** 중심 이동 ≤ 가로 1배 |

- **번호판 검출은 차량 crop 안에서 해야 한다.** 번호판 둘레 창만 잘라 검출하면 seed 프레임에서도 27개 중
  6~7개를 놓쳤다. 차량 crop에서는 차량 기록이 있는 seed 26개를 모두 다시 찾았다(IoU ≥ 0.92).
- **CSRT는 대부분 몇 프레임 만에 번호판을 놓친다.** 떨어진 프레임을 눈으로 보면 추적 박스가 가드레일 ·
  도로 · 다른 차 위에 있다 — 검증이 버린 것은 실제로 틀린 프레임이다.

결과는 [`ekld-results-verified-masked.json`](ekld-results-verified-masked.json) ·
[`ekld-results-chain-masked.json`](ekld-results-chain-masked.json) ·
[`results-verified-masked.json`](results-verified-masked.json) · [`results-chain-masked.json`](results-chain-masked.json).

| 인식기 · 규칙 | 기준 (CSRT) | CSRT+검증 | 검출 체인 |
| --- | ---: | ---: | ---: |
| 전용 `K1` 1장 | 7 · 9 | 7 · 9 | 7 · 9 |
| 전용 `K2` 투표 | 5 · 1 | 7 · 4 | 7 · 3 |
| 전용 `K1` = `K2` | 5 · 0 | 7 · 3 | 7 · 2 |
| **전용 `K1` = `K2` · 검증된 프레임 ≥ 3** | — | **7 · 0** | **7 · 0** |
| PaddleOCR `B+RS` | 4 · 0 | 4 · **1** | 3 · 0 |

칸은 「맞게 읽음 (13 중) · 틀린 값 확정 (27 중)」.

**결과 1 — 전용 인식기는 추적 검증으로 5 → 7, 오답 확정 0을 지킨다.** 새로 확정된 것은 `125호11**`(추적 튐이
원인이던 것)와 44px `200허11**`다.

**결과 2 — 검증된 프레임이 1장이면 일치 조건이 아무것도 거르지 못한다.** 검증 후 seed 한 장만 남으면 투표 =
1장이라 `K1` = `K2`가 저절로 성립한다. 그렇게 새어 나간 오답이 3건(`51두21**` 등)이다. 「3장 이상」은 결과를 본 뒤
정한 값이지만 근거는 「1장은 투표가 아니다」이고, 2장 이상 중 가장 작은 홀수다. GT 13개에 맞춰졌을 수 있다.

**결과 3 — PaddleOCR은 나아지지 않고, 한글을 다른 한글로 읽은 오답이 처음 확정됐다.** CSRT+검증에서
`36수31**`를 `36주31**`로 확정했다 — 형식에 맞아서 형식 검사로 못 막는다. 기준에서 PaddleOCR 오답 확정이 0이었던
것은 한글을 **빠뜨려** 형식에 걸린 덕이 크고, 프레임이 같은 번호판으로 모이자 틀린 한글도 투표를 통과했다.

**결과 4 — 두 방식은 결정적 차이가 없다.** 검출 체인이 대부분 비슷하거나 더 많은 프레임을 남기지만 확정
결과는 같다. 2줄 `전남82바52**`는 두 방식 모두 어느 인식기로도 못 읽었다(검출 체인에서 전용 인식기가 7장 모두
같은 오답에 투표했고, 1장 판독과 달라 확정되지는 않았다).

## 4. 이 결과로 정하는 것 · 정하지 않는 것

**정한다 — 형식 검사는 전처리와 무관하게 판독 경로에 필요하다.** 지금 `api.py._abstain_reason`은
형식 전체를 보지 않고 두 경우만 거른다 — 한글이 아예 없으면 `OCR_LOW_CONFIDENCE`, 「한글 1자 +
숫자 4자」면 `PARTIAL_PLATE_READ`. 그래서 한글은 있지만 자리 수가 틀린 판독(`12가345` 같은)은
`status=OK`로 나갈 수 있다. 어디에 어떤 이유 코드로 넣을지는 구현 PR에서 정한다. **형식 검사는 한글을 다른
한글로 읽은 오답은 못 막는다**(§3-⑥ 결과 3) — 자리 수·구조 오류용이다.
