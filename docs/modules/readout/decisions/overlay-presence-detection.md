# intake overlay 존재 탐지 — 방향 확정, 세부 미결

> **Owner:** 신유민 (`readout`) · 방향 확인 완료
> **이 문서는 미결 기록이다.** 아래 「미결」은 실제 블랙박스 샘플로 검증한 뒤 **Owner가 Technical Spec에서 확정한다.** 지금 채우지 않는다.
> 관련: `architecture/module-architecture.md` §7-1(Happy Path) · §7-2 · `product/core-user-flow.md` §5

## 확정된 것 — 방향

업로드 직후(intake)에 **overlay timestamp의 존재 여부만** 저비용으로 탐지한다. **시각 값 OCR은 하지 않는다.** 실제 값 판독은 §7-2대로 사건 선택 이후에 수행한다.

앞부분 프레임 샘플링으로 「있음/없음」만 판단한다.

**왜 필요한가:** 화면(`core-user-flow.md` §5)이 업로드 직후에 「이 영상에 화면 시각이 찍혀 있는지」를 알려준다. GPS 없음을 마지막 handoff에서 처음 알게 하지 말라는 원칙과 같은 이유다 — 시각도 마지막에 알게 하면 안 된다.

## 미결 — Technical Spec에서 확정

| # | 항목 | 왜 지금 못 정하나 |
| --- | --- | --- |
| 1 | 필요한 **프레임 수**와 샘플링 위치 | 실측 없음 |
| 2 | **ROI** (화면 어느 영역을 보는가) | 제조사별 layout 차이를 실제 샘플로 확인해야 한다 |
| 3 | **오판율** — 있는데 없다고 / 없는데 있다고 | 측정 안 됨 |
| 4 | **「overlay 없음」과 「탐지 실패」를 구분하는 방법** | 아래 참조 |

### 4번이 왜 중요한가

화면에 쓰는 문구가 달라진다. 「화면에 시각이 없습니다」는 **사실**이고, 그러면 사용자는 화면을 다시 보지 않고 파일 기록으로 계산한 시각을 받는다(`core-user-flow.md` §13). 「확인하지 못했습니다」는 **모른다는 뜻**이고 §3-1의 `알 수 없음(UNKNOWN)`이다.

**둘을 하나로 합쳐 「없음」으로 표시하면 안 된다** — 없다고 하면 사용자가 확인할 기회를 잃는다. 그래서 이 구분은 readout 내부 최적화가 아니라 **화면 문구를 결정하는 항목**이다.

## 실측 1건 (2026-09-19) — 미결을 닫지 않는다

블랙박스 영상 1개에 실제로 OCR을 돌렸다. **표본이 영상 1개·제조사 1종·프레임 1장이므로
위 미결 중 어느 것도 닫지 않는다.** 아래는 그 실측이 미결에 **더한 제약**이다.

대상 `20260810_175721_EVT_1` @14.76s · `PP-OCRv5_mobile_det` + `korean_PP-OCRv5_mobile_rec` ·
보조 전처리 3종 off. OCR이 conf 0.9724로 돌려준 한 줄은 이것이다.

```
2026/08/10 17:57:36 13.20 ×:+0.020 Y:-0.043 2:-0.012
└─── 시각 ───┘ └속도┘ └───── G센서 ─────┘
```

### 미결 #2(ROI)에 더하는 제약 — ROI로는 못 자른다

시각·속도·G센서가 **하나의 텍스트 줄**로 나온다. ROI를 아무리 좁혀도 **한 줄 안에서는
잘리지 않는다** — 줄 전체가 걸리거나 글자가 잘려 못 읽히거나 둘 중 하나다. 따라서
「시각만 남기는 일」은 ROI 설계가 아니라 **문자열 해석 단계의 몫**이다.

ROI가 필요 없다는 뜻은 아니다. 화면 어느 영역을 볼지는 여전히 미결이고, 이 실측은
**「ROI만으로 충분하다」를 배제**했을 뿐이다.

### 미결 #3(오판율)에 더하는 것 — 오판 1건, 다만 탐지 오판이 아니다

이 영상은 시각이 또렷하게 찍혀 있고 잘 읽혔는데도 구현이 「읽었지만 못 알아봄」
(`readout.overlay.ocr_failed`)으로 분류했다. 원문 전체를 `strptime`에 넣고 있었기 때문이다.

**이것을 오판율 수치로 세지 않는다.** 원인이 탐지 성능이 아니라 해석 단계의 구현 결함이고,
그 결함은 고쳤다(`_parse_overlay_text`). 미결 #3이 재려는 「있는데 없다고 / 없는데 있다고」는
여전히 측정 전이다. 여기 남기는 이유는 **fixture가 통과시킨 결함이 실물에서 드러난 경로**를
기록해 두기 위해서다 — mock의 `raw_text`는 전부 깨끗한 시각 문자열이라 이 갈래가 없었다.

### 표본의 한계

- **영상 1개 · 제조사 1종.** 다른 기종이 시각을 어떻게 배치하는지 모른다
- **프레임 1장.** 같은 영상 안에서도 줄 구성이 흔들리는지 보지 않았다
- 이 영상은 **dev set**이다(`experiments/ocr-baseline-2026-09-15/`에서 이미 썼다). 여기서
  나온 수치를 성능으로 보고하지 않는다

### 여기서 파생된 계약 공백

계약 §7 예시의 `raw_text`는 전부 `"2026-09-02 18:31:12"` 같은 **순수 시각 문자열**이다.
`raw_text`가 순수 시각인지 OCR이 준 **줄 전체**인지 계약이 말하지 않는다. 현재 구현은
후자를 전제한다. 계약 문구는 이 문서가 정하지 않는다 — 별도 항목이다.

## 현재 자료 상태

`research/architecture-input-memo.md`에 timestamp OCR 설계 근거는 있으나, **업로드 직후 존재 탐지에 필요한 프레임 수·ROI·오판율 실험은 없다.** 실제 블랙박스 샘플 확보 후 측정한다. 위 실측 1건은 그 실험이 아니다 — 사건 선택 **이후**의 값 판독 경로에서 나왔다.
