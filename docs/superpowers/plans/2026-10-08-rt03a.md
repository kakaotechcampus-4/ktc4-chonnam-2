# RT-03(a) 구현 계획

> 사용자가 요청한 `feature/runtime-job-execution` 브랜치에서 직접 실행한다. 커밋·푸시는 하지 않는다.

**목표:** 관련 이슈 #290(RT-03(a)): Runtime 스키마, 호출자 소유의 enqueue, 계약 조회 포트.

**구조:** SQLAlchemy Core Connection은 호출자의 트랜잭션에 참여한다. 고정된 Alembic 리비전이 물리 테이블을 관리하고, 조회 포트는 JobExecution v1.1 필드를 명시적으로 투영한다. 모듈 간 FK나 usage_refs 저장은 추가하지 않는다.

**명세:** `docs/runtime/runtime-implementation-plan.md` §6 RT-03, §9, §12; 기술 명세 §4.2–4.5, §6.3, §12.1, §12.4; JobExecution 계약 §4–6, §9.

**제약:** 사용자 변경과 recording-baseline-negative-001.json을 보존한다. claim/finish/Worker/heartbeat/cancel/retry/usage/HTTP 작업은 제외한다. 로그 상태는 IN_PROGRESS를 유지한다. 계약·결정·기준선은 변경하지 않는다. 실제 MySQL 8.4를 사용하고 MySQL 대상의 skip과 xfail은 각각 0이어야 한다.

## 작업 1: 스키마와 enqueue

- [x] `tests/common/jobs/test_repository_mysql.py`에 운영 migration, 호출자 가시성·rollback·commit, `(job_id, attempt)` 고유성, 일괄 처리 원자성, 대소문자를 구분하는 ID, 미등록 kind와 빈 입력의 실제 MySQL 시험을 추가한다.
- [x] `common/jobs/schema.py`, `repository.py`, `__init__.py`, `migrations/runtime/versions/0001_job_execution.py` 추가 전에 실패를 확인한다.
- [x] `enqueue(conn, job_records, trace_id) -> list[str]`를 구현한다. SQL 실행 전에 사용하는 메타데이터를 검증하고, 호출자의 활성 트랜잭션을 요구한다. 실행 ID는 Runtime이 생성하고 attempt 1은 QUEUED로 시작한다. DB UTC 마이크로초 시각을 사용하며 commit/rollback이나 재시도는 하지 않는다.
- [x] 기존 인수 검사를 보존하면서 RT-02(b)의 migration 기대값을 첫 Runtime 리비전에 맞춘다.
- [x] 대상 시험이 통과하는지 확인한다.

- [x] 실패를 확인한 뒤 `common/jobs/read_port.py`에 `read_executions(conn, job_ids) -> list[dict]`를 구현한다. 모든 attempt를 job_id/attempt 순서로 반환하고, JSON 호환 계약 필드와 usage_refs=[]를 사용한다.
- [x] 기존 JobExecution/CommonFixture 검증기로 출력을 검증한다. Case import나 변경은 하지 않는다.

## 작업 3: 검증과 인계

- [x] DAESINGO_REQUIRE_MYSQL=1과 JSON/JUnit MySQL 증거를 사용해 전체 pytest를 확인한다. 기존 MySQL 보고서 gate, 경계 검사, 계약 fixture 검증기와 diff 검사를 실행한다.
- [x] 최종 diff에서 트랜잭션 소유권, 스키마·메타데이터 일치, 내부 필드 투영, 식별자 처리와 migration의 전진 전용 동작을 확인한다.
- [x] 구현 로그와 common README에 범위·상세·실패→통과 증거·계획 차이·남은 위험·관련 이슈 #290을 기록한다. IN_PROGRESS를 유지한다.
- [x] 커밋·푸시·이슈 종료 없이 변경 파일과 실제 결과를 보고한다.

검토 중점: 일괄 쓰기 전 잘못된 메타데이터 거부, 중복 일괄 처리의 원자성, 호출자 rollback 후 새 관측자에게 행이 남지 않음, 대소문자가 정확히 구분되는 식별자, 서버·세션 시간대에 의존하지 않는 DATETIME(6) UTC 저장, Runtime이 대표 실행을 선택하지 않고 모든 attempt 반환.

검증: 스키마/enqueue 15개, 조회 포트 10개, gate 누락 5개, Case 식별자 호환성 2개에서 실패→통과를 확인했다. 최종 전체 pytest는 2230 passed / 26 skipped, 실제 MySQL은 93개·skip 0·xfail 0이며 경계·계약·diff 검사는 PASS다. 최초 일회성 migration 실패 원인은 미확정으로 구현 로그에 기록했다. 커밋·푸시·이슈 종료는 하지 않았다.
