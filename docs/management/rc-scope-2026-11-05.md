## 1. RC 판정 원칙

- **P0/RC 차단:** 사용자 핵심 경로를 막거나 신고자료의 정확성을 훼손하는 결함. **#583은 수정·회귀 검증 완료 전 정상 RC 수락 차단**이다. 해결하지 못한 채 수락하려면 PM이 **별도로 명시적 예외 승인**하고 사유·영향·우회·남은 위험을 기록해야 한다. 시간이 지났다는 이유만으로 Known Issue로 자동 전환하지 않는다.
- **RC 포함:** 기능은 반영하되 Owner 리뷰, 실제 경로 회귀, 필요한 배포 smoke를 마쳐야 완료다. 판정이 '포함'이어도 현재 PR이 미병합이면 아직 미완료다.
- **조건부 포함:** 검증이 통과한 경우에만 켠다. 안전성·일정상 부담이 크면 **기존 핵심 동작을 유지하는 대체 경로**로 마무리하고 추가 기능은 후속으로 넘긴다.
- **제외:** 이번 RC에서 새로 구현하거나 일반 공개 지원으로 약속하지 않는다. 이미 있는 정상 기능이나 제품의 장기 목표를 삭제한다는 뜻은 아니다.
- **시연 가치보다 정확성 우선:** 화면에서 보이는 기능이라도 허위 성공·불확실한 위치·시간·번호판·완료 상태를 확정 표시하지 않는다.

## 3. 사용자 공개 길이와 장시간 실험은 서로 다른 수용 게이트

- **현재 외부 사용자 입력 정책:** 단일 또는 여러 파일의 **합산 영상 길이 최대 10분을 목표**로 삼되 아직 10분을 보장하지 않는다. 배포 환경에서 실제 업로드→Recording→Coarse/Fine→Case 후보/수정→Package READY→신고용 영상 다운로드·확인까지 **10분 E2E**를 통과하면 허용한다. 미달하면 검증된 더 짧은 길이·용량·형식만 공개한다. 다중 파일은 [Case START_ANALYSIS 결정](../modules/case/decisions/start-analysis.md) §3-1의 순서·연속성·스트림 조건을 따른다.
- **#452 통제된 26분 기술 검증:** [PR #566](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/pull/566) → [#572](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/pull/572) → [#582](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/pull/582) 조건으로 실제 E2E를 수행한다. 성공하면 해당 환경·입력의 기술 근거, 실패하면 입력 토큰 수용·출력 잘림/종료 사유·후반부 후보 누락·비용·단계별 시간 등 한계의 근거로 기록한다. 이 **26분 검증 결과만으로 26분 사용자 업로드를 허용하지 않는다.**
- **공개 RC 동안 첫 Coarse 실행 예산 600초 유지:** #582는 26분 실험에 600초를 적용했고, 실험 후 150초로 복귀하던 당시 계획은 [Case 대기 결정](../modules/case/decisions/case-wait-timeout.md) §3-10([#611](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/pull/611))으로 대체됐다. 600초는 Search 실행 상한이며, Case 대기 마감은 같은 결정의 §3-2·§3-8을 따른다. **최종 공개 Search/Case 상한은 10분 실제 E2E 측정으로 따로 결정**한다. 270p·CRF28은 해당 실험용 변경으로서 운영 화질·품질·비용 최적값은 미확정이다.
- **RC 성공 판단:** 제한 시간 숫자 하나보다 **검증된 입력 범위에서 사용자에게 결과가 정상 제공되는지**를 본다. 합리적인 유한 deadline, 오류 종료와 안내, 복귀 경로는 필요하다. 26분 기술 검증 실패 그 자체를 공개 지원 범위의 정상 RC 통과에 대한 자동 차단 조건으로 삼지 않는다.
- 실험 결과 원문과 수치, Search 설정은 [#452](https://github.com/kakaotechcampus-4/ktc4-chonnam-2/issues/452), [Case 대기 결정](../modules/case/decisions/case-wait-timeout.md), [Search 실험 기록](../modules/search/experiments/README.md), [Recording 한도](../modules/recording/analysis-source-limits.md)에서 관리한다. 이 문서는 새 실행값이나 자동 설정 전환을 승인하지 않는다.

## 4. 공개 C/A-1 판정은 RC 기능 병합과 별도

**공개 모드의 권위 있는 결정은 [Ops Spec §2-3 「공개 운영 모드 결정」](../runtime/ops-spec.md)이며, 실제 개방 수용 기준은 [§21-1 G1~G7](../runtime/ops-spec.md)의 검증표가 소유한다.** 비용·사용 횟수·동시성 잠정값, 원본/Case/파생물 보관 목표, 11/20 운영 종료는 **Ops Spec §2-4·§14·§21-1**에서만 관리한다.

- **C 목표:** 일반 사용자 영상의 제한적 체험은 실제 권한 격리, 비용·남용 차단, 삭제, 배포 E2E 등 **모드별 필수 Gate 통과 후 PM이 별도 Go 승인**한다.
- **A-1 대체:** C 불가 시 **허가·비식별된 공식 샘플만 실제 API·Worker·AI 분석을 수행하는 E2E**를 제공한다. 일반 사용자 파일과 우회 API 분석은 서버에서 차단하고, 샘플 실행도 Case 접근 격리·비용·삭제·실제 E2E 검증을 통과해야 한다.
- **모두 불충족:** A-1 역시 자동으로 허용하지 않으며, 실분석 공개를 보류한다. 정적/사전 계산된 시연은 실제 E2E 성공으로 주장하지 않는다.
- **11/5 기준:** 정책·우선순위 결정이지 배포 검증 PASS가 아니다. 실제 모드·공개 상한·실행 revision·보안/비용/삭제 결과는 별도 검증 후 확정한다. #452의 26분 실험은 어느 모드의 공개 승인도 자동으로 증명하지 않는다.

**동결 이후에는** 핵심 사용자 여정 중단, 신고자료 정확성, 보안·비용 통제 등 **실제 공개 차단 수준의 수정**에만 예외를 허용한다. 사유, 영향 범위, 재검증 결과, rollback 가능 여부를 PR에 남기고 PM 승인 후 변경한다. **RC 차단 결함을 Known Issue로 내리는 일도 PM 별도 예외 승인 대상**이다.

기존 역할·책임 경계를 유지한다: PM은 Product Scope와 수락·A/C Go/No-Go, Runtime/Ops는 배포 revision·운영/복구 및 실제 E2E, Case·Search·Recording·Web·Readout은 각 소유 기능과 검증을 담당한다. 새 작업 배정은 이 문서가 아니라 해당 이슈·PR에서 조율한다.

RC 판정은 각 항목마다 **정책 결정 / 구현 상태 / CI·통합·실서버 검증 / 실제 배포 ON-OFF**를 구분해서 추적한다. 검증하지 않은 상태는 `NOT_RUN`/미검증으로 남기며 완료로 쓰지 않는다.
