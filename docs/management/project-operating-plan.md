# 프로젝트 운영 계획 (Project Operating Plan)

> 서비스 기획안 1.3의 10주 프로젝트 관리안을 옮긴 초기 기준안이다. 현재 일정에 맞게 다시 계획한 문서는 아니며, 이후 PM이 실제 진행상황에 맞춰 버전업한다.

> **현재 근시일 실행 순서는 이 문서가 아니라 `management/ownership.md` §7의 `자료조사 → 모듈안 고도화 → 계약 확정 → 목데이터 통합`을 따른다.** 아래 주차 계획은 정확한 일정표라기보다 **어떤 불확실성을 어떤 순서로 제거할 것인가**를 설명하는 기준으로 읽는다.

> **이 문서의 주차 일정은 git에서 관리하지 않는다.** 실제 일정은 팀 Notion에서 관리하며, 대폭 수정이 예정되어 있다. 여기 남은 주차 표는 확정 일정표가 아니라 *불확실성을 어떤 순서로 제거하는가*라는 원칙의 기록으로만 읽는다.

## 1. 10주 마일스톤 — 불확실성을 제거하는 순서

| 주차 | 먼저 확인할 불확실성 | 확인 방법 |
| --- | --- | --- |
| 1~2주 | 평가체계, 사용자 문제의 우선순위, Gemini 기본 방식(baseline)이 충분한가 | 평가체계(Evaluation Harness)·사건 데이터 구조(event schema)·실제 장시간 영상 평가 데이터 준비 + 실제 신고자 행동 인터뷰 + Gemini 1차 탐색(Coarse)/정밀 검증(Fine) 기본 방식 구축 + 원본 영상 1시간당 비용과 처리 지연시간(latency) 측정 |
| 3~4주 | 정밀 검증(Fine)에서 구조화된 판단 근거나 참고 사례(Reference)가 실제로 필요한가 | 같은 후보 영상 구간(clip)을 대상으로 Direct vs Structured Evidence vs Structured + Positive/Hard-negative Reference A/B 비교 + 실패 원인 분류(failure taxonomy) 분석 |
| 5~6주 | AI 에이전트 기반 작업 흐름과 사건 근거 상태(Evidence State)가 처음부터 끝까지 하나의 서비스 흐름(E2E)으로 연결되는가 | 사용자 보정·분기 처리 + 사건 후보 카드 + 번호판 + 발생시각 + 선택적 GPS 활용 + FFmpeg/파일규격/신고요건 검사 + 신고자료 묶음(Package) 생성까지 통합 |
| 7~8주 | 사용자가 실제로 해야 하는 일이 줄고 신고 준비 완료까지 더 잘 도달하는가 | 기존 수동 방식과 프로토타입(Prototype)을 비교해 사용자 직접 작업시간·검토 후보 수·수정 횟수·신고 준비 완료·안전신문고 연결(handoff)·실제 제출 행동을 관찰 |
| 9~10주 | 최종 실제 영상 성능, 개인정보·보안, 통합 안정성, 발표 준비가 충분한가 | 사전에 고정한 실제 장시간 영상 평가셋(locked real test) + 회귀 테스트(regression) + 비용/신뢰구간(CI) + 개인정보·보안 검토 + H.265/대용량 영상 전체 흐름(E2E) 검증 + 데모(Demo)/질의응답 준비 |

## 2. 1~2주차에 하지 않는 것

- 예쁜 UI부터 완성하기
- 모든 교통위반 유형 지원하기
- 자체 지도 UI 구축하기
- 얼굴 모자이크를 필수 기능으로 만들기
- VideoChat3 / SentrySearch / ADAS 기반 인프라부터 구축하기
- 자체 VLM 파인튜닝(fine-tuning)
- 상시 GPU 서버(VM) 운영
- 자율형 다중 AI 에이전트 영상 탐색(multi-agent video exploration)
- 신고기록·통계 대시보드 구축

## 3. 기술 확장 원칙

> 현재 기본 방식(baseline)이 충분하다면 새로운 모델을 계속 찾는 것보다 **전체 서비스 흐름(E2E)을 완성하는 데 집중한다.** 성능이 부족하더라도 더 좋아 보이는 모델을 무작정 비교하지 않고, **실패 원인이 필요성을 설명하는 대안 기술(challenger)만 검토한다.**

구체적인 `실패 원인 → 대안 기술` 연결과 개방 절차는 `modules/search/decisions/challenger-policy.md`에서 관리한다. 챌린저를 여는 결정은 주간 회의 안건으로 올려 PM이 승인한다(`management/cross-cutting-decisions.md` A-2).

## 4. 주간 운영 리듬 — 1.3 기록

- **주간 정렬 미팅 1회** — 지난주에 새로 알게 된 것 / 이번 주 가장 위험한 문제 / 막힌 점 확인
- **제품 명세(Product Spec) 검토 주 1회** — 제품 합의·규칙·이번 범위에서 하지 않을 것(Won’t)의 변경 여부 확인
- **평가(eval) 점검 주 1회** — 사건 후보 탐색·정밀 검증·전체 흐름(E2E)·비용·실패 사례의 성능 저하(regression) 확인
- **실제 사용자 학습 주 1회** — 과거 신고 행동, 직접 작업시간, 가장 번거로운 단계 등 사용자 검증 결과 확인
- **범위 확장 여부 격주 점검** — 지도·모자이크·전체 위반유형·대안 기술 등 불필요한 범위 확장(scope creep) 방지
- **정기 통합 최소 주 1회**

2026-09-04 결정(`management/cross-cutting-decisions.md`)으로 주간 정렬 미팅에 붙는 안건 3종:

- 챌린저 개방 제안 — `search` Owner가 실패 분류 근거와 함께 올리고 PM이 승인한다 (A-2)
- 신고요건 규칙 변경 보고 — `evidence` Owner (B-3)
- 문서 일관성·모듈 경계 점검 결과 — PM (B-4, `ownership.md` §6)

1.3에 기록된 팀 공통 시간은 **매주 월요일 오후 7시~10시**다.

## 5. 방향 전환(Pivot) / 재검토 신호

아래와 같은 신호가 **2개 이상 확인되면 제품 또는 기술 방향을 다시 검토한다**는 초기 기준이다.

- 실제 신고 경험자에게 신고자료 준비(Evidence Preparation)의 불편은 존재하지만, 대신고가 줄이려는 단계의 우선순위가 매우 낮음
- 프로토타입이 사용자 직접 작업시간과 검토 부담을 줄여도 실제 신고 준비 완료·제출 행동에는 거의 영향을 주지 못함
- 사전에 고정한 실제 장시간 영상에서 최종 상위 3개 사건 포함률(Final Recall@3)이 실사용하기에 부족하고, 실패 원인별 개선 경로도 보이지 않음
- 원본 영상 1시간당 처리 비용 또는 지연시간이 일반 사용자 대상 서비스(B2C)에서 감당하기 어려우며 최적화 경로도 없음
- 범용 VLM 단일 제품이 `장시간 영상 탐색 → 사건 근거 구성 → 신고 준비 연결`까지 사실상 동일한 사용자 경험을 매우 저렴하게 제공함
- 개인정보 처리, 외부 AI API 사용, 신고용 파생영상 처리 등의 제약 때문에 실제 사용할 수 있는 서비스 흐름을 만들기 어려움

## 6. 방향 전환 전에 먼저 묻는 질문

> **사용자 문제에 대한 가설 자체가 틀린 것인가, 아니면 현재 AI·구현 방식이 부족한 것인가?**

- 사용자 불편과 신고 전환 효과는 충분하지만 사건 탐색(search) 성능이 부족함 → 제품 방향을 바꾸기보다 **실패 원인에 따른 기술 개선**을 우선
- 사건 탐색은 되지만 GPS가 없음 → 사용자 위치 단서(user hint)를 유지하고 안전신문고에서 최종 핀을 선택하도록 연결
- 사건은 찾았지만 번호판이 불확실함 → 억지로 확정하지 않고 사용자 확인으로 넘기는 대체 경로(fallback) 사용
- 기술적으로는 잘 동작하지만 자동 신고 준비가 실제 신고 행동을 바꾸지 못함 → **제품 가설(Product Hypothesis)을 재검토**

## 7. 전면적인 방향 전환을 제한하는 시점 — 1.3 초안

> 6주차까지 사용자 문제, AI 기본 방식(baseline), 전체 서비스 흐름(E2E)의 가능성을 확인한 이후에는 새로운 아이디어로 프로젝트 전체를 전환하는 것을 원칙적으로 제한한다. 이후에는 **기능 범위 축소, 품질 개선, 실패 원인에 따른 구현 변경**을 우선한다.

## 8. 의견이 갈렸을 때 다시 수렴하는 방법

> **아이디어 발산과 선택을 분리 → 각자 먼저 의견 작성 → 치명적인 탈락 기준으로 후보 축소 → 반대 관점 검토(Red Team) → PM 최종 결정**

이 문서의 일정과 운영 리듬은 서비스 기획안 1.3에서 옮긴 초기 기준이며, 이후 실제 진행상황과 팀 합의에 따라 변경할 수 있다.
